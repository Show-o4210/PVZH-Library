# 02. 键名规范与后缀索引

本地化 CSV 通常以 `Key,Value` 组织文字，但原记录也可能含额外列或空键填充，不能重写时一律压成两列。历史参考见 [cn.csv](../资源/cn.csv)；键名应以当前输入为准。

---

## 一、 卡牌本地化 Key 的四大后缀规范

在 PVZH 中，卡牌通常以 `prefabName` 为前缀关联核心文本；该字符串可能长得像 GUID，也可能是英文名称。卡牌数据中的数字 `GUID` 与此前缀不是同一概念，不能拿数字编号直接拼接键名。下面的 `[GUID]` 指示例中呈 GUID 外观的文本前缀。

| Key 后缀格式 | 示例条目 (提取自 [cn.csv](../资源/cn.csv)) | 作用与显示位置 |
| :--- | :--- | :--- |
| **`[GUID]_name`** | `002f2d4b..._name,植物养料` | **卡牌名称**。显示在手牌标题栏、卡库收藏及出牌提示中。 |
| **`[GUID]_shortDesc`** | `002f2d4b..._shortDesc,一株植物获得[+1a]/[+1h]，然后额外攻击一次。` | **简短技能描述**。显示在战斗对局手牌界面的卡牌下方面板。 |
| **`[GUID]_longDesc`** | `002f2d4b..._longDesc,一株植物获得[+1a]/[+1h]，然后额外攻击一次。` | **详细技能描述**。显示在收藏卡册查看卡牌详情时的完整文字框中。 |
| **`[GUID]_flavorText`** | `002f2d4b..._flavorText,每天最重要的营养美餐。` | **背景故事/风味描述**。显示在收藏卡册详情面板底部的趣闻风味文字。 |

## 二、 典型文本示例解构 (以吸血僵尸为例)

提取自 [cn.csv](../资源/cn.csv) 的真实数据如下：

```csv
00848e55-e990-459f-8927-beefa06f815e_flavorText,他要来吸干你的叶绿素啦！
00848e55-e990-459f-8927-beefa06f815e_longDesc,[frenzy]\n在消灭植物时获得[+2a]/[+2h]。
00848e55-e990-459f-8927-beefa06f815e_name,吸血僵尸
00848e55-e990-459f-8927-beefa06f815e_shortDesc,[frenzy]。在消灭植物时获得[+2a]/[+2h]。
```

- **文本前缀**：`00848e55-e990-459f-8927-beefa06f815e`，应从当前卡牌的 `prefabName` 核对，不与数字卡牌编号混用。
- **`shortDesc` 与 `longDesc` 的差异**：有些卡牌的 `shortDesc` 会为了战场手牌简洁度使用更简短的关键字提示，而 `longDesc` 会给出更详尽的机制解释。

## 三、 游戏系统与 UI 通用 Key

除了卡牌专属的 GUID 文本外，`cn.csv` 还包含了游戏所有的系统 UI 与文字提示：

| Key 前缀/样式 | 说明 | 示例 |
| :--- | :--- | :--- |
| **`subtype_...`** | 族群分类显示名称 | `subtype_Bean,豆子` |
| **`ability_...`** | 技能共享名与说明 | `ability_frenzy,狂热`、`ability_desc_zombies_frenzy,...` |
| **多种系统前缀** | 界面按钮与菜单提示文本，不能只搜索 `UI_` | `LANDING_ARENA_TEXT,战斗`、`PVP_TIER_0_NAME,木头级别` |
| **`hero_..._name`** | 英雄名称 | `hero_Rose_name,玫瑰` |

以上示例按 B4 同版输入核对，大小写以实际键为准。`_name` 后缀也用于英雄、排位段名和系列名称，**不是卡名的充分条件**。批量分类应再结合卡牌 `prefabName` 与配置引用；未分类项进入人工复核，不能丢弃。卡名也会出现在 `_heraldFighter`、`_heraldTrick`、`ability_link*`、任务、商品和牌组说明中，改名时要同步这些引用。

---

## 四、 自定义卡牌时的补全规则

> [!IMPORTANT]
> 当你在 Mod 中创建了一张全新的卡牌时，应按其实际 `prefabName` 补齐名称、简短／详细说明和风味等所需键；必要时还包含瞄准或来源提示。数字 `GUID` 的变化本身不决定文本前缀。
>
> 缺键可能显示原始键或空白；不能据此承诺所有缺键场景都不会出错。新增定义应检查每个所需键可解析，并实机核对显示。
