# 14 · 卡牌身份、独立文字与原版资源复用

适用：用户要求新增GUID、保留原版美术但使用不同名称/说明、定位UUID与Bundle关系，或整理相关经验。先读[第23章](../Library-docs/23.卡牌身份与资源映射/README.md)，不要把新增定义、资源寻址和收藏登记当成一项功能。

## 调查与选择

1. 确认本次范围是文档、离线修改还是设备开发；文档任务只核对已有材料，不因为有调试命令就连接设备。检查工作树和用户已有改动。
2. 读取当前原包的card_data、CN与清单指纹。数字字典GUID、Card.Guid、prefabName、运行中实体ID、Unity对象path_id分开记录；完整类型串从原包复制。
3. 原卡属性/技能沿原身份修改。新GUID若共享prefabName也会共享普通文本前缀；不要用数字GUID拼新中文Key解决独立文字。
4. 独立文字需要独立prefabName与相应中文Key；同时补完整资源寻址。R9资源别名需要加载适配，不能把它当成原版JSON或本库v1工具天然支持的功能。

## 原版资源定位

按`prefabName → Prefab/InHand/InCollection逻辑路径 → Manifest Bn/Ex → Bn的Version/Dependencies → 磁盘Bn_Version → 包内资产名`核对。保留目录前缀，分别查三个用途，不从UUID猜32位包名算法。

当前Manifest版本不等于每个Bundle版本，也不等于APK内置资源版本。使用当前清单目标，不能按后缀数字最大选文件。旧索引仅作线索，缺当前条目时明确缺证据。

资源别名必须同时覆盖“是否打包、所在包、包内可用资产名”三个环节；只改Bn可能打开正确包却加载错误内部名称。RVA与ABI按当前二进制核对，不跨版本照搬。

本轮未验证Manifest.bin优先级、编解码或删bin行为。R9复用成功依赖窄路径适配，官方JSON/bin保持不变；不要把旧笔记的建议当作当前已授权操作。

## 新身份与项目管理

- 从只读原版模板克隆，不从当前已被改写的同GUID克隆。同步内外GUID，保留未要求修改的字段及能力字面引用。
- 原版GUID在同一有效卡表中不能冲突；大编号或R9的900001起点不是社区全局保留段。生成的资源/文本别名是项目约定，校验并限制来源。
- 中文分清名称、短技能、长技能、简介和目标提示。只有明确要求才自定义说明；技能仍须编译为原版组件，不能只改描述。
- 从实际胜出的card_data生成资源别名，与部署状态共同事务提交；退出原版/其他Mod后清除旧映射。
- 多Mod仍按整文件资源族优先；单项目AI按GUID累计编辑与跨Mod合并是不同事情。卡表与中文可能来自不同胜出文件，应明确提示缺键/错配风险。
- R9有new_cards及text合同；本库tools/natural-card-author仍是v1单卡原型，未移植R9 Android工程或完整运行时。

## 验证与归档

结构校验、非目标对象/卡体/中文Key差异、引擎定义、真实文字生成器、合法抽卡出牌、技能结算、资源实际映射、动画队列、原版冷启动隔离及恢复分别留证。不能拿哈希或编译PASS替代游戏效果，也不能把InCollection图可加载当成收藏解锁。

关注正反例：修改原卡后，新卡仍从原版模板克隆；同美术两新卡名/简介互不串用；继续编辑新GUID不重新分配身份；纯文字修正不改卡牌Bundle；排序变化别名随胜出卡表变化；回到原版无新GUID与旧映射。

首次真实API可能语义遗漏，即使计划合法。保留原始响应、失败与后续修正请求，不手改答案后仍称模型首次正确。凭证不入库，摘要不收账户日志、完整调试服务、APK或游戏资产。

R9的3次API与70项游戏检查是既有产品证据，见[第23章04](../Library-docs/23.卡牌身份与资源映射/04.R9验收与失败边界.md)。本指南不是运行时部署凭证，不自动授权新设备操作；归档复查与重新游戏测试分开记录。

## R28 原版资源名校验后续

新卡资源可寻址与运行时成功初始化也要分开。见[第23章07](../Library-docs/23.卡牌身份与资源映射/07.原版资源名校验与自动获取启动故障.md)：资源名字是原版数据，不能套独立别名的英数字正则；`Typical Beanstalk` 的空格和 `Jack O' Lantern` 的单引号应原样保留。运行时与Java共同核对可信 `template_guid → prefabName` 精确对应，仍拒绝路径和控制字符。

本版650定义中646有资源名，另4个null且不可用的占位必须明确排除，不能让白名单工厂因此阻断原版空绑定启动。换基础版本重新取可信原表。新卡没获取时先查首个启动错误；资源映射先失败可能使后面的补卡Hook根本未装，不能据被拦截的查询推断收藏资格失败。主机全模板检查与具体APK／设备／冷重启结果分别留证，PENDING不写成通过。
