# 15 · 多 Mod、本地新卡身份与玩家生命周期


适用：导入大型／旧式 ZIP、制作可组牌新卡、跨 Mod 同号切换、显式复制、删除 Mod 的玩家数据保护，或验收从收藏到正式对局的完整流程。资源身份基础先读 [Agent14](14-card-identity-and-assets.md)；详细说明见[第23章05](../23.卡牌身份与资源映射/05.本地新卡身份与服务器裸GUID边界.md)与[第20章06](../20.工程体验跃迁-资源门卫与教程跳过/06.多Mod资源映射与外国ZIP实测.md)。

## 开始前

1. 确认用户要求只是评估、文件制作还是设备验收；文档中的命令不是设备操作授权。检查当前工作树，保留已有 R9／R10／Mod2／Library 改动和失败记录。
2. 保留输入 ZIP 原件与 SHA；读取设备当前 Manifest、已加载收据、Mod 列表顺序／勾选。选择状态与实际加载状态可不同，不擅自改成一致。
3. 源资源、可信原版底稿、项目草稿和实际加载版本分开。不要把活动的改版文件再次登记成原版；底稿或目标版本未知时技术失败要明确。
4. 真正进行正式 PvE 时先备份当时实际 PlayerData、shared_prefs、受管资源与启动器记录；只做四份牌组／库存备份不足以覆盖进度和奖励。原权限／SELinux 保留，离线测试，恢复按本次差异处理，不能清空账户。

## ZIP 与多 Mod 规则

- 先从深目录识别当前 Manifest 登记的逻辑资源族，保留目录，只去末尾版本后缀；当前清单决定目标编号，不选最大尾号。
- 未知项、路径歧义和实际部署失败分别记录；未知文件保留在原件，不向任意应用路径盲写，不执行 ZIP 内程序。
- 顺序靠前整文件优先，显示采用／覆盖来源。AI 对某项目的局部编辑不代表跨 Mod 按 GUID／CN Key 自动融合。
- 资源部署、历史目标恢复、运行配置和加载收据保持事务一致。Unity 加载后不得只换磁盘文件继续当作新版本；要求完整重启。
- Syndrome 220 文件原样部署、985 定义、18 项运行抽样是特定原包的历史结果，不证明所有外国改版或全部技能兼容；英语包存在不证明当前中文准确。

## 新卡与来源身份

- 定义有效、资源可寻址、本地拥有权、普通收藏、合法组牌、保存、冷启动、正式出牌分别验证。Token 保留为技能定义，不强制发入普通卡库。
- 卡册另有GUID到职业合图Sprite的索引，不只按prefab路径加载。路径别名和Owned查询成功不等于可见卡面；新GUID回退只用明确原版模板且只补原返回null，不覆盖外国包已有非null美术。模板holder未加载或映射歧义时记录，不盲调可能抛托管异常的原生方法。
- 候选取实际卡表相对原版的 GUID 差集；可收藏判断继续使用本版原版过滤。至少四张的本地补齐要幂等，不改库存 Delta、货币、英雄和卡包。
- 安装内分配器扫描已登记的禁用／当前 Mod、历史及已知草稿，持久保留预约／观察号，不回收取消草稿。损坏登记不静默重置；这不是跨设备或社区的全局号段。
- 原版 GUID 共享；原生 `_pvzh` 新卡用稳定别名谱系；旧式新卡用 namespace、GUID、prefab。仅中文或身材修改不重造身份，不把整个勾选组合当作单卡来源。
- 显式 clone 必须继承 `card_identity_namespace`，二代 clone 也保留；已有原生别名保持，副本新造原生卡拥有副本别名。只测试 `_pvzh` clone 不足以证明外国包 clone 安全。
- 无 manifest 的外国原始 ZIP 用包 SHA 生成 ID，另一个 SHA 且无明确同源声明时保守视为新来源，可能要重新组牌。不得按卡名、相似卡体或作者展示名擅自推断同源。

## 切换、删除与旧收据

从旧收据对应的归档卡表、活动文件 SHA 和来源建立旧身份，不能用目标表代替旧表。R10 没有身份字段可按经核实的旧资源迁移；外部改动、旧资源缺失或无法读取时记未知来源。

保留原版与已核实同身份的新卡引用；缺失、同号异身份、未知旧归属按明确保守策略备份后精确处理。保留牌组元数据、有效邻卡、其他牌组和未知 protobuf 字段，不改成整份 JSON，也不全清 PlayerData。不足四十张让玩家补齐，不自动填卡；再次启用不自动覆盖玩家已经编辑的牌组。

资源、玩家文件、身份收据进入同一事务；先整批核对 target.before、stage.after、backup.before，再逐项写前重查。回滚遇到目标仍等于before可直接跳过，只有after行才要求可靠backup并恢复后核对；外部新内容停止自动覆盖。备份在prepare时有效不证明commit时仍有效，R11已实际发现并修复这个缺口。

纯身份／wire 单测不能代表存储事务；真实Safety／Codec加桌面静态文件API替身的18例能覆盖逻辑故障分支，但同样不代表Android权限／SELinux、完整资源事务、进程中断和设备恢复已经实测。分层报告并保留修前两例FAIL。

统计分清逻辑牌组与物理 full record：同一副套牌在 PlayerDecks 与 Delta 各出现一次，每份删 8 张，底层 16 引用不等于两副牌组。R11迁移已有此精确设备证据；本轮正式流程和恢复以第23章05的最终表及来源为准。

## 正式玩家流程验收

1. 真实收藏 UI 显示新普通卡，Token 不进入普通收藏。Provider 可见或有 Sprite 不能代替屏幕实际显示。
2. 真实牌组编辑器中加入／移除／保存新卡，按原版 Validator 检查职业、最多四张与 40 张。若用原 Provider 预建临时牌组，明确写“准备动作”，再验实际 UI 编辑，不能声称从空牌组全程手动。
3. 从原版当前真实进度节点进入正式 PvE，核对节点、模式、所选保存牌组与实际 engine 状态。原生 signal 导航须如实标明；单个 `fixture=false` 也不足以证明没有替换局。
4. 正式对局不调用调试 give／draw／summon／强制伤害或 fixture 注入来造胜利。测试卡可以在资源定义中做强，局内由正常 UI 与原版流程出牌结算。
5. 自然观察原版胜负 flow、RecordWin、实际结算页。离线若卡在奖励／服务器步骤，分层记录已完成和未完成部分，不伪称同步通过。
6. 完整冷启动核对同一副牌组与进度；最后停游戏，对照本轮备份恢复文件、权限／SELinux、资源、顺序／勾选、网络和事务状态。

R10的有画面fixture验证不是正式campaign通关；R11各层是否完成以本轮最终证据为准，不能只从迁移通过推出整条流程通过。新结果必须绑定候选 APK／脚本／资源、实际通过／失败项目和恢复摘要。

## 服务器与归档边界

官方返回的裸 GUID 没有 namespace，不能区分“以前 A 的同号卡”和“现在 B 的同号卡”。本地过渡保护不扩展官方协议；不能永久屏蔽碰撞数字，否则当前 Mod 的同号卡也无法组牌。不要宣称官方客户端、云端、联机和跨设备都兼容。

公开资料只保留关系、合同、筛选结果及来源 SHA。源码使用显式路径／类型白名单；APK、Bundle、全量导出、原始 API 账户记录、日志、PlayerData、凭证与签名均排除。归档工具的离线 PASS 不等于游戏通过，已有旧 FAIL 与用户工作树不删除。库内公开 Python v1 工具与独立 Android 产品能力继续分开。

## R26 可配置获取后续

见[第23章06](../23.卡牌身份与资源映射/06.可配置新卡获取与手机Mod列表.md)。此前R10/R11固定至少4张属于历史实现；R26默认开4张、目标1～999，只补同身份的可收藏新卡，不扣已有，不改变原版牌组4张上限。获取开关与模式/身份保护分开；候选取最终生效整表的GUID差集，token、超能、不可用继续排除。

检查持久化时，冷启动又得到4张不够：它可能每次从0重新补4。应检查补差before/quantity，或先获取8张再把目标降到2后冷启动确认仍持有8张。使用原版本地holder/保存命令/序列化链，不直接重写玩家protobuf，不操作库存Delta或宣称服务器同步通过。实机结论以第06篇的最终状态和来源指纹为准。

Silver类基础卡还会被原启动Fixup修正到最多4张。R26的候选专用保护只针对当前Mod有效可收藏的新GUID及原IsSilverCard为true的调用，原650张与Token不变；auto关闭不关闭此拥有权保护。别把集合显示、原Getter或缓存回写混为一谈，也不要修改用户卡的set来隐藏失败。版本缓存只解决内容变化后的重检，不能单独保存“低目标下已有8张”的语义。

## R28 获取故障的启动前置

见[第23章07](../23.卡牌身份与资源映射/07.原版资源名校验与自动获取启动故障.md)。排查顺序补上“已采纳／实际卡表与CN → 本次冻结获取设置 → 资源绑定 → 运行时安装状态 → 原生资格／库存／保存”。如果 `boot_failed_phase=card-assets`，先解决绑定；`player_cards` 检查被拦截表示未执行，不表示Token或不可组牌。

原版资源名允许真实空格、单引号，使用可信模板精确白名单，不能删空格或修改用户set绕过。650定义分646有名模板与4个不可用null占位，资源覆盖不等于收藏覆盖。具体新卡首次4张与冷重启零补差必须独立验收；RC1的主机构造失败和后续修正保留，未完成设备项保持PENDING。

## R29 已有数量连续性后续

见[第23章08](../23.卡牌身份与资源映射/08.本地新卡连续性与同账户保护.md)。自动获取与已有拥有权保护分开：关闭auto不等于允许丢已有新卡，保留已有数量也不能以目标4张重新发放替代。

制作供玩家获取／组牌的新卡时，先选原版可收藏非Token模板，检查真实set、双层cheats及Unusable。新增GUID不自动去除这些标记；R29没有collection覆盖字段或Token转普通卡接口。只读UI分类不是原生资格PASS，精确外观只属于Token时说明冲突，不以调试发牌或放宽库存限制替代。

1. 每条Unity释放前，在资源／PlayerCardSafety成功后，为实际赢家卡表的有效同身份candidate建立本次事务/PID的只读本地已有数量证明。Token等排除；不以Delta为拥有权源，不复制原卡／货币／整份账户。
2. 核对exact本地holder、Local persister、当前身份、locator与已缓存persister路径及Android用户根；只看GUID或holder指针不够。跨Mod身份、账户、路径、事务不明一律保护性skip，不放宽为按裸GUID恢复。
3. ContainsKey严格区分缺键与显式0。首次可判定库存即消费seed，无需补回也消费；只恢复缺键的原已有量，保留0与合法低数量，用户后来消耗到缺键不可再复活。
4. 后续只在确切Sync接受调用位置／线程／holder／旧对象／请求账户下，延续紧邻旧库存的真实数量，不用历史max、旧seed或发卡目标；不改DTO／Delta／官方卡。没有实际accept证据就不称官方同步通过。
5. 原生保存、读回和错误健康状态分别核对。关闭auto的RC2观察为4→0→4，grants空、原自动保存0、连续性独立保存1，证明本地启动接管；sync_accepts=0及网络validated=false保留，不能称完整联网或稳定验收PASS。
6. 资源先失败且seed未消费时，旧证明只归档供明确恢复，不自动跨PID重放；不要宣称所有失败后都能自动救回。证明含账户持卡数据，不随Mod导出、入Git或公开日志。
