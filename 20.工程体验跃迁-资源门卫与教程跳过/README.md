## 核心架构：Pre-Unity 门卫与常规动态 Hook 的本质区别

很多初学者容易将“资源门卫”误当成普通的 Frida 动态 Hook。**两者的执行时机与宿主生命周期有着本质的天壤之别**：

```mermaid
graph TD
    subgraph 阶段一: Pre-Unity 原生资源门卫 (OS / Activity 级抢先门禁)
        A["玩家点击图标启动 APK"] --> B["ResourceGateActivity (MAIN/LAUNCHER) 抢先运行<br/>此时系统尚未加载 libunity.so / libil2cpp.so / Frida!"]
        B --> C{"检查外部缓存目录<br/>/files/cache/ 是否齐全 2880 个 Bundle?"}
        C -->|"已就绪 (次启 23ms)"| D["极速放行"]
        C -->|"未就绪 (首启 8秒)"| E["从 APK assets 快速释放 2880 个 Bundle 至缓存目录"]
        E --> D
        D --> F["显式 Intent 启动原版 NimbleActivity / UnityPlayerActivity"]
    end

    subgraph 阶段二: 常规动态运行时 Hook (进程内 In-Process 动态插桩)
        F --> G["加载 libunity.so / libil2cpp.so 引擎"]
        G --> H["libpvzhgadget.so 自动拉起执行"]
        H --> I["FTUE 教程跳过模块: Hook 启动状态机直奔主界面"]
        H --> J["DeckShare 卡组分享模块: 挂载 + 号悬浮球与原生 Provider"]
    end
```

### 关键维度辨析：
- **常规动态 Hook（阶段二）**：工作在 Unity 初始化中或之后，用于修改运行时的内存变量、指针与 UI 交互；
- **Pre-Unity 资源门卫（阶段一）**：工作在 **Unity 和动态库完全尚未加载的绝对冷启动阶段**。如果等到 Unity 启动后再去阻止下载，官方的 C++ CDN 线程早就开跑了，为时已晚！必须在 Android Activity 入口级别实行物理隔离与前置放行。
