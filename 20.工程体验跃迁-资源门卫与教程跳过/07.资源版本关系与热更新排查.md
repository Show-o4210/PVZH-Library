## 远端名字与本地缓存名字

同版SO／默认Android配置已核对URI构造，本次实际HTTP成功响应支持以下路径：

```text
https://pvzheroes-live.ecs.popcap.com/assetbundles/ClientServerContentAssociations.txt
https://pvzheroes-live.ecs.popcap.com/assetbundles/android/1.67.13/manifest_version
https://pvzheroes-live.ecs.popcap.com/assetbundles/android/1.67.13/AssetPathsManifest
https://pvzheroes-live.ecs.popcap.com/assetbundles/android/1.67.13/data_assets
https://pvzheroes-live.ecs.popcap.com/assetbundles/android/1.67.13/loc/cn
```

Bundle HTTP请求使用逻辑名，不追加本地数字后缀，也不把`UnityABVersion_11064`拼进远端URI。下载后，本地精确目标为`cache/bundles/files/<logical>_<Version>`，例如`data_assets_36`、`loc/cn_9`。APK内完整Bundle则按无后缀逻辑名放在`assets/AssetBundles/`，复制器依据索引产生本地名。

`UnityABVersion_11064/AssetPathsManifest`内的`BundleNameToDetails`提供Version、Size、Dependencies；`BundleNamesByAssetPath`的值为带Ex／Bn的对象，不是简单字符串。应解析这份实际清单，不能用“目录里数字最大的文件”代替定位。

## 元数据与hash来源

完整分发同时包含Manifest JSON／bin、三个ABG、versions及manifest_version等元数据。三个`.abg.version`也分别记录。本次旧设备Versions仅bootstrap组为11033，官方三组version均返回11057；构建只修正这一组记录，2880项Bundle版本保持与清单一致。

- **AssetPathsManifest.bin是客户端生成的二进制缓存。** 本次采用与同一11064 JSON匹配的设备原件，SHA为`925aa4393eed2c838edf837470c0e24d2381f8bbb9c2af28f7e78398da4fd6d8`；不能称作HTTP官网下载。
- 本次官方AssetPathsManifest JSON SHA为`7e553a0a4de32c42cb9d750ba7ca8f1ea87ede43230fe13b754e528e4c3e39eb`，与设备对应JSON一致。此SHA是本轮对响应字节计算的工程指纹。
- **该官方Manifest没有单包官方SHA字段。** 下载收据／APK索引中的SHA是本轮实际取得字节的指纹，不是官方发布的签名或hash清单。官方Size、UnityFS头、解析回读和来源稳定性检查分别记录，不能混写成官方SHA校验。
- ETag、Last-Modified、版本映射字符串与内容SHA用途不同。它们不能单独证明今天刚发生更新，或所有文件均已更名。

## 为什么同族旧文件不能满足新目标

本次QA缓存有两个精确目标缺失：一个autotagged资源需要`_3`但仅有`_1`，ZombiesShell需要`_26`但仅有`_23`。同族存在不等于清单目标齐全；也不能将旧字节直接改名充数。R30门卫的按族复用与少量抽样收据遗漏了这类缺项。

同时，活动Mod会合法改变`data_assets_36`、`loc/cn_9`等内容和长度。**Size／工程SHA不同只说明与原版不同，不足以断言损坏。** 修复前先核对当前选定Mod、来源与部署收据，不能用官方原版覆盖正在使用的Mod。

R31门卫改为逐项核对精确目标：

| 情况 | 当前处理 |
| --- | --- |
| live≤内置Manifest，精确目标缺失 | 从本APK对应原始字节验证Size／SHA后原子补齐，保留旧编号 |
| 精确目标已存在 | 保留，包括长度不同的Mod；不把存在性复用说成原版内容校验通过 |
| live>内置Manifest | 保留较新元数据，按其清单重查；缺项列pending，不用旧字节假装新版本 |
| 较新非核心缺包 | 提示待官方更新，给Unity原有下载机会；内置准备成功与目标完整分开显示 |
| 较新指针对应Manifest缺失、清单损坏／越界 | 报告技术失败，不制造虚假的ready目标表 |

新状态`embedded_manifest`、`active_manifest`、`checked_target_count`、`pending_current_targets`与`current_targets_complete`分开登记。`last_run_successful=true`可以只表示内置准备成功；`current_targets_complete=true`也只保证当次精确目标存在，不保证已有内容为官方原版、可加载或技能正确。旧收据不能跳过新检查。

## 排查顺序

1. 记录APK、AssetVersion、Manifest、ABG及Bundle各版本域；先判定问题属于哪一域。
2. 读取当前有效Manifest，列出精确目标、缺项、依赖及原有旧编号；不要先清空缓存或按最大后缀选文件。
3. 区分缺文件、与原版字节不同、解析失败、Mod部署不同和实际游戏加载失败；保留原包、活动Mod和账户。
4. 新资源从已证来源进入隔离暂存区，核对来源和所需元数据；补缺采用原子写入，不沿用“同族任意版本存在就成功”。
5. 分别验新环境完整复制、升级补缺、现有Mod保留、较新未知清单边界及Unity加载。资源host通过不覆盖正式任务、对话或战斗结算。

未来更高Manifest的核心卡表／关卡／中文缺失仍可能被LauncherStore原有底稿要求拦住；本轮没有实现通用更新救援。核心卡表若变动，还须重验原版SHA绑定、资源白名单、技能目录和编译器，不能只替换文件便声称全部兼容。已有但损坏／零字节的精确目标也未自动覆盖修复，以免误删Mod。
