# 01. 从热更痛点到 Pre-Unity 资源门卫架构

在所有现代移动游戏中，为了降低应用商店的初始下载包体，通常都会采用“微端 + 运行期热拉 CDN 资源”的架构：PVZH 官方原版 APK 体积仅约 80 MB，但在第一次打开游戏时，它会强制联网向 CDN 请求下载 **2,880 个 AssetBundle（总计约 645 MB 资源）**。

对于普通玩家，这需要经历几分钟到十几分钟的漫长等待；而对于需要反复卸载、清理数据、进行回归测试的 Mod 开发者而言，每次调试都要重新下一遍 645 MB 简直就是一场噩梦。

本篇讲解为什么在 Unity 引擎内部做动态 Hook 无法优雅解决该问题，并详细剖析一套在操作系统层抢先拦截的 **Pre-Unity 原生资源门卫（Resource Gate）架构**。

---

## 一、 为什么常规动态 Hook 对热更下载无能为力？

很多熟悉 Frida 的开发者首先会想：“*我能不能直接在进入游戏后，Hook 它的下载函数或者伪造下载完成的返回值？*”

在实操中，这种方案几乎必然遭遇以下三大致命困境：

1. **时序严重滞后与竞态（Race Condition）**：
   - 当 Unity 引擎和负责网络通信的 `libNimble.so` 初始化时，C++ 层的底层下载线程几乎在瞬间并行启动；
   - Frida 动态注入哪怕只慢了 100 毫秒，官方的下载界面就已经被推上屏幕并开始建立 TCP 握手。
2. **底层资产校验死锁**：
   - 官方游戏并不仅仅是“下载文件”，还会对本地下载目录下的 2,880 个文件进行逐一校验；
   - 如果只是在内存里 Hook 欺骗游戏说“我已经下载完了”，但磁盘里根本没有这些 AssetBundle 文件，Unity 在随后的场景加载中一旦通过 `AssetBundle.LoadFromFile` 找不到贴图和着色器，**游戏会瞬间崩溃报找不到文件，或者画面全部变成粉红色的无材质方块**！
3. **内存与磁盘状态不一致**：
   - 要让游戏真正正常运行，这 2,880 个 Bundle **必须物理存在于手机磁盘中**。

---

## 二、 破局思维：在 Unity 诞生之前接管控制权（Pre-Unity Gate）

既然在 Unity 运行期干涉太晚，最完美的破局思路就是：**在 Unity 引擎、IL2CPP 二进制和 Frida Gadget 根本尚未被系统加载时，由一个极简的纯原生 Android Activity 抢先启动！**

```mermaid
graph TD
    subgraph 传统原版启动链路
        A1["玩家点击图标"] --> B1["系统直接启动 NimbleActivity / UnityPlayerActivity"]
        B1 --> C1["立即加载 libunity.so / libil2cpp.so 引擎"]
        C1 --> D1["Unity 扫描本地磁盘发现缺少 645MB Bundle"]
        D1 --> E1["强制进入漫长下载黑屏 (卡顿等待 15 分钟)"]
    end

    subgraph Pre-Unity 资源门卫启动链路 (本方案)
        A2["玩家点击图标"] --> B2["系统启动 ResourceGateActivity (真正的首选入口)"]
        B2 --> C2["此时内存中完全没有 libunity.so / libil2cpp.so ! 纯原生轻量状态"]
        C2 --> D2["检查磁盘，若缺失则从 APK 内部秒级释放 2880 个 Bundle"]
        D2 --> E2["资源就绪后，显式 Intent 启动原版 NimbleActivity"]
        E2 --> F2["Unity 启动扫描磁盘: 发现 2880 个文件完完整整!"]
        F2 --> G2["认定为已下载完成，0 秒无感直接进入游戏大厅!"]
    end
```

## 三、 冷启动进程验证（Ground Truth 证据）

在 Google Pixel 6（Android 16）真机上的实测抓取证明了这种**生命周期的完全物理隔离**：

### 1. 门卫启动时的系统状态
将门卫配置为首发入口后，冷启动第一秒执行系统进程转储：

```bash
adb shell dumpsys activity top
```
输出显示：
```text
TASK com.ea.gp.pvzheroes id=1234
  ACTIVITY com.ea.gp.pvzheroes/com.pvzh.sharecode.ResourceGateActivity 78abcd0 pid=28012
```

此时读取该进程 `/proc/28012/maps` 内存映射，**结果证实**：
- ❌ **`no libunity.so`**
- ❌ **`no libil2cpp.so`**
- ❌ **`no libpvzhgadget.so`**
- ❌ **`no libNimble.so`**

整个进程就是一个纯粹、轻量、秒开的 Android 原生应用，内存占用不足 20 MB，没有任何 3D 渲染开销。

### 2. 门卫放行后的系统状态
当门卫在后台以极高速度将预置的 2,880 个 Bundle 拷贝到指定目录后，调用 `startActivity(new Intent(this, NimbleActivity.class))`：

```bash
adb shell dumpsys activity top
```
输出显示：
```text
TASK com.ea.gp.pvzheroes id=1234
  ACTIVITY com.ea.gp.pvzheroes/com.ea.nimble.plugin.NimbleActivity 99ef012 pid=28012
```
此时原生引擎正式加载，内存中按顺序映射出 `libunity.so`、`libil2cpp.so` 和 `libpvzhgadget.so`。而此时**本地的 645 MB 资源早已稳稳当当躺在磁盘里**，游戏直接跳过了全部热更下载逻辑！

## 四、 本篇总结

理解了这一架构，我们就清晰地把**“资源门卫”**与**“常规运行时 Hook”**划清了界限：
- **资源门卫（Resource Gate）**：属于 **OS 级入口前置门禁（Activity-level Pre-load Gate）**，负责在引擎点火前把燃料（AssetBundles）备齐；
- **常规动态 Hook**：属于 **引擎级内存插桩（In-process Runtime Hook）**，负责在引擎运转中改善交互逻辑。

下一篇，我们将深入工程落地细节 —— **如何将这 2,880 个 Bundle 巧妙打包进 APK，并实现首次启动 8 秒极速解包、后续启动 23ms 极速放行的双轨校验流！**
