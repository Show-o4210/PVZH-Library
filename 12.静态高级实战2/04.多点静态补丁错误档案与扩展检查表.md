# 04. 多点静态补丁、错误档案与扩展检查表

本篇面向**维护者**：如何在同一 v3c RX cave 中堆叠多个 Hook、调试向的单卡上限破限、赋甲阶段踩过的完整错误档案，以及扩展下一个能力前的检查清单。  
卡师排错仍优先看第 11 章部署篇与工程内 `troubleshooting` 类文档。

---

## 一、 多 payload 共洞（v3c 不变）

### 1. 布局原则

```text
libil2cpp.so  RX PT_LOAD 末尾扩展 cave
├── inventory merge payload      ← SetLocalPlayerInventory epilogue
├── grant armor + History        ← ProcessEffect @ type 分流
├── sprite map 19→8              ← GetSpriteTypeFromGrantableAbilityType
└── （零填充至页/空隙边界）
```

| 约束 | 说明 |
| :--- | :--- |
| **禁止**新增 `PT_LOAD` | 第 11 章 v1/v2 已证 Houdini / 真机易死 |
| **必须**同步 SHT `sh_offset` | 否则真机 bionic 白屏；`PT_DYNAMIC` 与 `.dynamic` 偏移必须一致 |
| 反汇编 cave 用 **VA** | file offset 与 VA 常差 `0x4000`，ADRP 译错会全盘飞 |
| asm 字符串保持 **ASCII** | Keystone 非 ASCII 会导致构建失败却误装**旧 so** |

### 2. 主要锚点表（本快照，跟版必重核）

| 用途 | Hook / 符号 | 备注 |
| :--- | :--- | :--- |
| 库存 Merge | `SetLocalPlayerInventory` epilogue **`0x1FEB4E0`** | 见第 11 章 |
| 赋甲分流 | `ProcessEffect` **`0x21F6E24`** | `w21`=type |
| 图标映射 | `GetSpriteTypeFromGrantableAbilityType` **`0x1EFF22C`** | 19→8 |
| 单卡上限 | 见下节多处 `mov #4` | 调试便利 |

以当次构建产物 `dist/arm64-v8a/PATCH_INFO.txt` 为权威。

### 3. 推荐构建与安装顺序

```bash
# 1. 确认 reference 为原版 so（可从补丁 so 还原）
python scripts/recover_original_so.py [patched.so]

# 2. 总装
python scripts/build_and_patch.py

# 3. 重打包 / 签名 / 安装（签名变更需卸载重装）
python scripts/repack_apk_with_so.py
# jarsigner … ; adb install -r …
```

**禁止**：构建失败（非 0 退出）仍 repack——极易装上旧二进制，排查成本极高。

## 二、 单卡份数上限 4 → 40（调试补丁）

组卡界面「锁 4」有**多源**，只改 C# `const` 内联往往不够：

| RVA（示例） | 语义 | 补丁思路 |
| :--- | :--- | :--- |
| `0x1FE7E34` | `GetMaxCopiesOfCard` 内联 | `mov w0,#4` → `#40` |
| `0x1FEB168` | `ClampCardInventoryToMaxInDeck` | 同上 |
| `0x1EE4BF4` | `AutoDeckBuilder.GetRemainingAllowedCountOfCard` | `mov w8,#4` → `#40` |
| `0x1D32444` | `CanMoveCard` 对比 `DeckEditorGroupConfig.MaximumCardCount` | 配置字段常为 4，需改比较立即数 |

> [!WARNING]
> **不要误伤**枚举立即数，例如 `CardLocation.Unowned = 4`、`MoveCardFailureReason` 等。  
> 首轮只改 const 时，组卡 UI **仍可能锁 4**（已复现）：真正拦路的是 `DeckEditorGroupConfig` 路径。

该补丁面向**本地调试 / 压力测试**，是否打进社区默认包由维护者决定。

## 三、 错误档案：赋甲阶段 E1–E7

下列条目来自真机会话复盘，保留**失败路径**以便对照 logcat。

### E1 — 错误 TypeInfo

| | |
| :--- | :--- |
| **现象** | 打出 grant 即 SIGSEGV，`fault addr 0x28`，pc 落在 il2cpp 字符串/元数据 |
| **误用** | `Armor..ctor` 里给 **ModifiableInt** 用的静态槽 |
| **正确** | 与 `ArmorSystem.IsAmoredTarget` / `GetComponent<Armor>` **同一业务 TypeInfo** |
| **教训** | ctor 旁的 class_init 槽 **≠** `typeof(T)` 业务槽 |

### E2 — `GetTypeFromHandle` 参数类型错误

| | |
| :--- | :--- |
| **现象** | 栈落在 payload 内 `bl GetTypeFromHandle`，仍 fault `0x28` |
| **原因** | 需要 **`Il2CppType*`**（常为 `&klass->byval_arg`），不能传裸 `Il2CppClass*` |
| **教训** | 优先抄游戏已验证的 `GetComponent<object>` + rgctx 用法 |

### E3 — 错误 Type 调用 `AddComponent` → abort

| | |
| :--- | :--- |
| **现象** | SIGABRT；经 `Entity.AddComponent` → `InstanceManager` → `isinst Poolable` 失败 |
| **原因** | RuntimeType 不是可池化的 `Armor` |
| **教训** | `AddComponent(Type)` 强依赖正确类型 + 池 |

### E4 — 手搓 `object_new` + 改 `List<Component>`（最致命）

| | |
| :--- | :--- |
| **现象 A** | 卡能打出，**附甲不生效** |
| **现象 B** | 对局一段时间后闪退 |
| **栈特征** | 线程 **`AssetGarbageCol`**，il2cpp GC mark，怪异 fault 地址 |
| **原因** | 未走 `InstanceManager.Acquire`；破坏托管堆；**延迟**崩溃极难查 |
| **教训** | **永远不要**在 Entity 上手工 new + 改 Components 列表 |

### E5 — 构建脚本 Unicode

| | |
| :--- | :--- |
| **现象** | Keystone `encode('ascii')` 失败；若未注意会装上旧 so |
| **原因** | asm 注释含中文破折号等非 ASCII |
| **教训** | payload 汇编源仅 ASCII；检查 exit code 再 repack |

### E6 — 签名与安装

| | |
| :--- | :--- |
| **现象** | `INSTALL_FAILED_UPDATE_INCOMPATIBLE` |
| **处理** | 卸载旧包再装（本地数据会丢） |
| **教训** | 社区包签名策略固定，避免玩家反复卸装 |

### E7 — logcat 抓栈注意点

| | |
| :--- | :--- |
| **残留信号** | 旧 pid 的 Fatal 可能混进 buffer → 先 `pidof` 确认当前进程 |
| **有用信息** | Unity `E CRASH` 完整 `#00…#N` 与**线程名**（UnityMain vs AssetGarbageCol） |
| **命令备忘** | 见本节末尾 |

### 附：第 11 章 ELF 族错误（索引）

| 编号 | 现象 | 根因方向 |
| :--- | :--- | :--- |
| ELF-v1/v2 | 无法 dlopen / `JNI_OnLoad` | 新 PHDR / 新 PT_LOAD |
| ELF-v3b 真机白屏 | 秒退 | SHT `sh_offset` 未与 `.dynamic` 同步 |
| **v3c** | 真机稳定 | RX cave + SHT 平移 |

## 四、 抓栈与真机验收命令

```bash
adb shell pidof com.ea.gp.pvzheroes
adb logcat -b all -c
# 复现后：
adb logcat -d -v threadtime
# 过滤关键词：E CRASH / Fatal signal / libil2cpp / Unable to load / dynamic section
```

验收清单：

- [ ] 冷启动不白屏（v3c）  
- [ ] 空 `inventory_extra` 可进游戏  
- [ ] 当场不崩（UnityMain）  
- [ ] 玩 1～2 分钟不崩（**GC / AssetGarbageCol**）  
- [ ] 玩法效果（减伤 / 数量）  
- [ ] UI（可后置，但发版前应目视）  

模拟器通过 **≠** 真机通过（华为等 Android 10 设备上 v3b→v3c 已验证过一次）。

## 五、 未完成边界（勿当稳定 API）

| 项 | 状态 | 说明 |
| :--- | :--- | :--- |
| Splash `type=20` | WIP / 曾闪退 | 字段为 `int DamageAmount@+0x10`，与 Armor 的 `ModifiableInt` 不同；MethodInfo 槽易误绑 |
| Multishot 等 21–23 | 未真机验收 | 错误 BSS 槽曾指到 Firebase / Nimble 符号 |
| Remove / Duration | 未完整 | 赋甲移除不走官方 Grantable 拆除 |
| armeabi-v7a | 未交付 | 仅 arm64-v8a |
| Heroes merge | 非重点验证 | 库存以 Cards 为主 |

**Il2CppDumper 入口不可盲信**：多个标签指向函数**中段**。  
扩展 Splash 前必须用反汇编确认 prologue，并用 **xref** 鉴定 MethodInfo 槽，禁止「地址长得像就用」。

## 六、 扩展新能力检查表（复制用）

### 加 Hook 前

- [ ] dump 里分清：目标是 **GrantableAbility**、独立 **Component**，还是纯数值字段？  
- [ ] 找到游戏**已有** Get/Has/Add 路径（抄 `ProcessArmoredDamage` 之类，而不是 ctor）  
- [ ] 记下经 xref 确认的 MethodInfo / TypeInfo 槽与 init flag  
- [ ] 确认创建是否必须 `InstanceManager.Acquire`  
- [ ] UI：History / 枚举映射 / 卡定义 special_abilities，断在哪一环？  

### 实现时禁止

- [ ] 禁止新增 PT_LOAD（本游戏 v3 结论）  
- [ ] 禁止对 `Entity.Components` **手写 List 追加**  
- [ ] 禁止对未确认 TypeInfo 调 `GetTypeFromHandle` / `AddComponent`  
- [ ] 禁止 asm 非 ASCII  
- [ ] 禁止构建失败仍 repack  
- [ ] 禁止把调试用 MAX_COPIES 与实验枚举不经说明打进「稳定」说明文档  

### 发版前

- [ ] `PATCH_INFO` 记录 hook、cave、hash  
- [ ] 真机冷启动 + 对局效果 +（如需要）UI 目视  
- [ ] 卡师文档只暴露**已验收**字段（当前稳定成品示例：`19` = 赋甲）  
- [ ] 声明：仅本地研究，勿用于官方 PvP

## 八、 结语

第 11 章打通了「自定义卡能进组」；第 12 章打通了「Base 可扩展真实战斗语义」的第一条成品能力——**运行时赋甲**。  

可复用的不是某一个 RVA，而是方法：

1. **规则载体**对齐官方组件与系统；  
2. **托管对象**只走游戏池化路径；  
3. **UI**接 History / 映射，不另起炉灶；  
4. **ELF**坚持 v3c；  
5. **失败路径**写进档案，让后来者少付一次 GC 延迟崩溃的学费。

愿每一次 SIGSEGV，最后都能变成检查表上的一行。
