# 03. AB 包内 BKHD SoundBank 解构与手改警告

Unity TextAsset 可以承载 Wwise SoundBank 二进制数据。例如[康加僵尸资源包](../资源/1f826228d36c6f0478c72b56f17541d2_1)的历史案例。识别标记是载荷开头的 `BKHD`，不是 Unity 对象名称或 `.bnk` 后缀本身。

## 一、常见 Chunk 的分工

银行由多个 Chunk 组成；常见结构如下，**并非每个银行都包含所有块，也不保证排列完全相同**。

| Chunk | 作用 |
| --- | --- |
| `BKHD` | 银行头，含格式版本与银行标识等信息；不是全部媒体的偏移表 |
| `DIDX` | 内嵌媒体索引：媒体 ID、相对 `DATA` 载荷的偏移、字节长度 |
| `DATA` | 内嵌媒体字节；可能是 WEM，也可能是 Wwise MIDI 等数据 |
| `HIRC` | 事件、动作、容器、音乐片段/轨道等对象及引用、播放属性 |
| 其他块 | 初始化、状态、环境、平台等信息，提取/回写时不能随意丢弃 |

本次 `Global_Data.bnk` 有音乐逻辑但没有 `DATA`；实际媒体在外部流文件或其他银行中。“没有 DATA”不代表这个银行没有价值。

## 二、只读提取内嵌媒体的基本规则

对本次小端银行，Chunk 头由 4 字节标记和 4 字节载荷长度组成。`DIDX` 每个索引项是三个 32 位小端无符号整数：

```text
(media_id, offset, size)
media_bytes = DATA_payload[offset : offset + size]
```

注意 `offset` 相对于 **DATA 载荷起点**，不是整个 `.bnk` 文件开头。提取前校验 Chunk 边界、DIDX 长度是否为 12 的倍数，以及 `offset + size` 是否越界；遇到不同银行版本/布局不要强行按本例解读。

本次可用的初步分类：

- `RIFF` 开头：按 Wwise 媒体交给支持的解码器检查，常保存为 `.wem`。
- `01 e0 00 00` 开头：本次解析识别出的 Wwise MIDI 数据，记录为 `.wwise-midi`，不是通用 MIDI 格式承诺。
- 其他标记：保留为 `.bin` 并记录来源，不因不能试听而删除。

仅识别开头不足以证明文件正确，还应核对原索引长度、哈希及解析结果。

## 三、为什么不要用文本 Dump 改银行

> [!CAUTION]
> 不要把二进制银行当作普通 TextAsset 文本编辑后回写。只读十六进制检查没有问题，风险在于未经验证的修改与重打包。

文本解码/重新编码可能改变任意字节；变长替换也可能使 `DIDX` 的偏移、大小及 Chunk 长度与实际内容不一致。Unity 对象序列化与外层 Bundle 还需要正确保存。

错误后果可能是加载失败、缺声或崩溃，不必然每次都卡死；也不能简单归因为“CRC 一定错误”。正确处理方式是使用确实支持该版本/替换形式的工具，核对重建银行，再验证写回的 Unity 载荷。

`HIRC` 不只是一个偏移表，自动重导入媒体也不等于自动重写音乐时长和所有播放逻辑。修改路线与工具限制见[第 04 篇](04.QuickBMS与社区工具自动化替换.md)。
