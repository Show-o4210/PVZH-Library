# 07. 动态音频追踪与导出质量核对

静态分析回答“文件在哪里、如何编排”，动态观察回答“这个场景实际触发了什么”。本次使用临时 Frida 只读观察器，在随机 PvE 中追踪，不改参数、返回值、战斗策略或资源文件，也没有做 PvP 验证。

## 一、适合观察的调用与文件访问

可按游戏版本的 dump 定位 Wwise 封装，记录时间、事件/状态 ID、银行名称、文件路径及调用结果：

| 观察点 | 可以回答的问题 |
| --- | --- |
| `PostEvent` | 哪个事件被触发；需再沿银行引用找到媒体 |
| `SetState` / `SetSwitch` | 当前音乐状态/分支发生了什么变化 |
| `LoadBank` / `UnloadBank` | 哪个银行参与该场景，加载是否成功 |
| `SetRTPCValue` | 音量等实时参数改变，不一定意味着停止事件 |
| 文件打开/读取与结果 | 实际成功读取哪个媒体，哪些只是失败的搜索路径 |

地址与偏移必须按当前 dump 核对，不能跨版本复用。记录应有限时、有限量，避免高频日志影响游戏；结束后脱离观察器并停止本次启动的辅助进程。Hook 基础参见[第 15 章](../15.动态运行时初探/README.md)。

本次抓到 `SetState("Music_Game_Flow_State", "Music_Gameplay_Plant_Plan")` 及银行/媒体访问。其中部分同名 WEM 在 `DecodedBanks/`、应用 `files/` 路径尝试失败，随后从 `streaming_audio/` 成功读取，这是**搜索路径回退**，不是发现三份实际音频。

成功打开的文件也包含英雄、卡牌和 UI 声音，不能全部归为 BGM。一个已通过静态引用连接到音乐主事件、并在实机开局读取的例子是：

```text
PLAY_MUSIC (2932040671)
  → MusicSwitchContainer 990311620
    → MusicRanSeqContainer 735509063
      → MusicSegment 660387914
        → MusicTrack 610143122
          → streaming_audio/546029782.wem
```

该来源为双声道 16000 Hz Custom Vorbis，约 4.452 秒，是片段而非完整对局 BGM。

## 二、音乐音量为 0 是否让追踪失效

本次首次追踪时用户音乐为 0，后来改为 100 补测。dump 显示 `MixManager.SetMusicVolume` 设置 `MUSIC_VOLUME_RTPC` 并保存音量，没有在该方法中直接调用 StopEvent/UnloadBank。

所以音量为 0 时抓到的事件、状态和引用仍有价值；但底层虚拟化或缓存可能影响实际文件读取。补测确认了有声状态下的 WEM 读取，**并非严格同阶段、同缓存的 A/B 实验**，不能断言 0 与 100 的文件集合完全相同。需要靠实际可听场景补证时，记录音量设置再追踪即可。

## 三、名称不明时用证据关联，而不猜曲名

本次中英文资源未给出可靠的完整曲名表。可沿“命名事件 → 设置状态的动作 → 音乐条件 → 序列/片段/来源”建立用途关联：

| 命名事件线索 | 支持的用途关联，不是官方曲名 |
| --- | --- |
| `PLAY_UI_GAME_CHANGEPHASE_PLANTMAINPHASE` / `...ZOMBIEMAINPHASE` | 常规出牌阶段分支 |
| `PLAY_UI_GAME_CHANGEPHASE_COMBATPHASE` | 战斗结算分支 |
| `PLAY_UI_GAME_SUNCOUNTER_ENTER` | 阳光计数器入场所设置的状态，不能直接命名为换牌曲 |
| `META_ACTIVEHERO_DISCO` | 内部英雄状态关联，不证明有固定数量的“电舞主题曲” |
| `META_CURRENTNODE_FTUE_NODE_1` / `...SLIM` | 新手教学首关分支 |
| `PLAY_UI_GAME_LOSE` | 失败分支 |

未知状态只保留组 ID 和值 ID。比如 `614401776/778/779/780` 是未命名的变体条件，不能当作英雄 ID 或关卡号。静态关联也不保证实机每局按离线试听版完整演奏；动态日志中的旧状态组名称不能未经核对便等同于主音乐容器里的所有条件。

## 四、本次广覆盖导出结果

| 分类 | 可听文件数 | 含义 |
| --- | ---: | --- |
| 序列/切换编排 | 82 | 当前工具可支持的分支，优先试听 |
| 单片段编排 | 207 | 保留段内裁剪/混合 |
| 单轨/随机变体 | 368 | 补段或比较变体的素材 |
| 缺 MIDI 等声部的部分还原 | 1165 | 可能稀疏或有长静音，不是完整混音 |
| 合法随机候选修复补充 | 2 | 原候选的两个有效版本，保留原错误规则 |
| 原始 WEM 片段 | 260 | 各播放一次，不额外拼接或淡出 |

共 **1824 个编排/轨道文件 + 260 个原始片段**。1824 项中有 1000 种不同 PCM 内容，重复上下文仍保留；这些数字均不代表独立曲目数。原始片段播放总长约 27.5 分钟，有限循环编排总长约 12.7 小时。

另外 163 个规则只有 MIDI 或没有受支持音频来源、7 个渲染结果完全无声，不包装成无声 MP3；银行、规则与失败记录仍保留。初始成功的 1822 项加两个候选修复得到 1824 项。4471 个音乐 MIDI 来源保存于清单及银行，没有假装已合成完成。

这批导出未添加自编旋律、AI 生成声音、替代乐器、自动归一化或压限。第一批实例 A 得到了试听认可，**不意味着第二批所有变体都经过人工听感验收**。

## 五、最低质量核对与人工交接

检查文件信息与整段解码，而不只看工具返回了输出文件：

```powershell
ffprobe -v error -show_entries format=duration:stream=codec_name,sample_rate,channels -of json mp3/example_a.mp3
ffmpeg -hide_banner -v error -i mp3/example_a.mp3 -f null -
```

验收清单：

1. 比较源文件和研究副本 SHA-256；银行导出需保证字节完整。
2. 验证所有成品整段可解码，并检查采样率、声道、时长、全静音、异常满幅采样等。
3. 随机选择、循环位置、裁剪和叠轨应与规则核对；记录人工试听结果，不把机械解码当作听感验证。
4. 不擅自删除低音量、静音间隔或疑似削波；先保留原版，再另存可追溯的修复版。
5. 保留 PCM WAV，MP3 只作试听；编码或重采样并不会提高原始质量。
6. 内容去重比较 PCM 与格式参数，不仅比较可能带不同元数据的 WAV 文件哈希。规则/用途别名仍要保留。
7. 对交接 ZIP 做完整性检查，附目录清单、文件数与归档哈希；不只确认能打开压缩包。

本次全部交付 MP3 已整段解码，三个归档通过完整性检查，260 个 WEM 副本与原文件哈希一致。部分版本存在低音量、间隔或满幅采样，未强行“修音”，因此不声称整批完全无削波。

人工队建议先听“序列”，再听“片段”；轨道和原 WEM 用于补段，缺 MIDI 的版本单独标注。可按研究编号填写疑似场景/曲名与置信度，信息不确定时保留空白。应交付来源、规则、参数、别名与错误记录，不只交付一堆 MP3。

提取范围与授权范围不同。原始银行、官方媒体和衍生试听仍属于官方素材相关内容；本章的方法说明不授予将其用于同人游戏公开分发的权利，参见[许可与使用条款](../许可与使用条款.md)。
