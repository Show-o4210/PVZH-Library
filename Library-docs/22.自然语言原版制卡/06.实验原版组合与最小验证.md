# 实验原版组合、语义检索与最小验证

记录日期：2026-10-21。本页是后续Android R14产品的阶段性事实，公开Python v1工具、plan.schema.json、旧API与历史成绩保持原样。完整Android工程、游戏资产、APK及测试运行时不随Library提供。

当前已取得一张实际API生成实验卡的原引擎合法出牌结果：10费7/5植物单位，随机植物锦囊补满手牌，本次获得的牌准确设为0费。首个冷进程场景21项、空手边界17项、近满手边界21项通过；另完成24条实际API回归并独立复核，发现一次已实测的重复触发语义失败，RC5交回模型定向修订后11项通过，原失败保留。最终设备恢复23项通过。机器状态见[阶段摘要](实验组合验收摘要.json)，不能据此认为任意原版组合全部通过。

## 一、从固定配方到原版组件组合

玩家提出上述技能后，旧工作台将其拒绝：原conjure快捷表达只支持固定GUID一张，没有随机池、数量或生成结果改费参数。后续调查发现，原版已有相应节点；“工具没有快捷表达”与“原版引擎无法实现”并不相同。

R14保留keep/replace/append/copy_native等旧计划，新增`native.mode=compose`，允许已知原版组件形成实验提案。模型可以参考原版来源自行选择组合，不要求每一个组合都具有固定配方ID。未知类型/字段、错误参数、重复组件、无效引用或私有规则仍不能通过实验标签绕过校验。

示意表示：

```json
{
  "mode": "compose",
  "entities": [
    {
      "components": [
        {"type": "PlayTrigger"},
        {"type": "TriggerTargetFilter", "data": {"Query": {"type": "SelfQuery"}}},
        {"type": "PrimaryTargetFilter", "data": {"Query": {"type": "SelfQuery"}}},
        {"type": "BuffEffectDescriptor", "data": {"AttackAmount": 1, "HealthAmount": 1}}
      ]
    }
  ]
}
```

这是Android项目计划中卡牌native部分的结构示例，不是公开Python v1的新接口。完整类型和缺省字段从匹配原包模板克隆；查询用同样的type/data表示，普通数值对象、数组与null保持原样。默认目标、事件来源和辅助实体引用仍需按需求核对。

## 二、分别记录事实、结构与验证

| 状态 | 能说明的事实 |
| --- | --- |
| 原版有来源 | 类型、字段、枚举或已有组件组合有依据 |
| 工具可表达 | 当前编译器能构造相应数据 |
| 结构通过 | 参数形状、实际组件/查询角色、身份/引用、每实体类型唯一等有效 |
| 实验未测 | 可以提出并保存候选，尚未证明技能结算 |
| 指定场景通过 | 对应候选在该场景的实际状态变化符合预期 |
| 已采纳/已部署 | 用户审批和资源加载状态，与前面各层独立 |

JSON/ECS结构正确不能保证任意触发上下文或交互都正确；结构校验也不应只因缺少固定配方就拒绝已有原版组件的新组合。角色依据真实类型事实，不能只凭类名后缀猜。

原包曾观察的字符串不等于引擎完整枚举。例如SetStat的StatType实际为CardStat，共享1.67.8 ARM64 dump中包含SunCost；不能因模板只出现Attack/Health就误拒绝准确设费。版本、字段和枚举出处应一同登记。

原版节点组合与R12私有extension许可保持分离。原版费用修改和卡池筛选不需要借用新私有规则；攻击后扩展等仍按匹配运行/作者许可处理，不因本页开放所有私有编号。

## 三、资料检索与可复现经验

R14按“随机锦囊”“填满”“十张”“免费”“获得的牌”等效果含义检索原版参考，不要求玩家知道来源卡名或GUID。返回原版来源能力片段、相关节点模板/字段、语义提醒和裁剪状态。

反馈卡的主要依据：

- GUID180：按锦囊、阵营、排除超能力组合生成卡池。
- GUID449黄瓜队长、542时空博士：生成事件、DrawnCardQuery和生成牌改费；原样复制会观察其他来源生成的牌。
- GUID501虫洞守门人的第5实体：生成事件结合按来源排除自身的过滤。改为只匹配自身来源形成候选，后续必须实测。

检索最初只取来源的前三个实体，会遗漏501关键第5实体。调整后新增完整性断言，反馈需求上下文41548字符，来源为449/542/180/501，仍受总预算约束。来源出现在列表里，不代表关键实体已完整交给模型；裁剪应明确标记。

上下文把旧快捷能力注明`simple_plan_only=true`及`compose_available=true`，避免旧模式限制否定新组合。提示提供可参考的做法，模型仍只输出当前Mod三资源的待审数据提案，不执行代码、不操作账户。

经验案例宜保存需求、原版依据、简短设计说明、实际差异、独立预期、前后状态及失败修正；不依赖模型内部思维链，也不只保留最终成功JSON。模型没有收到真实测试报告时，不能声称已验证。

从实际S02失败补充了参考登记`r14-native-reference-2`：说明自己登场、其他卡事件和瞬时触发范围，提供TriggerTargetFilter(SelfQuery)等原版参考，并提示CardGuidQuery字段为Guid、植物监听僵尸不需要更换自身阵营。SelfEntityFilter/WillTriggerEffectsQuery应结合完整来源与实测判断，不因缺某一个组件就一律判错；仍保留自由组合。新版检索6组通过，反馈需求上下文42535字符；原RC4的24条回归继续作为旧资料基线，不被新资料结果覆盖。

## 四、真实API过程与失败

本次使用手机生产工作台和外部模型完成多轮生成，未以手写答案冒充模型回包：

1. 初次提案采用大量减费近似0费，没有完全满足准确设费要求，近似方案没有被当作完整需求通过。
2. 后续回复已经使用SetStat(SunCost=0)及自身来源过滤，但重复输出new_cards；流程还触发GUID历史扫描的大卡表内存问题，保留失败。
3. 修复扫描及候选上下文后，明确要求继续修改当前候选GUID；经一次编译反馈修正，得到实际compose计划，采纳到独立QA项目再进行原引擎测试。

待审候选中的新增卡已经存在，下一轮应通过cards修改同一GUID，不能再次new_cards。累计事实需要结构化进入上下文，不能只依赖旧聊天文字。编译错误与修复请求、最终产物仍应分别保存。

首答近似、格式/语义修正和失败不被抹去；统计模型表现时应区分手机正式聊天过程、单轮回归、校准与最终结果。

### 单轮24条回归与独立复核

RC4另做24次主机API请求，使用手机实际native_context，把模型提案交给手机native_plan编译。主测模型为deepseek-flash，每例一次、零自动修复，未采纳任何回归提案。这条回归路径不冒充手机正式聊天的完整UI/传输链。

| 结果 | 计数与解释 |
| --- | --- |
| 请求 | 24次，零自动重试 |
| 严格聊天外壳 | 23/24；一例澄清意图正确但漏plan:null |
| 提案 | 17份；18个期望提案需求中有一例不必要澄清 |
| 手机编译 | 16份ready；一例CardGuidQuery误用CardGuid字段被拒绝，实际应为Guid |
| 独立复核的回复意图/类别 | 22份格式有效且类别符合预期；不是22张技能正确 |
| 自动分类命中 | 原报告19/24，只是文字启发式，不是语义成功率 |

独立复核纠正了三条文字分类误判，以及植物GUID326上plant_hero/own_hero等价导致的自动探针误报。回复类别、结构编译、静态语义与原引擎结算分别计数，当前没有建立覆盖全部24条的技能语义成功率。

不必要澄清发生于“植物监听僵尸打出”：模型额外引入将植物变成僵尸的歧义。原版事件目标筛选可以观察敌方，不要求换自身阵营。实验需求也有生成数量、随机池和准确设费的可编译表达，但来源限定、当前手牌快照、期限和其他事件范围仍需逐个候选验证；反馈卡900011的通过不能代替本次新e01/e06候选的全部验收。

### 实际反例：结构通过但范围错误

S02原API提案通过编译，小豆丁合法打出对敌方英雄3伤也成立；随后合法打出无关GUID347，敌方英雄又受到3伤，9项检查中的`other-card-does-not-deal-again`失败，结果为SEMANTIC_FAIL。该提案没有自身出牌筛选且缺少参考来源中的瞬时触发guard，这是本例完整组合的实际问题，不扩写成“缺少某一个固定组件必然错误”。

S03登场抽2牌的原提案另测10项通过，随后无关GUID347打出没有再次抽牌。它提供正反例对照，不证明所有PlayTrigger组合都正确。

RC5将上述实测现象及`reference-2`资料交给模型，一次请求、零自动重试，模型修正版加入TriggerTargetFilter(SelfQuery)，手机编译为ready。随后独立冷进程原引擎测试11项通过：小豆丁合法出牌对敌方英雄造成3伤、己方英雄不变；再打出无关347没有再次造成伤害，同一进程继续存活。计划没有用手写答案替换，未采纳到用户Mod。安装交接期间另一次请求实际读到旧`reference-1`，其记录保留，但不算RC5资料验收。本次修正是新增证据，不改写RC4原始S02失败或24条基准成绩。

## 五、首个原引擎场景：21项通过

测试使用实际R14 RC4候选、独立冷进程和原游戏引擎无画面对局。缓存部署与候选身份相符，测试卡为新增GUID900011、10费7/5。通过真实合法出牌扣费并触发技能；give仅准备测试牌，未直接修改最终手牌结果。

场景沿用原版关卡001的手牌上限10，起始资源50、双方英雄100血、自然抽牌0；默认调试局的上限30不用于这项“补满10张”断言。生成动作发生前保留4张原手牌：

- 原手牌身份与费用保持。
- 实际入手6张，最终手牌为10。
- 新增6张均属于此次核对的34张原版植物锦囊候选集合，费用全部为0。
- 来源单位仍为7/5并留场，正常支付10点资源。
- 随后由原版GUID141生成GUID326，后者仍为1费，没有被实验单位改为0费。
- 之前生成牌的0费保持，其他单位打出不会再次填满手牌。
- 同一进程继续存活，当前PID没有崩溃记录。

此次用34张集合核对实际入手结果，不证明全部随机种子、每种候选或所有溢出触发均已穷举。“生成10张”的配置与“实际入手6张”的结果分别记录；没有将丢弃或未观察到的中间事件虚构为完整证据。

补充空手场景17项通过：生成前原手牌为0，实际获得10张，均为目标卡池且0费，最终手牌为10。近满手场景21项通过：生成前原手牌为9，实际入手1张且0费，最终仍为10，保留原手牌及其他来源生成等反例。三例实际加载卡表SHA相同；由于独立测试场景参数不同，其候选ZIP指纹分别登记，不能把不同前置条件视为同一完整包。

全例无触控模拟、无逻辑截图。无画面状态不能证明逐帧动画、special美术或完整自然玩家对局通过。连续温重开生命周期、其他机型、24例全部候选结算仍未穷举。近满手首次尝试在建fixture前，测试助手将正常`Runtime loading: player-cards`响应判为失败；修正就绪判定后恢复同一次冷启动，再完成合法出牌与21项检查。首次就绪误判仍保留，不记成技能失败，也不用后续PASS覆盖旧记录。

## 六、内存问题与GUID保护

第二次生产API流程在GUID迁移扫描历史Syndrome卡表时触发256MiB Java堆OOM，栈落在完整TextAsset UTF-8解码。只为提取GUID就建立整张卡表字符串和JSONObject，会放大大型历史资源的内存占用。

修正采用TextAsset字节区间视图及严格流式JSON身份扫描，只提取顶层GUID和卡体Card.$data.Guid；其他值仍完整校验语法、UTF-8与转义，但不建立完整对象树。按内容SHA缓存限定数量的GUID集合，不跳过当前、禁用、历史或草稿来源，不以捕获OOM/强制GC后继续预约代替修复。

36项本地检查通过，包含91,840,001字节合成JSON在64MiB堆内扫描10000个GUID，以及真实原版Bundle身份保真、视图零复制和非法边界拒绝。该大输入测试只覆盖JSON流扫描，不包含91MB UnityFS解包；不能据此承诺任意大Bundle都能在64MiB中编辑。

后续RC4已完成上述实际API生成、QA采纳和首个游戏场景，但仍不能由一次成功推出所有大Mod或资源编辑峰值均已验证。原设备OOM和修正后结果分别保留。
