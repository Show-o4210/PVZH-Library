# 03. 原生 Provider 调度与持久化写入实战

在卡牌数据经过合法性过滤后，最关键的一步来了：**如何把这套卡牌真正保存进玩家的游戏卡册中？**

在早期的 Mod 探索中，很多开发者习惯性地去打磁盘文件的注意（例如通过文件 IO 强行改写手机私有目录下的 `PlayerDecks` 缓存文件）。这种做法在 Unity 游戏中是灾难性的：

> ❌ **直接硬写文件的致命缺陷**：  
> Unity 游戏在运行期间，所有数据都在内存中保持着实时缓存。你在外部把文件改了，游戏根本不知道！当玩家进入卡册或退出游戏时，**游戏内存里的旧数据会直接覆盖写回磁盘，你刚刚替换的文件瞬间被抹去**；如果格式稍有不慎引发 UUID 冲突，还会导致游戏启动报空指针异常（NPE）直接卡死。

**最优雅、最稳定的做法，是“走正门”** —— 调用游戏原版负责卡组创建的官方底层服务：**`PlayerDeckProviderImpl`**！

本篇详细讲解如何挂载原生 Provider、如何在内存中分配 C# 数组，并完成全套持久化流程。

---

## 一、 官方底层接口（RVA 矩阵）

在 PVZH Android 1.67.8（versionCode 294）中，与卡组持久化相关的核心方法如下：

| 接口名称 | RVA 偏移 | 功能作用 |
| :--- | :---: | :--- |
| `PlayerDeckProviderImpl.CreateNewCustomDeck` | `0x01D1A9DC` | 创建合法卡组对象，分配官方 UUID 并初始化元数据 |
| `PlayerDeckProviderImpl.FindDeckById` | `0x01D1AEC4` | 根据 UUID 检索目标卡组对象指针 |
| `PlayerDeckProviderImpl.MarkDeckAsModified` | `0x01D1BF64` | 将目标卡组标记为 Dirty（脏数据），加入待持久化队列 |
| `PlayerDeckProviderImpl.PersistChanges` | `0x01D1B984` | 触发官方持久化链路，写入磁盘并通知原版 UI 刷新 |
| `DefaultDeckEditorDeckSaver.SaveOverDeck` | `0x01D341A4` | 将平铺的卡牌 ID 序列写入指定卡组模型 |

---

## 二、 构建平铺卡牌数组（Flattening Card Array）

官方的 `SaveOverDeck` 接收的不是二维的 `[[GUID, Count], ...]`，而是一个扁平化的卡牌整数集合（`IEnumerable<int>`）。

例如：`[火龙草 (608), 3张]` 需要展开为：`[608, 608, 608]`。

```javascript
// array_flattener.js

function flattenCardList(acceptedCards) {
    const flatArray = [];
    for (const [guid, count] of acceptedCards) {
        for (let i = 0; i < count; i++) {
            flatArray.push(guid);
        }
    }
    return flatArray; // 例如输出长度为 36 或 40 的连续整数数组
}
```

## 三、 实战：主线程安全写入全流程（Frida 驱动）

结合我们在第 17 章构建的 `UnityDispatcher`，完整的写入执行代码如下：

```javascript
// deck_importer_service.js

async function executeNativeImport(deckName, heroId, acceptedCards) {
    console.log(`[ImportPipeline] 准备在主线程导入卡组: "${deckName}" for Hero: ${heroId}`);

    // 1. 将所有 Native 操作完整投递至 UnityMain 主线程！
    return await UnityDispatcher.runOnUnityThread(() => {
        const il2cppBase = Module.findBaseAddress("libil2cpp.so");
        
        // 绑定 IL2CPP 函数指针
        const pCreateDeck = new NativeFunction(
            il2cppBase.add(ptr("0x01D1A9DC")),
            'pointer', ['pointer', 'pointer']
        );
        const pMarkModified = new NativeFunction(
            il2cppBase.add(ptr("0x01D1BF64")),
            'void', ['pointer', 'pointer']
        );
        const pPersist = new NativeFunction(
            il2cppBase.add(ptr("0x01D1B984")),
            'void', ['pointer']
        );
        const pSaveOverDeck = new NativeFunction(
            il2cppBase.add(ptr("0x01D341A4")),
            'void', ['pointer', 'pointer']
        );

        // 2. 获取在游戏初始化时捕获到的 Provider 单例实例指针
        const providerInstance = getCapturedProviderInstance();
        if (!providerInstance || providerInstance.isNull()) {
            throw new Error("游戏底层 PlayerDeckProvider 尚未初始化，请先进入一次卡册！");
        }

        // 3. 构建 C# 字符串参数 (Hero ID)
        const csHeroId = createIl2CppString(heroId);

        // 4. 调用官方 CreateNewCustomDeck：生成全新合法模型与 UUID
        const newDeckPtr = pCreateDeck(providerInstance, csHeroId);
        if (newDeckPtr.isNull()) {
            throw new Error("调用 CreateNewCustomDeck 失败，返回空指针");
        }

        // 读取由官方生成的全局唯一 UUID
        const deckUuidPtr = newDeckPtr.add(0x10).readPointer(); // +0x10 为 Id 字段
        const deckUuid = readIl2CppString(deckUuidPtr);
        console.log(`  -> 官方 UUID 分配成功: ${deckUuid}`);

        // 5. 设置自定义卡组名称
        if (deckName) {
            const csDeckName = createIl2CppString(deckName);
            newDeckPtr.add(0x18).writePointer(csDeckName); // +0x18 为 Name 字段
        }

        // 6. 将扁平化的 40 张卡牌写入模型
        const flatCards = flattenCardList(acceptedCards);
        const csCardEnumerable = createIl2CppIntList(flatCards);
        
        pSaveOverDeck(deckUuidPtr, csCardEnumerable);
        console.log(`  -> 已成功向卡组模型灌入 ${flatCards.length} 张合法卡牌`);

        // 7. 触发官方保存与脏标记
        pMarkModified(providerInstance, deckUuidPtr);
        pPersist(providerInstance);

        console.log("✅ 原生持久化指令已触发！游戏原版 UI 将在下一帧自动渲染新卡组！");
        return {
            success: true,
            uuid: deckUuid,
            importedCount: flatCards.length
        };
    });
}
```

## 四、 核心机制剖析：为什么这样做零封号风险？

1. **完全符合原版业务链路**：
   - 从 `CreateNewCustomDeck` 到 `SaveOverDeck`，我们**调用的每一个函数，都是游戏原版自带的官方方法**；
   - 游戏原版的单人卡册系统在收到这个指令时，与玩家手动在屏幕上点击“新建卡组”再一张张拖进去，在底层逻辑上看**完全一模一样**！
2. **免除 ID 碰撞与数据损坏**：
   - UUID 是由原版引擎的 `System.Guid.NewGuid()` 生成的标准格式，不会与旧卡组产生冲突；
   - 官方的 `PersistChanges()` 会按照游戏自身的序列化规则（CRC/哈希/加密）自动完成落盘，不需要我们手动去分析任何底层的私有存档格式。

至此，导入全流程已经完美闭环。而在一个完整的工具中，分享必须是“双向”的。下一篇，我们将学习如何从内存中提取玩家当前的卡组，生成便于社交分享的人性化中英文清单与 `PVZH1:` 代码！
