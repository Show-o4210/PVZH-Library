# 04. 复用引用与批量翻译工作流

批量改写 cn 的难点包括共享名、嵌套标记、重复句、名称别称及界面上下文。本页总结文言中文包中可复用的做法，不要求读者拥有原工程或其脚本。输入统计与交付边界见[05. 文言中文包实战与验收](05.文言中文包实战与验收.md)。

## 一、固定输入，建立译前目录

从同一 APK／底座取得 cn、`fonts/inline_text_tag`，以及需要交叉核对的 `cards/card_data`、`data_assets`。记录来源、SHA-256、TextAsset 名称与 path_id；不同来源的同名 `cn_8` 不能当作同一输入。

| 层次 | 应保存的内容 |
|---|---|
| 输入／原文 | 原 Bundle、精确提取的 CSV 字节和指纹，保持不变 |
| 记录目录 | 原始键、逻辑键、原值、CSV 记录序号与物理行区间、角色、受保护片段 |
| 引用目录 | 标签定义、`|key|` 引用、实际配置引用、名称候选、缺失与异常 |
| 翻译 | 分批任务、初稿、保留理由、主审修订、按键上下文例外 |
| 输出 | 新 CSV、新 Bundle、前后对照、校验报告、交付指纹 |

原键若含 BOM 或特殊前缀，可另建逻辑键便于查找，回写仍用原始字段。保留额外列、空值、空键填充及末尾分隔状态。**清理工作视图不等于清理游戏资源。**

依赖目录要区分证据：实际 `Tag → Text → |key|` 是序列化引用；`ability_desc_*` 的命名关联是推断；正文中同名子串只是同步候选。遍历嵌套关系时维护已访问集合，避免循环展开。标记基础见[03](03.富文本与图标标记语法.md)。

## 二、复用起草，不盲目合并语境

完全同文且角色相同的条目可形成一个翻译单元，保留全部原键。不同标点、空白、换行的近似内容只生成比较视图，不自动归一。

分类应结合真实配置和人工检查：`_name` 不只属于卡牌，本次首轮曾将排位段名与套牌系列名误分到卡名组，重分类后才交给 UI 组。令牌、旧卡名称与英文 `prefabName` 也要纳入，不能只找 GUID 外观的键。

相同原词也可分译。例如两个原值都是“战斗”：

| 键／用途 | 本案例译法 |
|---|---|
| `LANDING_ARENA_TEXT`，主页出战入口 | 出征 |
| `END_TURN_BUTTON`，回合末交战按钮 | 交锋 |

每日签到与每日挑战分开；“收藏”页名与“收藏若干张牌”的动作分开。关键操作允许保留清楚的说法：本例保留“确认、免费、回收”，将 SIGNOUT 的“注销”明确为“退出帐号”。

## 三、先定文风与术语，再批量翻译

先做覆盖规则、风味、UI、共享术语的一小批试译，让用户确认。本例采用浅近文言：规则对象、数值、时序、条件清楚，故事保留笑点，不用生僻词强行改尽每个字。

术语表至少记录“源词、新词、适用范围、保留情形”。例如牌包译“牌囊”，与法术“锦囊牌”区分；“环境→境域”仅用于游戏环境牌，不无界替换普通自然环境。

规则译文还须检查：

- **打出与进入场上**：不要把“打出”一律改成“出场”；召唤、变形等进入场上的方式未必相同。
- **目标与范围**：自身、本线、邻线、其余、所有、任意、随机不能省成模糊雅词。
- **时序与次数**：回合始／末、被灭、受伤、造成伤害，以及首次／每次／额外攻击分别保留。
- **相近词的机制差异**：职业 Madcap 的“疯狂”不等于 Frenzy“狂热”，不能按近义关系合并。
- **原文歧义**：对照同卡长文、同版目标筛选与效果配置；记下静态消歧依据，不靠想象改技能，也不把静态核对写成战斗实测。

可按共享术语、规则、叙述、UI 等拆批。若采用子 agent，应明确各自输出文件，起草后冻结结果再交叉审阅，由主审统一裁决并记录初稿、定稿和理由；不要让多个角色相互覆盖同一文件。

## 四、名称翻译应单独规划

正文改完而保留全部专名时，实际界面仍会很像原版。本例在实机反馈后才补译卡名、英雄、牌阵标题与栏目。因此完整计划应尽早明确这些范围，不把短词和专名一概视为无需翻译。

名称表需要检查：

1. 每个原键有决定，保留项有理由。保留物种、武器、身份；“角龙”等整体词不要为添“之”拆坏，“小鬼”也不凭空变成有年龄含义的“鬼童”。
2. 卡名、令牌和英雄新名之间没有新增重名。若原来就同名，应按实体标识分开处理，不能只以中文名为唯一 ID。
3. 同步共享链接、说明、`_heraldFighter`／`_heraldTrick`、任务、商店、关卡与对白中的直接引用。
4. 牌阵标题改名后，提示句中带引号的标题也同步，不能只有选择页更新。

### 一次最长匹配与上下文例外

禁止按名称列表逐个对全表 `replace`：短名可能破坏长名，新译名又会被下一轮替换。可采用以下流程，也可用匹配区间／结构化片段实现同样的约束：

```text
保护图标、参数、键引用、富文本与换行片段
  → 按实体和键上下文决定允许更名的引用
  → 同次最长匹配，长名及已生成目标名作为阻挡词
  → 对原始输入片段只替换一次
  → 应用已审定的按键别称或整句修订
  → 复查残留旧名、碰撞及全部排除项
```

| 本例歧义 | 处理 |
|---|---|
| 英雄“玫瑰”、卡牌“野玫瑰”、花刺谚语 | 英雄按键白名单；整张卡名优先匹配；普通花名双关保留 |
| “传送”卡、传送动词、传送门／传送机 | 仅确切卡名引用改名 |
| “窝瓜”卡与窝瓜族群 | 单卡按语境改名；`subtype_*` 和族群枚举不随单卡更名 |
| 测试关卡用植物种类或“巨尸”代指英雄 | 查配套英雄／关卡上下文后按键同步，不全局改普通卡名及部落名 |
| “巨人学家／巨尸学家”等旧别称 | 同版效果和上下文能确认时，加入逐键别称表 |

最长匹配只能防机械套改，不能代替语义审核。未知别称保留待查，不能因音近就认定同一张卡。

## 五、回写与验收分层

先跑空补丁回写，确认逐字节不变，再应用译文。仅重写目标 CSV 记录，其他记录复制原始片段；用 CSV 写入器处理目标字段的引号，不删除或重新排序原键。

| 层次 | 必查内容 | 能证明什么 |
|---|---|---|
| 覆盖 | 每个单元恰好一次；源文匹配；键数量／顺序、额外列、空值保留；修改键存在且唯一 | 没有漏写、串版本或结构性丢项 |
| 保护字段 | 完整标记、引用、各类占位；数值、正负号、百分号；富文本顺序；每种字面及物理换行；方括号等分隔符数量 | 本轮没有误改这些结构；集合比较仍需配合顺序、位置与语义审阅 |
| 语义与引用 | 对象、条件、时序、否定、次数；新名碰撞；旧名残留、排除项和共享键存在性 | 经过人工审核，不能单靠数字相同断言语义等价 |
| Bundle | 只改目标 `m_Script`；另存新包并加载；读回内容与目标 CSV 相等；按序列化文件名＋path_id 比较对象原始字节 | 目标 TextAsset 正确，其余对象未变；不要求压缩包整体字节相同 |
| 部署 | 实际资源来源、目标哈希、重启后抽查 | 文件放在正确位置且被使用 |
| 显示 | 共享关键词、卡册、英雄、主页、商店、长名称／说明；新增汉字、截断与换行 | 已抽查界面可读，不代表穷尽每条文字 |

例如 `[+1a]` 改成 `[-1a]`，只比较数字会漏检。未知原标记、重复映射和既有缺键另列为原有异常，不算成本轮新增，也不为了报告“全绿”而删掉。

交付时区分 CSV 与 Bundle：前者用于审阅，后者用于资源替换。每版保留独立目录、差异表、保留理由、主审记录和指纹，避免覆盖已试用版本。图标改绘属于独立美术流程，不计作 cn 翻译或字体通过证据。

## 六、屏幕仍有原文时如何定位

先搜索当前 cn 的值，再查实际键、共享映射、动态参数与实际加载的包。还要检查同一中文词是否在另一语境中有不同键，而非重复修改已更新的值。

若字面文本不在 cn 内，不能承诺仅靠 cn 修复。本例画面有 `RANK: NA`、`Round 4`，但 cn 已有“名次：无”，倒计时模板含 `[roundtext]`。这只能确认当前 cn 文本不能完整解释实际显示；究竟来自其他资源、运行时逻辑或外部配置，仍需另查。保留未知标记和参数，不用猜出的键或硬编码文字掩盖问题。
