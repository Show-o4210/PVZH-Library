# 02. IL2CPP 符号表 dump 与内存查表实战

在传统的 Mono 引擎 Unity 游戏中，反编译 `Assembly-CSharp.dll` 就能直接看懂所有的 C# 代码和变量名。然而，现代 Unity 游戏普遍采用了 **IL2CPP（IL to C++）** 编译技术：所有的 C# 代码都被预先编译成了 C++，再编译成原生动态链接库 `libil2cpp.so`。

这意味着在二进制世界里，所有高层的面向对象语法、类名与函数名在运行时都被抹去了，只剩下一串串机器码地址。

本篇讲解如何使用开源工具 **Il2CppDumper** 还原符号表，并在生成的 `dump.cs` 中快速定位目标业务逻辑的 **RVA（相对虚拟地址）**，掌握在 Frida 中计算运行时内存绝对地址的核心方法。

---

## 一、 IL2CPP 的“剥离”与“还原”原理

要理解符号表查询，首先要了解 Unity 是如何存放元数据的：

```mermaid
graph LR
    subgraph 编译打包 (Unity Build)
        A["C# 源码<br/>(Class / Method / Field)"] --> B["C++ 机器码<br/>libil2cpp.so"]
        A --> C["字符串与反射元数据<br/>global-metadata.dat"]
    end
    subgraph 逆向还原 (Il2CppDumper)
        B & C --> D["Il2CppDumper 解析器"]
        D --> E["还原工程符号<br/>dump.cs / script.json"]
    end
```

- **`libil2cpp.so`**：存放所有的原生汇编执行代码；
- **`global-metadata.dat`**：存放类名、方法名、字段名及常量字符串等元数据（位于 APK 的 `assets/bin/Data/Managed/Metadata/` 目录下）；
- **`Il2CppDumper`**：通过比对这两者的索引结构，将二进制偏移与人类可读的 C# 语法重新缝合，输出一份伪代码符号表 `dump.cs`。

---

## 二、 读懂 `dump.cs` 的符号结构

用文本编辑器（如 VS Code）打开提取出的 `dump.cs`，搜索我们感兴趣的业务类。

以 PVZH 客户端中负责卡组管理的真实类 `PlayerDeckProviderImpl` 为例，其在 `dump.cs` 中的声明结构如下：

```csharp
// Namespace: 
public class PlayerDeckProviderImpl : IPlayerDeckProvider // TypeDefIndex: 4321
{
    // Fields (字段定义与偏移)
    private Dictionary<string, Deck> m_decks; // 0x18
    private bool m_isDirty;                   // 0x20

    // Methods (方法定义与 RVA 偏移)
    // RVA: 0x01D1A9DC Offset: 0x01D1A9DC VA: 0x01D1A9DC
    public Deck CreateNewCustomDeck(string heroId) { }

    // RVA: 0x01D1AEC4 Offset: 0x01D1AEC4 VA: 0x01D1AEC4
    public Deck FindDeckById(string deckId) { }

    // RVA: 0x01D1B984 Offset: 0x01D1B984 VA: 0x01D1B984
    public void PersistChanges() { }
}
```

### 关键元数据解析：
1. **`RVA: 0x01D1A9DC`**：
   - 即 **Relative Virtual Address（相对虚拟地址）**；
   - 它表示该函数的机器码起始点，距离 `libil2cpp.so` 模块加载基地址的**相对偏移量**；
   - 只要游戏版本不变，这个相对偏移就是固定不变的。
2. **`Fields 偏移 (如 0x18, 0x20)`**：
   - 表示该类实例化后，对象指针（`this`）内部各属性在内存中的偏移位置，用于通过指针直接读取内部私有变量。

## 三、 ASLR 机制与内存基址计算公式

在现代 Android 系统中，为了防止缓冲区溢出攻击，启用了 **ASLR（地址空间布局随机化）**。游戏每次启动时，`libil2cpp.so` 在内存中的起始地址都是**随机分配**的：

```text
第一次启动: libil2cpp.so 基地址 = 0x7688200000
第二次启动: libil2cpp.so 基地址 = 0x72a4100000
```

因此，**千万不要在脚本中写死内存绝对地址**。我们必须通过 Frida 提供的运行时 API 动态计算出目标函数在内存中的实时绝对位置：

$$\text{函数实际物理内存地址 (Absolute Address)} = \text{libil2cpp.so 加载基址 (Base Address)} + \text{函数相对偏移 (RVA)}$$

## 四、 实战：在 Frida 中计算目标函数指针

以下是一份标准、健壮的 IL2CPP 符号地址解析脚本模板：

```javascript
// target_resolver.js

function getIL2CPPMethod(rvaOffsetHex, methodName) {
    // 1. 获取当前进程中 libil2cpp.so 的内存基地址
    const il2cppBase = Module.findBaseAddress("libil2cpp.so");
    
    if (!il2cppBase) {
        console.error("❌ 未能在当前进程找到 libil2cpp.so 模块，请确认游戏是否为 ARM64 原生运行状态！");
        return null;
    }

    // 2. 基地址与 RVA 进行 64 位指针相加
    const targetAddress = il2cppBase.add(ptr(rvaOffsetHex));
    
    console.log(`[Symbol Resolver] ${methodName} -> 基址: ${il2cppBase} + 偏移: ${rvaOffsetHex} = 目标地址: ${targetAddress}`);
    return targetAddress;
}

// 示例：解析 1.67.8 版本中创建新卡组的函数
const RVA_CREATE_DECK = "0x01D1A9DC";
const pCreateNewCustomDeck = getIL2CPPMethod(RVA_CREATE_DECK, "PlayerDeckProviderImpl.CreateNewCustomDeck");
```

运行输出示例：

```text
[Symbol Resolver] PlayerDeckProviderImpl.CreateNewCustomDeck -> 基址: 0x72a4100000 + 偏移: 0x01D1A9DC = 目标地址: 0x72a5e1a9dc
```

## 五、 版本对齐与工程规范

> [!WARNING]
> ⚠️ **严禁混用不同游戏版本的 RVA 偏移**：
> RVA 地址是与编译生成的二进制强绑定的。即便是官方一个仅有几兆字节的细微版本更新（例如从 1.67.7 更新至 1.67.8），编译器都会导致二进制函数发生重排，RVA 偏移会整体错位。

### 推荐的工程化管理规范：
在编写通用 Mod 脚本时，建议将版本号与 RVA 偏移拆分为独立的配置文件或常量字典：

```javascript
// version_offsets.js
const PVZH_OFFSETS = {
    "1.67.8": {
        versionCode: 294,
        PlayerDeckProvider_CreateNewCustomDeck: "0x1D1A9DC",
        PlayerDeckProvider_FindDeckById: "0x1D1AEC4",
        DefaultDeckEditorDeckSaver_SaveOverDeck: "0x1D341A4",
    },
    // 未来适配新版本时，只需在下方追加新 dump 的 RVA
};

// 根据当前运行时的版本号动态选择偏移表
```
