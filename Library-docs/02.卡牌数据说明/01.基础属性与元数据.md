# 01. 基础属性与元数据

在 PVZH 的卡牌 JSON 数据集中（如 `card_data_5`），每张卡牌都以一个顶层 GUID 为键的 JSON 对象存在。外层包含了一系列元数据字段，主要用于 UI 界面渲染、卡牌收藏库展示、卡组构筑合法性校验及合成分解机制。

---

## 一、 卡牌数据外层 JSON 结构简图

以下为省略组件的结构示意，使用带注释的JSONC，不能直接导入；prefabName占位符也必须替换为有匹配文本和资源寻址的实际标识。完整关系见[第23章](../23.卡牌身份与资源映射/README.md)。

```jsonc
{
  "900000001": {
    "entity": {
      "components": [ /* 内层底层 C# 组件数组 */ ]
    },
    "prefabName": "900000001-prefab-uuid",
    "baseId": "BasePlantFighter",
    "color": "Guardian",
    "set": "Gold",
    "rarity": 3,
    "setAndRarityKey": "Bloom_Legendary",
    "displayHealth": 3,
    "displayAttack": 2,
    "displaySunCost": 2,
    "faction": "Plants",
    "ignoreDeckLimit": false,
    "isPower": false,
    "isPrimaryPower": false,
    "isFighter": true,
    "isEnv": false,
    "isAquatic": false,
    "isTeamup": false,
    "subtypes": ["Pea", "Flower"],
    "tags": ["Pea", "Flower"],
    "subtype_affinities": [],
    "subtype_affinity_weights": [],
    "tag_affinities": [],
    "tag_affinity_weights": [],
    "card_affinities": [],
    "card_affinity_weights": [],
    "usable": true,
    "special_abilities": ["Armor", "Strikethrough"]
  }
}
```

## 二、 基础标识与元数据字段

| 字段名 | 数据类型 | 说明与合法值 | 修改注意事项 |
| :--- | :--- | :--- | :--- |
| **GUID (字典键)** | JSON键为字符串，内层Guid为整数 | 当前有效卡表中的定义编号（如 `900000001`）。 | 必须与当前原包Card组件的Guid一致，不可在同表重复；不是全社区注册号。 |
| **prefabName** | `string` | 文本和资源路径使用的标识，可为UUID外观或英文名。 | 同时参与中文Key及Prefab/手牌/图鉴路径生成，不是数字GUID的别名。 |
| **baseId** | `string` | 卡牌基类模板（如 `BasePlantFighter`、`BaseZombieFighter`、`BaseTrick`、`BaseEnvironment`、`BasePlantOneTimeEffect` 等）。 | 决定卡牌的基础分类范式，影响游戏加载时的实体挂载逻辑。 |
| **faction** | `string` | 归属阵营。合法值：`Plants`（植物）、`Zombies`（僵尸）、`All`（通用/系统）。 | 必须与职业及卡组构筑逻辑匹配。 |
| **usable** | `bool` | 原包的可用性元数据。 | 不能仅凭此字段证明新卡已完成收藏/组牌登记，或全部抽取/生成路径都受阻；按具体流程核对。 |

> [!NOTE]
> **创建全新卡牌的核心法则**：
> 1. **内外GUID一致且同表不重复**：解析、克隆完整原包定义，再正确写回cards TextAsset；不是随意往文件末尾追加文本。
> 2. **共享prefabName通常也共享文字**：可作为另一卡牌定义借用原版资源，但不能靠数字GUID自动分离中文。独立文本、美术寻址与收藏登记分别处理，见[新卡指南](05.手动修改最佳实践与新建卡牌指南.md)。

## 三、 职业 (Class / Color) 映射关系表

原版清单 11065 中，`color` 是顶层属性字符串。`"0"` 表示无属性，双属性以逗号和空格连接，例如 `"MegaGro, Smarty"`。这与独立的阵营字段 `faction` 配合使用。650 条原版定义中的双属性样本均为同阵营。

| 阵营 | 官方中文名称与 `color` 的原生枚举 |
| :--- | :--- |
| 植物 | 爆花 `Kabloom`、猛长 `MegaGro`、守卫 `Guardian`、聪明 `Smarty`、光能 `Solar` |
| 僵尸 | 有脑 `Brainy`、健壮 `Hearty`、狡猾 `Sneaky`、猛兽 `Hungry`、疯狂 `Madcap` |

## 四、 稀有度与卡库属性 (Rarity & Set)

原版清单 11065 的 650 条卡牌定义均包含一个根级 `PvZCards.Engine.Components.Rarity`。修改稀有度时，外层整数与组件 `$data.Value` 同步写入。

| 稀有度 | 外层 `rarity` | 组件 `Value` | 原版标签示例 |
| :--- | :---: | :---: | :--- |
| 罕见 | `0` | `R1` | `Bloom_Common` |
| 稀有 | `1` | `R2` | `Bloom_Rare` |
| 超稀有 | `2` | `R3` | `Bloom_SuperRare` |
| 传说 | `3` | `R4` | `Bloom_Legendary` |
| 基础卡（常见） | `4` | `R0` | `Dawn_Common`、`Token` |
| 活动卡 | `5` | `Event` | `Premium_Event` |

`setAndRarityKey` 关联本地化资源的 `LocalizedStrings` 键。例如中文 `Bloom_Legendary` 显示「高级 - 传说」，`Galaxy_Legendary` 显示「银河 - 传说」。留空使用对应稀有度的通用文字。自定义标签可在 Mod 的 `loc/cn` 增加独立键。`set`、`craftingBuy` 和 `craftingSell` 是独立字段，同一稀有度的卡可以使用不同卡集或合成分解价格。

## 五、 显示攻防与类别标志位 (Display Stats & Flags)

### 1. 显示数值 (Display Stats)

> [!IMPORTANT]
> 外层 JSON 中的 `displayAttack`、`displayHealth` 和 `displaySunCost` **仅供 UI 渲染与收藏卡册显示**！
> 真正影响战场实际战斗与费用的数值，在内层 `entity.components`（如 `AttackComponent`、`HealthComponent`、`SunCostComponent`）中生效。改动数值时必须**内外层同步修改**。

- `displaySunCost`: 手牌界面上显示的费用值。
- `displayAttack`: 手牌界面上显示的攻击力。
- `displayHealth`: 手牌界面上显示的生命值（法术卡或场景卡通常为 0）。

### 2. 卡牌机制标志位 (Flags)

| 标志位字段 | 类型 | 说明 |
| :--- | :---: | :--- |
| `isFighter` | `bool` | 是否为随从/单位卡（随从植物或随从僵尸）。 |
| `isEnv` | `bool` | 是否为环境/场景卡（Environment）。 |
| `isAquatic` | `bool` | 是否具有水生能力（挂在水路）。 |
| `isTeamup` | `bool` | 是否具有团队协作能力（同格子可叠放两张植物）。 |
| `isPower` | `bool` | 是否为超能力卡（Superpower）。 |
| `isPrimaryPower` | `bool` | 是否为主超能力卡。 |
| `ignoreDeckLimit` | `bool` | 是否忽略默认的 4 张编组上限（例如：海军豆、炒豆子）。 |

## 六、 族群 (Subtypes) 与 标签 (Tags)

卡牌的族群与标签分为两套系统：

1. **Subtypes (逻辑族群)**：
   用于**游戏引擎战斗逻辑判定**（例如："当一个**豆类**植物登场时..."、"所有**坚果**获得+1/+1"）。
   - 示例：`["Pea", "Flower"]`、`["Nut"]`、`["Imp", "Moustache"]`。
2. **Tags (展示/UI 标签)**：
   用于**UI 属性文字提示与搜索过滤**。
   - 示例：`["Pea", "Flower"]`。

> [!NOTE]
> 通常情况下，`subtypes` 与 `tags` 的内容是一致的，但在某些自定义 Mod 中，开发者可将逻辑判定与文本展示解耦。

## 七、 协同关联 (Affinities) 与 特殊能力标签 (special_abilities)

### 1. 协同关联 (Affinities)

某些卡牌与特定卡牌、族群或标签存在 AI / 推荐出牌关联系数：
- `subtype_affinities` / `subtype_affinity_weights`: 关联族群及其协同权重。
- `tag_affinities` / `tag_affinity_weights`: 关联标签及其协同权重。
- `card_affinities` / `card_affinity_weights`: 关联特定卡牌 GUID 及其权重。

### 2. 特殊能力标签 (special_abilities)

`special_abilities` 数组包含了卡牌在 UI 上需要高亮显示的关键字词标。常见值包括：
- `Armor`（护甲）
- `Strikethrough`（贯穿）
- `Deadly`（致命）
- `Frenzy`（狂暴）
- `Untrickable`（免疫法术）
- `Truestrike`（无视盾牌/精准）
- `Repeater`（双重攻击）
- `Overshoot`（先发制人）

> [!TIP]
> 推荐在添加独立能力组件时，同步在 `special_abilities` 中补充对应的标签名，以保证卡牌手牌面板图标和文字提示正确渲染。
