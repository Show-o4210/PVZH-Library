# 05. 手动修改最佳实践与新建卡牌指南

2026-10-19修订：区分卡牌身份、文本前缀和资源寻址，纠正旧版“全网唯一GUID”“共享prefabName仍可按数字GUID补独立中文”的说法。资源完整关系见[第23章](../23.卡牌身份与资源映射/README.md)。

## 1. 复制当前原包结构，再做精确修改

从用户当前原包找到完整实例，复制类型串、字段层级和枚举，仅改变需求涉及的部分。不要凭GUI名称给所有组件追加Component后缀；当前原包实际使用Card、SunCost、Attack、Health等类型。

复制原版模板能减少结构错误，但不是语义和游戏行为的保证。仍应检查内外显示与实际属性、嵌套实体类型唯一性、原版技能的来源/目标及卡牌引用。技能树见[03](03.技能逻辑树与EffectEntities.md)，自包含基本流程见[Agent08](../08-basic-mod-walkthrough.md)。

## 2. 改原卡与新增定义分别处理

改原卡时通常保留字典GUID、Card.Guid和prefabName，修改对应组件及显示值，并同步原prefabName下的中文说明。只改display字段或描述不代表实际技能改变。

新增卡时从只读原版底稿克隆完整定义，再同步外层字典键和内层Card.Guid。不能只在JSON文件末尾随意追加文本：应解析整个字典，检测重复和字段一致性，再正确写回Bundle内的cards TextAsset。

GUID需要在同一有效卡表中唯一，不存在本章已验证的“全网唯一”注册规则。较大数字可以降低撞号概率，但不能保证独立Mod兼容；R9从900001起分配是项目约定，不是社区保留号段。卡组、库存与收藏系统是否接受新GUID还需另行处理。

## 3. 共享美术不等于共享文字可以自动分开

当前原版小豆丁是数字GUID326、prefabName为Weenie_Beanie。中文名通常从Weenie_Beanie_name读取。若新增900001仍复用这个prefabName，普通文本也会共享此前缀；添加900001_name不会自动让游戏改用它。

| 需要的效果 | 做法与边界 |
|---|---|
| 新GUID，但允许原名与原美术 | 可以从原版克隆并共享prefabName；分别核对实际属性/技能，不能称为独立中文或收藏登记完成 |
| 新GUID，独立名称/说明，共享原美术 | 独立prefabName和中文Key，同时提供匹配的资源寻址；R9用加载适配把美术路径复用到原版 |
| 新GUID，独立美术 | 还需包内资产、Manifest映射与依赖等工作，本次未完成 |

只改prefabName会改变Prefab、手牌图、图鉴等资源请求，不能只添加文字就结束。R9的资源别名是额外加载能力，未适配的原版APK和公开制卡工具v1没有自动获得该功能。

## 4. 新身份的局部示意

下面只演示两个身份字段，**不是完整卡牌对象，不能直接导入**。完整定义必须从当前原包克隆；当前实际身份组件使用Card而非CardComponent。

```json
{
  "900001": {
    "entity": {
      "components": [{
        "$type": "PvZCards.Engine.Components.Card, EngineLib, Version=1.0.0.0, Culture=neutral, PublicKeyToken=null",
        "$data": {"Guid": 900001}
      }]
    },
    "prefabName": "Weenie_Beanie"
  }
}
```

该片段选择共享原prefabName，因此普通文本仍会读取Weenie_Beanie前缀。独立文本方案、R9元数据与适配依赖见[第23章03](../23.卡牌身份与资源映射/03.新增GUID与资源复用流程.md)，不要把该约定当成原版字段。

## 5. 最小验收

核对GUID一致、显示与组件值一致、中文键绑定、资源路径、Bundle非目标对象及回读。进入游戏后分别检查卡牌定义、实际文字、合法抽取/打出、技能结算与画面；再做原版退出隔离。

新增定义已加载或能调试召唤，不证明收藏、组牌和库存持久化已完成。原版能力完整复制也可能保留特定来源卡的引用，不要机械替换所有整数或据少量样例宣称全部组合可用。
