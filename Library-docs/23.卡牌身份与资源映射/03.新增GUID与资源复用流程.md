# 03. 新增GUID与资源复用流程

## 1. 按目标选择修改层

| 目标 | 卡表 | 本地化 | 资源加载 |
|---|---|---|---|
| 改现有卡，保留美术 | 修改对应GUID的属性/技能 | 按原prefabName更新文字 | 通常沿用原资源，无需新别名 |
| 新GUID，共享原名和美术 | 克隆定义、修改字典GUID和Card.Guid | 共享prefabName通常也共享文字 | 可沿用原路径；不等于独立收藏已登记 |
| 新GUID，独立文字，共享美术 | 克隆定义、分配独立prefabName | 建立独立前缀的Key | 必须有匹配的资源寻址；R9使用窄范围别名适配 |
| 新GUID，新美术 | 定义与身份都需处理 | 独立文字 | 新包、包内资产、路径映射及依赖另做，本轮未完成 |

“只加数字GUID”与“独立文字+完整资源寻址”是不同交付范围。直接修改现有prefabName也会改变资源请求；只补中文而没有资源路径可能出现文字正确、美术缺失。

## 2. 克隆原版底稿，避免复制当前改版结果

R9把只读原版底稿与当前Mod区分。`template_guid`始终选择原版模板；若当前项目已经把原版326改成带打出伤害的新技能，随后以原版326为模板创建无技能新卡，模板应仍来自原版，不能误复制已改的326。

克隆时同步：

1. 外层字典键、内层Card.Guid和新增身份元数据。
2. 外层显示费用/攻防与实际对应组件值。
3. 独立prefabName及其名称、短说明、长说明、简介、目标与出牌提示等所需中文Key。
4. 明确的原版资源模板，不能由模型任意给一个资源路径。

其余字段及能力中的字面GUID引用原样保留，除非本次需求明确要求修改并已理解其语义。锦囊/环境不应被补上单位攻防或关键词；原版完整能力复制仍要核对阵营、类型与隐含引用。

## 3. R9身份和别名合同

下面是**R9产品约定**，不是原版必需字段，也不是第22章公开Python工具v1的输入合同。

- 自动GUID从900001起找项目内未占用编号；允许显式指定合规正整数。900001不是全社区永久预留段，不保证两个独立Mod不会使用相同GUID。
- 同一有效卡表中的新GUID不能撞原版或已有定义。多Mod仍是整表优先，不能把数字选得大当作兼容策略。
- 新prefabName为`pvzhmod_<项目ID的SHA256前12位>_<GUID>`，用于项目内的独立文本/资源身份；这是命名约定，不是原版资源UUID生成算法。
- 本版元数据校验要求模板存在于原版、资源标识等于模板prefabName、内外GUID一致、别名格式一致；每个项目最多1000个资源别名，单次计划最多40项改动。

新卡的局部结构示意，不含完整原版组件：

```json
{
  "900001": {
    "prefabName": "pvzhmod_d9fdfcfb2b6a_900001",
    "_pvzh": {
      "schema": 1,
      "guid": 900001,
      "template_guid": 326,
      "resource_prefab": "Weenie_Beanie"
    }
  }
}
```

`_pvzh`由R9启动器读取；原版CardData对已知字段的加载在本次样例中正常。不能推广成引擎支持任意额外字段或新原生类型。

文本读取继续用新标识，例如`pvzhmod_d9fdfcfb2b6a_900001_name`。只有美术资源寻址时，匹配到这个别名才改成`Weenie_Beanie`，然后让原版查表。原卡请求不改，全局中文前缀也不替换。

R9适配范围是Prefab、InHand、InCollection及已有Android/iOS音频路径族；限制目录、别名格式和原版资源标识，三个寻址入口一致处理。**音频路径族有实现，但本轮没有独立音频播放验收，也没有音频扩展。**

## 4. Bundle写回与启动事务

卡表和CSV都是Bundle内TextAsset的内容，不是可以直接拿UTF-8文本覆盖的外部JSON/CSV文件。文本长度改变后，需要正确重建相关序列化对象及Bundle数据。R9沿用R8手机端Java `NativeBundle`和lz4-java写回，手机端不依赖UnityPy；离线核对用UnityPy独立解包比较。

本次R9新增验证集中于新卡身份、文本与实际结算；通用Bundle增减长度、非目标对象及无操作字节保留的基础验收属于此前R8，不能把它说成本次重新完成的全部测试。

文件职责如下：

| 内容 | 位置/作用 |
|---|---|
| 卡牌定义与R9身份元数据 | 修改后的`cards/card_data`资源族 |
| 中文名称与各类说明 | 修改后的`loc/cn`资源族 |
| 关卡数据 | `data_assets`资源族；本次卡牌请求未生成或修改它 |
| ZIP项目清单 | `mod.json`声明文件来源、逻辑资源族、版本和运行时依赖`card-assets-v1` |
| 本次实际加载状态 | R9事务提交的`loaded.json`，记录胜出文件及`card_asset_bindings` |
| 官方资源路径清单 | AssetPathsManifest及bin，本轮保持不变 |

启动器从**最终胜出的card_data**解析别名，与文件部署、loaded状态一起提交；失败沿原事务回滚。不要把所有勾选Mod的别名直接合并，也不要另留一份脱离实际卡表的映射文件。

## 5. 多Mod优先级与AI累计编辑分开

AI在一个目标项目中按GUID局部编辑，输出该项目的新累计版本；其他卡、中文和关卡保持。保存版本与当前游戏加载版本分开记录，完整退出应用再从启动器进入才加载新内容，没有热更新承诺。

多Mod组合仍按**逻辑资源族完整文件覆盖，排序靠前优先**：

- Mod A和B都修改card_data，A靠前则读取A整份卡表；B的新GUID不会自动补进来。
- 中文资源独立选胜出文件。如果只覆盖卡表却从另一Mod取中文，可能缺Key或说明错配；应提示，而不是宣称自动兼容。
- 只有A卡表里的资源别名生效；把B排到前面后，别名也应随胜出的B卡表重新计算。
- 冲突作为提示保留，不因组合政策禁止进入；损坏文件、越界路径、无法部署等技术错误不能伪称已应用。

本次实际检查了AI项目与Mod2交换优先级：AI在前有3个别名，Mod2在前别名清空，两种顺序均提示覆盖且可应用。没有把两份内容合并成新Mod2。

## 6. AI合同与语义审核

R9区分`cards`编辑已存在GUID、`new_cards`创建新身份。API输出需求计划，编译器负责身份、原版组件、文字与Bundle；不允许模型手写prefab路径、执行Hook或新增原生类型。

示意请求计划，**不能直接送入公开v1的plan.schema.json当作已支持**：

```json
{
  "schema_version": 1,
  "status": "ready",
  "new_cards": [{
    "template_guid": 326,
    "name": "成长豆",
    "stats": {"cost": 3, "attack": 7, "health": 8},
    "native": {
      "mode": "replace",
      "abilities": [{
        "trigger": "turn_start",
        "target": "self",
        "effects": [{"type": "buff", "attack": 1, "health": 1}]
      }]
    },
    "text": {"flavor_text": "同一美术，独立成长。"}
  }]
}
```

技能由native生成，说明同步生成；用户明确要求的自定义文字最后应用。自定义文字仍可能与实际技能不一致，需要预览审核。真实API曾遗漏简介、把“简介”写进技能短说明；JSON合法和编译通过都没发现这一语义问题。补明确字段解释后，第三次真实请求修正，并用中文Key差异与游戏检视文本核对，未改写模型答案冒充原始成功。

## 7. 新卡交付所需的适配声明

新卡ZIP依赖`card-assets-v1`，适配器必须与当前游戏原版方法相容。卡表技能可以使用原版组件，但这种独立prefab文本身份的美术复用不等于未修改的原版APK也能直接识别。

把该ZIP放进未适配的原版或旧R8不能保证显示。真正的新美术、收藏/组牌登记、全部复杂技能组合、运行中重载定义，均需另外开发和验证。
