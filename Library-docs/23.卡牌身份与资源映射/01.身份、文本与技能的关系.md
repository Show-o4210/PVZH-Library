# 01. 身份、文本与技能的关系

## 1. 六类标识不要混用

| 标识 | 当前案例 | 作用及约束 |
|---|---|---|
| 卡表字典键 | `"326"`、`"900001"` | JSON字典中的卡牌定义编号；新增卡在同一有效卡表中不能重复 |
| 实体组件 `Card.Guid` | 数字 `326`、`900001` | 卡牌定义的引擎身份，应与外层字典键一致；从当前原包取得完整类型串 |
| `prefabName` | `Weenie_Beanie`、UUID外观字符串、R9独立别名 | 参与文本前缀和资源路径生成；不是数字GUID的另一种写法 |
| 本地化Key | `Weenie_Beanie_name` | CSV精确键；后缀和大小写需核对实际引用 |
| 运行中实体ID | 调试状态中的某个手牌/场上实体ID | 一次对局中的实例身份；同一种卡可以有多个实体，不能拿它当卡牌GUID |
| Bundle名与包内对象标识 | `autotagged/...`、资产路径、Unity对象path_id | 文件定位和包内引用；Unity对象path_id也不等于卡牌GUID |

原版小豆丁的当前实际卡表是字典键`"326"`、组件`Card.Guid=326`、`prefabName="Weenie_Beanie"`。鳄梨GUID为1，`prefabName="2f9fa005-8b50-4d1a-89be-38e4a82036c4"`。这已说明prefabName既可以像UUID，也可以是普通英文名。

社区索引中的`UUID`通常指这个资源/文本字符串，不是卡牌数字GUID。不要把`TEXTURE_NAME`、资源路径或本地化键的前缀都统称为GUID。

## 2. 属性和技能从卡表读取

`cards/card_data_<n>`是Unity Bundle，内有名为`cards`的TextAsset，其`m_Script`是卡牌JSON。外层显示字段与内层组件承担不同职责：只改`displayAttack`不等于已改实际力量，只改中文“造成6点伤害”也不产生伤害效果。

当前原包的身份组件片段如下，**不是完整可导入卡牌模板**：

```json
{
  "$type": "PvZCards.Engine.Components.Card, EngineLib, Version=1.0.0.0, Culture=neutral, PublicKeyToken=null",
  "$data": {"Guid": 326}
}
```

旧教程里的`CardComponent`、`SunCostComponent`等示意不能代替当前完整类型。克隆卡牌时保留原版结构，只改变身份与明确请求；模板内引用其他卡的GUID、种族或专属效果，不应因新增身份而全局替换所有整数。

同一`prefabName`不要求两张卡的属性、技能相同：这些主要来自各自的卡表定义。但原生能力可能带有对来源卡或特定视图的隐含联系，需要单独验证，不能保证任意能力包移植都等价。

## 3. 文本从prefabName派生

| R9文字字段 | 当前常用游戏Key | 含义 |
|---|---|---|
| `name` | `<prefabName>_name` | 卡名 |
| `text.short_description` | `<prefabName>_shortDesc` | 卡面技能短说明 |
| `text.long_description` | `<prefabName>_longDesc` | 详细技能说明 |
| `text.flavor_text` | `<prefabName>_flavorText` | 简介、趣味介绍、背景台词 |
| `text.target_hint` | `<prefabName>_Targeting` | 目标提示，注意大小写 |

还可能引用`_heraldFighter`、`_heraldTrick`等出牌提示。模板克隆时复制当前需要的文字；改名后核对相关提示，不能只补一个`_name`就声称全部显示已同步。

例如两张不同GUID的卡都使用`prefabName="Weenie_Beanie"`，普通文本路径都会请求`Weenie_Beanie_name`。新增`900001_name`不会自动让第二张卡改用这个键；修改共享Key还会影响原卡。这是“新GUID已独立，中文仍串用”的根本原因。

R9给新卡分配独立prefabName，再把美术寻址复用到原版，因此同一美术可以有不同卡名、技能说明和简介。中文CSV位于`loc/cn_<n>` Bundle的`LocalizedStrings` TextAsset；修改要保留CSV引号、换行、额外列及非目标记录，不能按物理行随意切分。

## 4. 卡牌定义与收藏登记分开

R9游戏读到653/654张定义，调试接口能按新GUID实际抽卡并合法打出，证明定义已加载。它没有证明新卡已在收藏里显示、拥有数量已保存、能够组牌或通过卡组合法性校验。

资源路径`InCollection`也只是检视/图鉴美术入口；能找到图鉴图片不等于完成收藏系统登记。R9未扩展收藏、组牌或账号库存的持久化。

## 5. 最小核对顺序

先核对字典GUID与Card.Guid，再核对prefabName及其中文Key，最后核对三类资源路径与实际加载。文本读取、属性读回、技能结算、资源映射和画面布局分别留证。R9用原版CardTextGenerator及检视面板工厂读回文字，再通过带画面对局验证出牌和回合效果；没有把文本读回当作技能成功。
