# 05. 本地新卡身份、玩家拥有权与服务器裸 GUID 边界


R9 解决了新增 GUID 的独立文字和原版美术复用，R10 增加本地拥有权及缺失引用保护，R11 继续处理“两个 Mod 都有同一个新 GUID”的问题。这三个阶段分开记载，不把后续结果回写成 R9 当时已经完成。

**本地新卡的身份不能只看数字 GUID。** 本机预约新号可以减少新冲突，来源身份与玩家文件过渡处理已有冲突；二者都没有给官方服务器新增来源字段。服务器后来返回一个裸 GUID 时，本地无法凭这个数字判断它原来属于哪个 Mod。

## 定义、美术、拥有权与牌组是四条链

| 层次 | 负责内容 | 单独完成后仍不能证明什么 |
| --- | --- | --- |
| `card_data` 定义 | 字典 GUID、`Card.Guid`、属性、阵营、职业、原版技能组件、Token／可用标志 | 不证明图片可加载，也不证明玩家拥有 |
| 文字与资源寻址 | `prefabName` 对应 CN Key；R9 别名适配复用原版 Prefab／InHand／InCollection | 不证明普通收藏或组牌登记完成 |
| 本地拥有权 | R10 根据真实原版筛选补足可用新增卡的本地数量 | 不证明库存 Delta、服务器或所有界面同步支持 |
| 牌组与身份过渡 | 原版 Provider 保存牌组；切换时处理缺失或同号异身份引用 | 不自动恢复已经被玩家重新编辑的旧牌组，也不扩展云端协议 |

资源定位链仍见本章前四篇。多 Mod 的资源组合保持整文件覆盖，不能因为拥有权按 GUID 工作，就把多个卡表逐卡合并。

## R10：自动识别候选，继续使用原版收藏规则

候选集合是“实际胜出卡表 GUID 减去可信原版底稿 GUID”，不按 `>=900000`、是否有 `_pvzh`、是否有别名或卡表行数判断。外来改版在低编号空位添加的卡，也属于候选。

候选不等于可收藏。运行时查询原版 `DeckEditorUtils.IsCardAllowedInAnyDeck(CardData)`；当前版本核对的条件包括 `Usable`、`IsPower` 与忽略集合 `Token`、`Cheats`、`cheats`、`Blank`。Token 继续留在定义表供技能使用，不强改成普通收藏卡。原版职业、阵营、英雄与同卡张数限制继续生效。

对允许的新增卡，在本地 `PlayerInventory.Cards` 中补到至少四张：只补 `max(existing,4)-existing`，重复读取不累加，已有更多也不减回四张。**不向库存 Delta 授予新卡**，不改货币、英雄或卡包。拥有权不是把一份修改后的完整库存永久覆盖到账户。

R10 已有证据包括：原版卡册数据提供器返回新增普通卡而排除 Token；原版 Validator／Provider 保存 40 张临时牌组；升级与完整冷启动读回同一牌组；使用保存序列进入有画面 fixture 抽牌、合法出牌；移除 Mod 后精确保留原牌组其他记录。R10 当时没有完成正式 campaign 入口与通关，也没有验证官方同步。

## 收藏卡面还有独立的 GUID 索引链

R11推进真实收藏界面时进一步区分了“能按逻辑路径取到InCollection资源”与“原版卡册真的画出新增卡面”。原版 `DeckEditorCardSpriteCache.GetSprite(cardId)` 还会按数字GUID查询职业合图的Sprite索引；新大GUID超出原版索引可返回null。路径别名成功、单位能在战场出现、Owned有数量，都不能单独证明卡册卡面可见。

本轮方案在实际胜出卡表上生成 `collection_asset_bindings`，将新增GUID映射到可信原版模板GUID。带合法 `_pvzh` 的卡取明确的 `template_guid`；旧式卡只在原版prefab、阵营与卡种唯一匹配时建立映射，外国自定义美术或歧义prefab不猜。普通原版GUID不进入此回退表。

运行时保留原GetSprite已经返回的非null结果；只有登记新卡原返回null才向同一个缓存查询模板Sprite，避免替换外国包自己已有的正确卡面。模板职业holder尚未加载时记录未加载／null，不贸然执行可能抛托管异常的原生调用；还有线程重入保护。该机制不生成新美术、不替代路径资源适配，也不扩大拥有权范围。实现和静态正反例只是机制证据，最终可见卡面仍按本轮实际屏幕与最终事实表验收。

这个发现应追加为R11经验，不能回写成R9当时已经逐项测试了收藏UI，也不能把卡册Provider通过改称为卡面渲染已通过。

## R11：先预约新号，再比较稳定身份

### 安装内预约不是社区全局号段

手机工作台的分配器持久保存预约，检查已登记的当前／禁用 Mod、历史与已知草稿卡表。取消草稿或移除 Mod 不回收已观察或预约的号码；登记损坏、来源读取失败等情况明确报错，不能静默清空后重新从头分配。

该机制只减少同一安装内由工作台新造卡时的冲突。不协调其他手机、社区作者或以后导入的旧 ZIP；`900001` 仍不是社区保留号码，也不自动重写外国包内部 GUID。GUID 还可能被关卡、牌组和扩展参数引用，盲目换号会使这些引用分离。

### 原生卡、旧式卡与显式复制

| 卡牌类别／操作 | R11 当前身份依据 |
| --- | --- |
| 原版底稿已有 GUID | 原版共享身份，允许各 Mod 改写其能力 |
| 带合法 `_pvzh` 的原生新卡 | 已有稳定独立 `prefabName` 谱系；普通属性、技能和 CN 更新不重造身份 |
| 没有 `_pvzh` 的旧式新卡 | `card_identity_namespace`、GUID、`prefabName` 的组合 |
| 工作台显式“复制此 Mod” | 副本继承源命名空间，连续复制继续继承；复制已有原生卡也保留别名 |
| 副本中新造的原生卡 | 分配器预约新号，并使用副本项目的新原生别名 |
| 无 `mod.json` 的外国原始 ZIP | 默认 ID 来自 ZIP SHA；不同包 SHA 且无明确同源声明时视为不同来源 |

`mod.json` 中新增的 `card_identity_namespace` 是启动器项目合同，默认 Mod ID，接受 1～80 位字母、数字、下划线和连字符。它是显式谱系声明，不是原版引擎字段，也不构成第三方身份认证。

例如从外国包 A 显式复制出 B，B 继承 A 的 namespace，之后只改中文或属性仍按同一卡处理。直接重新导入作者的另一份无清单 ZIP，启动器没有这份明确复制关系：即使名称相似，也不自动认定同源。这样的外国包升级可能需要重新组牌，原记录先备份。不得笼统承诺“任何改版正常更新都不影响牌组”。

开发复核曾发现“旧式外国包副本换了项目 ID，牌组因此被清理”的问题；R11 RC2 引入 namespace 继承修正。不能只用原生 `_pvzh` 卡的复制测试证明外国卡复制也安全。

## 旧收据迁移与一次本地过渡

应用目标前，先核对旧加载收据指向的卡表归档、活动卡表及其 SHA，而不是把准备启用的 B 表反推成此前 A 的身份。R10 收据没有 R11 身份字段时，可以从经核实的旧表及来源重建；活动文件被外部替换、归档缺失或不能读取时，旧来源属于未知。

过渡时原版 GUID 保留；新卡只有旧、新稳定身份相同时才保留既有引用。已移除、同号异身份和无法证明旧归属的新卡引用先备份后精确处理。首次未知来源采用保守策略，并告知需要重新组牌；不凭当前目标表已有这个数字就保留所有旧引用。

玩家文件与资源、身份收据共用事务：准备阶段生成备份和暂存；提交前整批核对玩家原件、暂存、回滚备份的 SHA，第一份用户文件还未改变时就拒绝后面某份文件的问题；逐项写入前再检查一次，覆盖整批检查后的外部变化。资源与玩家内容部署后才提交加载收据。

回滚按目标当前状态判断：仍为 `before` 的行直接跳过，不依赖这时已经用不到的备份；等于 `after` 的行必须有可靠原备份才恢复；既不等于前也不等于后的外部改动停止自动覆盖。恢复后再次核对 SHA。并发变化或中途故障的完整正确性需要存储层故障验收，不能仅用纯身份函数证明。

处理范围为已核对 protobuf 的 `PlayerDecks`、`PlayerDecksDelta`、`PlayerInventory`、`PlayerInventoryDelta`，只删除目标引用，保留其他卡、牌组 Id／Name／HeroId／Theme、未知字段及其他牌组。原版不足 40 张的套牌保持待补齐，不擅自填卡或清空 PlayerData。

运行时仍可过滤当前定义表不存在的裸 GUID，但不永久封禁一个碰撞数字。切到 B 后，玩家可以重新把 B 的同号新卡加入牌组。再次启用 A 也不把旧引用自动塞回已经编辑过的牌组。

## 服务器裸 GUID 是独立边界

假设 A 的 `900001` 是甲卡，B 的 `900001` 是乙卡。启动器知道自己刚从 A 切到 B，所以能处理本地 A 引用；官方服务若随后只返回 `[900001]`，其中没有 namespace 或原生别名，不能判断这张记录原先指甲还是乙。

因此，本地身份保护不等于官方服务器知道新增卡，不保证官方客户端能读带新卡的账户，也不代表联网／联机已经兼容。测试应离线进行，记录服务器同步未验。不要通过永久拦截这个数字解决问题，否则当前 B 的乙卡也永远不能正常组牌。

### 明确保留的限制

- 本机持久预约不保证跨设备全局数值唯一；外部同号不自动重写或逐卡合并，实际整文件赢家决定生效卡表。
- 服务器裸GUID没有来源字段；本轮离线验收，未扩展官方同步/PvP协议，未验证服务器奖励到账。
- 无manifest的外国ZIP更换SHA且无稳定同源声明时保守视为新来源；同一legacy namespace/GUID/prefab内语义重用不能自动区分普通修改。
- 正式流程覆盖一副40张测试牌组、植物任务002及代表新卡，非所有英雄/技能/关卡/外国改版的穷举验收。Syndrome沿用R10的特定原包历史结果。
- 本轮未调用AI API；公开Python v1制卡合同未因Android产品更新而升级。
- 源码仅本地Git归档，不附游戏载荷/账号/密钥/签名；重建仍依赖外部原APK及SDK等。

官方返回的裸GUID没有Mod来源，本地namespace与切换防护不扩展服务器协议。外国无manifest的不同ZIP SHA在没有同源声明时仍视为新来源；显式clone继承namespace的合同与此分开。

完整筛选来源与指纹见[玩家生命周期验收摘要](玩家生命周期验收摘要.json)。本次文档整合没有调用设备或API，设备结果来自表内来源；本地Git提交与远端发布另行记录。
