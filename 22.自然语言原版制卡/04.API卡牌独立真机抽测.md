# API卡牌独立真机抽测（2026-10-18）

本轮是上一轮离线／API生成之后的独立设备验证。用户要求挑选已有API输出放进游戏，确认技能实际结算，并且与mod2隔离、不合并。没有再次调用API，也没有改写模型计划或把手写计划当作模型输出。

## 隔离和输入

从[已公开的八批模型计划](../tools/natural-card-author/benchmarks/recorded/)中选取六个ready方案，由同一原版编译器从匹配原包回包。每份只改变一个GUID；因为多个模型方案使用相同底卡326，它们作为六个单卡profile分别冷启动，不声称在一包中同时加入六张新收藏卡。

测试使用B4底座，只保留原引擎调试、资源与教程跳过，不加载mod2技能脚本。Gadget用于传输语义命令和创建测试对局，实际技能由缓存中的原版组件树执行。B4 APK SHA-256为`9af06d613c55644e1bbc9558f0108f0c61e0b37830da29525d5935c54fef97bc`；脚本SHA与每份设备卡表／中文指纹见独立[真机验收摘要](真机验收摘要.json)。

设备是root Pixel6 ARM64。测试前核对手机安装APK与已保留的本地R25包完全一致，备份卡表、中文、关卡三缓存及mod2资源收据。临时换装B4，写入独立候选和原版关卡；不改mod2源码、资源或发布APK，不清账户数据。

## 验证方法

每份在独立冷进程建立`agent_test`，seed=1337、双方100血／50资源，使用普通原版初始牌组，再给入测试卡。通过`legal_plays`和原版`play`验证手牌、落点、费用与触发；`summon`仅用于准备前置场景或单独观察原生创建行为。

保留全部请求／响应、开局与收尾实体状态、实际PID、runtime身份、设备缓存指纹及当前PID的crash buffer。手动出牌与创建是不同测试路径，不能因为一次召唤存在单位就声称打出触发已经验证。

## 本轮结果

最终六份方案均通过，共25个检查点。每份API计划及候选Bundle保持原样，未修补制卡编译器；三头花生复制的首次助手断言失败与重测分开保留。

| API用例 | 实际结算与反例 | 最终检查 |
|---|---|---|
| `play_hero` | 小豆丁合法打出扣1费，僵尸英雄受3伤；植物英雄不变，普通植物不重复造成伤害 | 4／4 |
| `played_target` | 自己登场变2/2，后来打出的植物各得永久+1/+1；旧单位和等待中的手牌不提前增益，控制者不跟着重复加成 | 4／4 |
| `adjacent_freeze` | 左右相邻两只敌军获得Slowed；同线、远线敌军、相邻友军和自己不冻结 | 3／3 |
| `turn_zombie_draw` | 纸板机器人实际2费3攻4血；连续两轮各抽2张额外牌，加自然1张共3，牌库对应减少3；植物方只正常抽1张 | 3／3 |
| `damage_not_attack` | 原版骆驼先加血确保来源存活：1攻被装甲1抵为0时不回手，来源受伤也不触发；另一来源实际造成1伤后仅弹回一个随机植物，原实体进入手牌并离开路线 | 6／6 |
| `copy_three_nut` | 保留小豆丁1/1与身份，原有植物不追溯改攻；新打出1攻单位升到3，新打出6攻千斤南瓜降到3且生命仍6；僵尸打出不改攻 | 5／5 |

两项额外观察：B4直接召唤带登场伤害的小豆丁未扣英雄血；在出牌增益控制者在场时直接召唤普通植物，也没有获得+1/+1。它们只说明此次B4显式CreateCard准备路径，不概括为所有原版召唤／现身机制都等价。

六个最终进程均存活，当前PID的crash buffer没有记录；日志中的初始化错误另列于下节，不能简写成“无错误”。随机回手仅验证seed=1337下候选集合与一次实际结果，不证明随机分布或全部种子。

## 遇到的流程问题

B4旧资源界面继承了mod2设置的`skip=false`，停在“资源已准备好／进入游戏”，没有进入Unity，语义接口因此尚不可用。已用原生UI层级确认原因。在三缓存显式散列校验之后，测试助手直接启动原版`NimbleActivity`，未改用户的记忆选项、卡表编译器或mod2门卫。

这属于两个版本之间的启动助手适配问题，不是技能不生效或游戏闪退。不能把这种专用B4启动路径照搬到必须选择资源的mod2正式流程。

七次测试尝试（含一次助手FAIL）在第一次fixture状态可读前，共记录14次`state`轮询的托管`System.NullReferenceException`，栈在`GetPlayerFactionForPhase`／`GetCurrentBlockingPhaseState`。完整错误响应保留；等待初始化后可读并继续完成技能检查，没有出现native access violation，fixture就绪后错误响应为0。它提示`app_ready`与“新对局可读”仍是两个不同屏障，不能报告整轮接口从未报错，也不能仅凭发生时机归因为某张技能卡。后续应在调试API层补充明确的对局就绪结果，而不是让公开UI依赖异常重试；本轮没有修改B4底座。

三头花生复制的r1检查把GUID81“夏威夷聪明果”作为高攻目标。其攻击已正确从4设为3，但它的原版打出技能会给坚果+2生命，实际为3/7；助手却按基础5血断言，整例因此保留FAIL。旧的其他坚果也各增加2血，保留豆子种族的技能控制者没有加血，符合原生效果。重测换用无技能的GUID7千斤南瓜，并保持API计划及候选Bundle不变；旧失败、当时助手源码及状态快照全部保留，不归因为制卡组件错误。

## 范围

本轮验证headless模型中的实际出牌与原引擎结算，没有模拟点击或截图，也没有做逐帧动画、special美术或AI预测验收。B4的headless `animations_empty=true`不能作为实际动画播放成功的证据。

测试结束已恢复R25安装包与三缓存，SHA全部与测试前一致，mod2资源收据未变化。手机停在正式必选资源页面，原版／mod2两个入口均启用，尚未选模式；启动该页面后三缓存再次核验不变。恢复状态另记在机器摘要。上一轮构建报告保留`runtime_verification: NOT TESTED`原值，新游戏证据单独存放，不回写旧静态结果，也不把六份抽测扩大为全部原版技能已验证。

原始实验工程、候选与日志位于用户工作区`native-card-device-lab`；不作为Library工具依赖。库中只放方法、最小断言结果与来源散列，不附带游戏资产、完整运行时或账户数据。
