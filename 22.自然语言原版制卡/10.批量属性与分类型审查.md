# 10. 批量属性、有限程序与分类型审查

2026-10-24，Android R23阶段归档。本文接续[独立审查与新手表达验收](09.独立审查与新手表达验收.md)：保留技能修改的完整候选取证，把简单重复的属性任务交给本地程序全量处理。它没有升级本库公开Python v1合同，不提供完整Android工程、调试接口或游戏资产。

最终RC4已完成真实DeepSeek批改与原样候选三卡原引擎14项PASS；RC3还完成单卡例外、拒绝不保存和手动历史整理后的真实请求。保留RC2审查OOM、一次测试GUID断言纠正与低堆夹具边界。下面的415单位与1241项属于本机数据或协议范围，不能写成415张卡都在游戏内打出。筛选记录见[批量属性验收摘要](批量属性验收摘要.json)，设备、AI与内存修复状态分别登记。

## 1. 将一条规则交给程序，不让模型列出整张卡表

玩家说“把全部单位改成9/9”时，若AI逐个输出GUID、再逐卡完整读回技能，数百张相同操作会同时消耗输出、工具预算与上下文。问题应在操作表达与证据组织上解决，不能仅增加token上限或先压缩一段仍会重新读取的大文本。

R23新增的Android计划示例：

```json
{
  "schema_version": 1,
  "status": "ready",
  "bulk": [{
    "op": "set_stats",
    "selector": {"faction": "both", "include_tokens": true},
    "stats": {"attack": 9, "health": 9}
  }]
}
```

模型只输出一条选择规则和两个数值。本地程序冻结当前Mod快照，选出单位、改写显示与ECS基础值、保留其他字段，再产生带计数、哈希和最多8个样本的摘要。费用未填写便保留；原技能、后续增益或变形规则也保留。因此“基础属性改为9/9”不保证其在所有战斗时刻永远保持9/9。

首版同一plan不混写`bulk`与`cards/new_cards/localization/levels/registry`，程序明确拒绝混合输入。需要例外或技能联动时，可以先产生bulk候选，再沿该候选追加普通卡牌/文字修改，最终展示相对于保存版的累计差异。这个限制属于当前产品表达范围，不是游戏引擎无法同时处理这些数据。

选择器支持阵营、`include_tokens`、明确GUID、tag与费用范围；批量固定设置及有界算术是已登记能力，不接受任意路径和字段。当前单位判定会排除英雄/玩家实体。Token/power标记和不可收藏标记分别统计，`include_tokens=false`排除任一已识别类别；不能据此保证识别所有外国改版的自定义token，也不改变卡牌收藏或组牌资格。

## 2. 审查策略根据实际差异决定

`report`或模型自称“只有属性变化”不能决定审查类型。程序从真实编译前后卡数据求diff，再确定以下义务。

| 实际变更 | 程序证据 | 模型必须核对 |
| --- | --- | --- |
| 纯基础属性 | 全部目标、显示/ECS一致、其他字段与技能不变 | 用户要求的范围、数值、聚合与样本；无需逐卡读未变技能全文 |
| 纯CN文本 | 卡数据不变、实际Key和值差异 | 文意、目标绑定、引用与是否把未实现技能写成已实现；无需为每次改字重读未变技能全文 |
| 技能或结构 | 真实变动GUID及最终候选定位 | 对应卡的完整身份、文本、组件、技能实体及证据 |
| 属性与技能混合 | 每张卡分别分类，其他纯属性卡仍保留程序全量检查 | 仅对实际技能/结构变动卡强制完整读取，不要求所有属性卡跟着全文重读 |
| 显示/ECS不配对或类型错误 | 定位到GUID和字段的程序错误 | 不允许用AI的pass覆盖失败 |

纯属性白名单只包括以下成对值：

| 显示字段 | 根ECS组件中的字段 |
| --- | --- |
| `displaySunCost` | `SunCost.$data.SunCostValue.BaseValue` |
| `displayAttack` | `Attack.$data.AttackValue.BaseValue` |
| `displayHealth` | `Health.$data.MaxHealth.BaseValue` |

变化后的成对数值必须是相同32位整数。只掩去这些数值后，卡的所有其他内容仍须一致；新增卡、tag、subtype、metadata、技能或其他组件变化都会转入完整审查。不能通过宽松数字转换、修改报告标记，或只更改卡面字段得到“属性安全”结论。

R17的“全部变动卡完整读取”保留为历史策略；R23将其收窄到真实技能/结构变化。全文义务本身没有弱化：`card:<GUID>`必须是当前最终候选，完整有序技能实体及辅助依赖都在，部分阅读、`original-card`、搜索结果或模型自述都不能冒充全文收据。相关完整性规则继续参考[第09节](09.独立审查与新手表达验收.md)。

## 3. 原版0攻单位可能没有Attack组件

实际650张定义中，有37个已选单位的`displayAttack=0`，同时根实体没有Attack组件。这是原包的合法省略，不能将全部缺组件情形判成坏数据，也不能只把显示攻击改成9。

本次只为“原来显示0攻、根Attack数量为0”的卡补入最小容器：

```json
{
  "$type": "PvZCards.Engine.Components.Attack, EngineLib, Version=1.0.0.0, Culture=neutral, PublicKeyToken=null",
  "$data": {"AttackValue": {"BaseValue": 9}}
}
```

类型字符串来自本次原包现有Attack组件，不能跨游戏版本照搬。程序同时更新`displayAttack`，保留其余组件与顺序。审查分类仅豁免这一精确最小容器：增加额外字段、多个Attack或其他结构改动仍会要求完整审查。

因此“不增加任何组件”并非所有属性编辑的正确不变量。更准确的是：只允许有原版事实依据、与目标属性配对的最小补全，并记录具体GUID和数量；其他技能/结构必须不变。换一份输入包后应重新统计，37不是跨版本常量。

## 4. 沙箱是有限数据程序，不是JavaScript

R23的`pvzh-ops-v1`输入示例：

```json
{
  "language": "pvzh-ops-v1",
  "program": [{
    "op": "set_stats",
    "selector": {"faction": "both", "include_tokens": true},
    "stats": {"attack": 9, "health": 9}
  }]
}
```

预演在冻结卡表的内存副本上执行，返回受约束的bulk计划、目标摘要和指纹，`read_only=true`、`writes_performed=false`、`runtime_validation=NOT_TESTED`。只有随后显式生成候选，才进入现有编译流程；候选仍需玩家同意后保存Mod，预演和模型不能自动采纳或部署。

程序支持`set_stats/adjust_stats`、筛选、当前值/基准值与有界算术；不执行任意JS、宿主反射、原生桥、文件、网络、ADB或无限循环。操作数、目标数、表达式深度、工作步数、时间与报告尺寸都有本地限制。示例中的数值范围是当前沙箱政策，不应称为游戏引擎极限。

多步程序的选择器按每步开始时的当前卡表重新计算；例如前一步改变费用，后一步费用范围可能命中不同集合。`current`取该步开始时该卡的值，`base`取整段程序输入值。不能一边更新同一卡字段，一边让后续字段意外读到本步刚写的结果。

## 5. 账本重放必须使用真实编译父候选

保存版、请求起点与最新编译父稿是不同对象：

```text
saved S → 旧pending W → 本轮内部候选 A → 返修候选 B
```

审查本轮变化看`W→B`，最终累计预览看`S→B`；若B由A上的bulk编译，重放B的最新账本必须从A开始。拿W或S重放会把合法的第二轮返修误报为输入哈希不符。反过来，不核对父稿也可能让失效证据被沿用。

本地账本固定在`authoring/batch-history.json`，记录输入/输出卡表指纹、逐步操作、完整选中GUID及属性前后值。验证器重新执行冻结程序，比较操作和完整选集，再读取最终候选每个目标的真实显示/ECS值；阵营、单位、token和不可收藏统计也从实际卡数据重建，不采信报告里的概述。

R23接口使用`describe(saved,working,after,report,batchBasis)`区分审查起点与最新bulk的编译父稿。来源Mod、父草稿、ZIP与卡表指纹均应绑定。给后续CN子稿复制报告时，不能让旧bulk元数据假装成CN这一步新产生的批量证据。

账本用于追踪和独立重放；本文不宣称已经完成任意RFC 6902 patch、任意脚本、每条操作撤销UI或部署失败自动回滚的通用管道。Mod版本与审批机制继续按产品当前实现分别验收。

## 6. 全量证据留本地，模型读取摘要和所需页

本机保留完整差异、完整选集、候选与账本。默认模型输入只给全量计数/哈希、分类、最多8个样本和明细读取句柄；摘要明确标记“聚合完整、明细省略”，不把抽样说成全部检查。

- `summary(fullFacts)`保留分类证据，纯属性样本不重复技能树。
- `requiredReads(fullFacts)`只为实际`skill_changed_guids`建立全文义务；旧事实格式无分类时兼容原策略。
- `read_change_details`按增量/累计与cards/localization/levels分页，单页1至8项；需要完整卡技能时仍按GUID读取。
- `compactReport`用于待审提案和工作候选上下文，避免下一轮又回灌全量`card_previews`或所有GUID。

大批量UI同样显示总数和少量样本，完整列表分页。预览基线应冻结到草稿当时的源卡表/CN并保存哈希；Mod后来保存新版本后，打开旧提案仍用旧基线，不能用新source生成看似“没有变化”的假差异。

在本次固定9/9本地案例中，RC2完整facts约183万字符，RC3将纯属性变化投影为精确标量后约150万字符，默认审查摘要仍约2.08万字符。这个差距来自分类型证据和按需投影，不是把完整事实删除，也不是AI已经完成游戏结算验证。

## 8. 小摘要仍可能伴随大堆内存，保留真实失败

RC2第一轮真实AI已经产出bulk且编译完成，但进入`verifyBatchScope`时又把整张卡表通过`toString→JSON parse`复制一次，在Android 256MiB Java堆上OOM。此前的三卡游戏场景通过不能覆盖这次工作台失败；减少传给模型的token，也不自动减少本地保留的卡表、Bundle、ZIP或研究快照。

RC3保持独立重放、字段门禁和哈希语义，调整对象生命周期：批量操作对真正改动的卡/属性路径采用copy-on-write；验证器只读传入冻结源，不额外复制整表；属性分类用只读结构比较而不每卡复制两份；哈希流式生成，返回给外部的分页内容单独detach。工具调用结束后释放上一阶段研究对象，在编译与候选事实提取期间不继续持有旧研究卡表；包内冻结引用与公开防御复制分开。

当前六个输入/输出/非属性/操作/账本/摘要黄金哈希与RC2一致，源数据在执行和重放后仍不变。官方Android JSON在128MiB JVM堆上完成四轮415目标全量重放，同时保留独立原版/保存版表和32MiB无关状态；另一份含候选序列化回读的128MiB黄金对照也通过。完整73项反例套件在256MiB通过；其128MiB运行仍在测试夹具连续复制原表时OOM，该失败另存，不能冒称完整套件128MiB通过。

这些测试说明已排除已知重复复制路径，不是ART内存峰值保证。随后RC3真实批改、例外与整理历史请求在同一进程完成；最终RC4真实批改及冷进程三卡原引擎复验通过。后续成功没有回填RC2 OOM，仍需按新任务输入和设备状态继续观察。

## 9. 最终新手表达、工具schema与整理历史

最终真实请求仅为“把所有单位都改成9/9。”，没有向模型预填GUID、标准答案或人工改写其计划。DeepSeek产出203字符的一个bulk，命中415单位、实际变化414张，UI保留8个预览样本；属性审查的`required_full_skill_reads=[]`。真实API候选卡表Bundle与固定批改结果相同。

整个最终请求共4次供应商HTTP，合计输入41,217、输出1,411 tokens；包含独立需求、作者工具往返和审查。它是多请求累计usage，不是单个上下文占用，也不是与旧版本相同任务的统计对照。`query_units`和`run_sandbox`各一次有效执行；最终工具说明明确区分外层参数对象与内层操作数组：

```json
{"program":{"language":"pvzh-ops-v1","program":[{"op":"set_stats","selector":{"faction":"both","include_tokens":true},"stats":{"attack":9,"health":9}}]}}
```

前版模型曾先把工具参数写成`{program:[...]}`，能自行纠正但多消耗请求。RC4用嵌套JSON Schema与外层完整例子减少这类形状歧义，未放宽运行时校验，不把裸数组默认为合法程序。

RC3连续请求“再把豌豆射手改成10/10，其他刚才的修改都保留。”正确只改GUID10，其余卡不变；随后拒绝该提案，保存版仍是全体9/9。测试原先错误地把“豌豆射手”断言为GUID326，后从实际原版身份纠正为GUID10。旧FAIL留存，未修改AI计划、未补一轮API凑结果。这里的GUID326是三卡游戏抽测选用的普通植物，不是豌豆射手。

历史整理用30条原消息、原始归档90,195字符验证；本次测试保留最近4条，发送历史投影由40,691降至16,624字符，真实请求确认使用派生记忆，原消息仍完整保留。UI默认保留最近8条；没有自动调用模型压缩，也不将原始归档大小当成实际发送大小。派生摘要、用户备注和历史内容不替代当前源卡表、用户同意或游戏收据。
