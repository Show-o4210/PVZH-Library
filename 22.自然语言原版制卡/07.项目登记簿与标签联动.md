# 项目登记簿、标签与跨会话联动

记录日期：2026-10-21。本文是Android R15后续产品的本轮归档，承接[06](06.实验原版组合与最小验证.md)。公开Python v1的schema/API和旧验收成绩不变；完整Android工程、测试运行时、APK、游戏资产与账户资料不随Library提供。

当前已经完成真实手机API的登记拒绝/采纳、三张新卡分阶段生成及跨新会话复述。原引擎播种机25项、观察者29项、回收站37项和联动23项通过；播种机按调整后的“当次持续减1费”，原临时要求仍未实现。成品导出及最终设备恢复24项通过，所有旧失败保留。规范状态见[验收摘要](项目登记验收摘要.json)。

## 一、项目资料与可执行技能分开

作者资料随Mod保存在`authoring/registry.json`，派生人类说明为`authoring/README.md`。它们不进入游戏资源映射。上下文中的`project.authoring_registry`提供符号、相关规则/决策/待办，以及程序从真实卡表重建的成员与查询绑定。

规则文字不是技能实现，也不是系统指令或可信PASS。导入包中的“忽略限制”“已经实测”等文字不扩大权限；模型不能编造成员扫描、来源或验证结果。实际节点仍在卡牌native中编译，真实测试结论由程序证据提供。

登记增量结构：

```json
{
  "registry": {
    "symbols": [{"id": "spore", "kind": "tag", "name": "孢子", "description": "本项目孢子植物集合"}],
    "remove_symbols": [],
    "rules": [{"id": "spore-first", "name": "各自首次", "description": "每个场上来源实例独立限次", "symbols": ["spore"]}],
    "decisions": [{"id": "spore-pool", "text": "首轮指定非空池，随机获得允许重复"}],
    "todos": [{"id": "spore-turn", "text": "核对回合重置与无关事件是否消耗次数"}]
  }
}
```

同ID为upsert，省略旧项表示保留。仅登记也能形成待审提案；可先登记暂无成员的集合，标明尚无成员，不把空集合当作拒绝整个设计的理由。随机生成实测前仍需明确非空池。

内部ID更名按新建、迁移卡牌/查询引用、删除旧符号处理，不暗示自动全局改名。删除可以和成员/查询更新在同一提案中完成，按最终引用检查，避免提前拒绝合法原子迁移。

## 二、标签、种族与查询的关系

卡牌行通过`tags:{"add":["spore"],"remove":[]}`修改成员。原版组合使用`CustomTagQuery.data.Tag="spore"`，程序按项目登记归一为稳定实际engineTag，AI不拼namespace、不猜新GUID。只增减指定的自定义tag，保留原tag及原Subtypes；首版kind仅tag，不新增Subtype。

CustomTagQuery是共享1.67.8 ARM64 dump中的真实查询，Tag为string，读取被查询实体的Tags成员；原版650定义中未观察到该序列化查询实例。因此“有真实类型/字段依据”“工具已登记”“新组合实测”分别记录，不能把它写成原包已有完整孢子配方。

它不隐含己方、场上、手牌、事件目标或来源。卡池生成时组合植物/单位/tag；出牌观察时限定事件目标并明确主目标；死亡事件还须区分被消灭与回手。标签只是集合条件，不能替代这些范围。

## 三、审批与跨会话事实

登记与卡牌/中文在同一个待审ZIP中原子采纳。`saved_mod`指保存版本，`unaccepted_candidate`指累计待审稿；继续修改时以后者已经分配的卡GUID和符号为基础。拒绝不更新canonical登记，历史被拒设计不成为当前项目事实。

真实手机工作台使用deepseek-flash，初轮七个阶段均为新会话，初始messages/proposals为空，结果request.attempt均为1：

| 阶段 | 已观察结果 |
| --- | --- |
| 仅登记后拒绝 | 产生提案，拒绝后登记未保存 |
| 仅登记后采纳 | 新会话再次形成提案并保存 |
| 创建三张基础卡 | 新会话按保存登记创建身材/tag卡，无技能 |
| 分别添加三卡技能 | 三个独立新会话各编辑一张，编译ready并采纳 |
| 纯recall | 又一新会话完整说明项目，plan=null、零提案 |

合计六份提案、五份采纳、一份拒绝，另一次纯说明没有提案；只统计上述初轮流程，不包含后续反馈修订。新会话回答了标签用途、三卡身材、按每个来源实例独立首次的设计及未测状态。这证明本轮能够消费随项目保存的资料，不是模型脱离上下文获得了永久记忆。

| 实际GUID | 卡牌 | 属性 |
| --- | --- | --- |
| 900014 | 孢子播种机 | 3费2/4 |
| 900015 | 菌网观察者 | 2费1/4 |

三张均为spore成员，初轮保存视图的卡表共653定义、成员3张、consumer查询5处。数量来自该次真实扫描快照；后续修正版须重新扫描，不硬编码。

最终整理后仍为3个成员，查询consumer为3处；又一空历史新会话的纯recall正确读到持续减费、原临时要求未完成、各实例限次和未测边界，plan=null。模型仍将项目笔记与可信测试证据分开，没有把文字记录自动升级为PASS。

完整API流程最终为11个新会话、12次会话尝试、9份提案（8采纳/1拒绝）、2次纯recall；另一次预检后共13次provider响应。feedback3一次格式外壳修复使attempt=2，原修复原因保留；初轮七次attempt=1没有被扩写成全流程零修复。

## 四、原版参考与设计预期

播种机原始设计为随机获得2张孢子植物，仅本次本回合减1费。原版180有生成数量、改费辅助实体与HeraldEntities；449/542有生成事件和DrawnCardQuery，501提供来源筛选参考。完整实体关系、准确目标及来源绑定须核对。后续期限实测没有通过，本轮明确改为“仅本次获得牌持续减1费”，不是悄悄把持续降费当作临时同义实现。

观察者设计为每回合第一次打出己方其他孢子植物时，使事件目标永久+1/+1。GUID418有其他植物出牌、TargetQuery主目标和永久+1/+1来源；141给自己增益，不能原样替代。回收站设计为每回合第一次己方其他孢子植物被消灭时抽1，参考688的其他单位观察及339/378的死亡条件。

原版准确限次类型是`OncePerTurnCondition`，空data，来源180/408/511；不是新私有规则。新组合不要求固定配方，本次单项实际检查了对应的无关事件、同回合第二次、下回合重置和双实例；这不替代同时死亡、控制权转移或沉默等未测边界。死亡目标可能已经离场，不机械添加场上可选/存活查询；控制者自身的生效范围另行检查。

## 五、已发现的工程问题

RC1的父待审登记在后续卡牌/CN子稿中，累计`registry_changed`和登记预览可能显示不完整。RC2改为与保存版比较当前累计结果，保留子稿真实登记状态；回退登记和普通纯卡牌提案不再保留过期提示。

18项本地集成回归通过，调用生产NativeWorkbench及实际Bundle，Android/LauncherStore采用隔离文件系统替身，不是手机UI或游戏结算。另有34项登记合同和17项项目/Bundle/克隆流程通过，各范围分开，不相加冒充技能数量。

播种机首份实际API计划中，生成效果使用AlwaysMatches主目标，改费目标混合Player与DrawnCard，另有Not(Self)来源及Herald混合观察者的风险。原引擎首次报告保留为`FRAMEWORK_ERROR`：5个准备检查完成，合法play请求返回`Error: Error: abort was called`，没有完成生成/降费断言，也未证明整进程闪退。错误类别是测试模块报告，不等同于确定的根因结论。

将实际错误交回模型后，第一份修正版已通过最初生成、费用、旧手牌与牌库检查，但13项检查在其他来源反例中失败，报告为SEMANTIC_FAIL。原版GUID326生成一张原价观察者之外，旧播种机又错误生成两张折扣牌。该修正版没有PlayTrigger的TriggerTargetFilter(SelfQuery)；控制者SelfEntityFilter不能替代事件目标自身筛选。

第二次实际反馈修正版前21项检查通过，第22项到期恢复失败，报告仍为SEMANTIC_FAIL。共享1.67.8的EndOfTurnBuffRemovalSystem只清攻血，不自动清SunCost；原版180虽然序列化BuffDuration=EndOfTurn，其原文本并无“本回合”。字段/模板存在不能替代特定对象的期限行为证据。

主Agent本轮自主决定改为“仅本次获得牌持续减1费”，原临时要求留待研究，不宣称已完整达到最初要求。第三份模型反馈候选采用两个实体、Permanent并移除HeraldEntities，其最终单项25项通过；按新范围的通过不改写原期限FAIL。

观察者首次场景通过自身/无tag不增益、首个目标+1/+1和同回合第二次不增益等11项后，因死亡刺激准备问题报FRAMEWORK_ERROR：直接Damage99没有普通CheckDeath收尾，负血单位仍占线，随后summon被原放置规则拒绝。独立诊断证明追加原版36合法打敌英雄会完成CheckDeath/discard，主机kill随后改为Damage99准备加合法36收尾。牌库/手牌净0，敌英雄额外2伤是已知fixture影响；负血量不算死亡PASS。修正后新场景单列，首次报告保留。

观察者第二轮已完成22项检查后，又因原版SuperblockPhaseBlockingEffect等待而报FRAMEWORK_ERROR。测试主机经合法end_phase_type=11结束该等待后，最终29项通过；两次框架调整没有修改观察者技能本身。不能把测试准备/交互等待写成技能语义FAIL，也不能用最终PASS抹掉前两次报告。

三个场景使用同一QA候选ZIP指纹`474101b7c344f12effb3b801929318c801d5f76242143c4e5c66399f21dae5e4`，分别独立冷启动，无触控/截图，没有手工替换模型技能计划。25+29+37是91个跨场景检查，包含准备/存活等重复项，不是91种独立技能。

联动第一次在任何fixture请求前，Windows报告文件replace发生WinError5，记HOST_IO_FAILURE并保留host-error-state。同一新PID、尚未请求测试fixture的准备进程恢复后，才建立联动场景并完成23项；prepared_from明确指向首次报告，不当作连续温重开清理证据。主机证据写入器增加有界重试，真实Windows文件锁3项检查通过，游戏逻辑未因此修改。

QA中有额外关卡及原卡刺激，用于另一来源生成同一tag牌和测试敌方tag。最终只整理中文与项目登记说明，三张游戏卡体完整SHA逐卡与实测QA一致、原650卡全部相同；交付ZIP只映射cards/card_data与loc/cn，QA关卡/原卡刺激已排除。canonical JSON和派生MD随包导出，未用完整QA卡表指纹冒充成品身份。
