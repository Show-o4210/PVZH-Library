# 能力范围和面向玩家的下一步

## v1已经开放

| 类别 | 范围 |
|---|---|
| 底卡 | 当前已登记原版中的可用单位；改名、费用、力量、生命，保留原美术与身份 |
| 时机12类 | 打出／现身、回合开始、自己受伤、自己造成伤害、自己死亡、友方单位打出、其他友方单位打出、敌方单位打出、己方抽牌、本线战斗开始、本线战斗结束、持续光环 |
| 目标15类 | 自己、出牌事件目标、双方英雄、友敌单位、其他友军、本线敌军、邻线敌军、自己及邻线友军、可用友方路线、自身路线等合同中的明确集合 |
| 动作13类 | 伤害、治疗、抽牌、增减属性、冻结、消灭、回手、额外攻击、召唤指定单位、获得指定卡、指定变形、设属性、即时资源变动 |
| 词条 | 两栖、组队、致命、狂热、穿透、必中、魔免、墓碑、双重打击；装甲数值另列 |
| 原生能力包 | 同阵营可用单位完整能力复制；415个来源逐一静态编译及组件包比较通过 |

这些集合存在组合约束，不能理解成12×15×13种组合全部任意成立。比如抽牌要求英雄目标，召唤要求路线，英雄不能被弹射，手动选择目前只支持打出，持续光环目前只支持永久buff。不同来源的属性、动画、战斗交互仍须单独实测。

完整能力包复制原样保留字面GUID，不自动改写来源同名卡、来源种族或专属视图的隐含联系。415项通过证明静态组件包保真；不能推出415种移植在任意底卡上均符合玩家期待或不存在循环。报告记录来源引用，公开产品还需要经过实机验证的配方白名单。

## 尚未开放

- 锦囊／环境本体制作、全种族／地形／费用条件、移动与次级目标、所有倍数和保留能力变形。
- bounce后继续修改同一卡、多个Manual动作共享目标、同一实体重复效果类型及全部复杂原版树的自由拆装。
- 新的独立收藏卡／美术、跨阵营完整技能包自动适配、任意脚本、R19／R25私有规则及新Gadget。
- 多卡累计项目、冲突合并、撤销、APK安装与运行中旧单位迁移。

其中不少内容可以继续用原版方式扩展；登记新原生配方、补独立预期、再做游戏验收即可。类型索引162项是当前原包事实，不表示162类全部已开放给自然语言任意重组。

## 面向普通用户还要补齐什么

1. **累计项目。**原包、当前项目、历史版本分开，按GUID合并patch，防止第二次单卡构建覆盖第一次修改。编译器保持只读基线和精确改动范围。
2. **预览与澄清。**显示AI理解的底卡、身材、关键词、技能、来源和未完成条款；缺信息时继续对话。保存前给出实际改动，而不是让用户阅读原生JSON。
3. **能力登记。**逐步增加地形、种族、条件、移动、墓碑和原版复杂配方；标注来源、支持范围和独立测试。不能单靠模型自称“会做”。
4. **自动游戏回归。**对每类配方准备可复现的正反例，验证事件、来源、目标、手牌／资源和真实离场；动画与AI另验。编译／回包PASS不自动升级为战斗PASS。
5. **加载适配。**把审核通过、版本匹配的原版补丁交给游戏加载层。首版适合在对局开始前加载；运行中换定义、旧单位是否迁移和缓存刷新是另一组待验证设计。

## UI／hook边界建议

前端请求自然语言制作服务，取得ready／clarify／unsupported结果。ready结果再交给同一编译器，得到目标GUID补丁、中文、指纹和报告；加载端只消费校验通过且版本匹配的产物。AI没有直接写内存或执行native调用的权限。

当前工具已经提供`NativeCatalog.capabilities()`、`planner.messages/generate()`、`compile()`和`write_card()`作为可复用接口；[plan schema](../tools/natural-card-author/plan.schema.json)可接前端形状校验。尚未制作HTTP服务、Android UI或hook加载器，没有测试宣称热更新已经可用。

面向所有玩家的发布门槛应是“项目不会丢修改、用户能看懂并纠正AI、支持列表能验证、失败可以回退”。本轮先建立这一流程的制作核心，不以小样本结果宣称通用制卡产品完成。
