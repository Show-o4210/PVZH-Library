# 05. 会话式制卡、提案审批与持久化

2026-10-20。本文记录独立Android启动器R13的后续工程经验：长期对话、会话切换、整份修改同意/拒绝，以及对话内真实卡片。它建立在R9之后的Android Bundle编译、身份映射和R12能力许可上，**不是本库公开Python v1工具的升级说明**。公开工具合同、2026-10-18 API成绩和六份独立设备抽测仍按原章节保留。

对应执行指南见[Agent17](../agents/17-conversation-authoring-and-approval.md)。新卡资源和本地身份见[第23章](../23.卡牌身份与资源映射/README.md)，受限实验配方见[第21章08](../21.语义调试与技能扩展实战/08.实验能力登记与冷启动许可/README.md)。本次没有因为加入聊天界面而扩大技能或美术制作范围。

## 1. 自动保存聊天与采纳Mod是两次不同的保存

单轮“输入要求→生成预览”可以制作一张卡，但连续讨论需要回答：当前在修改哪个Mod、第二轮依据的是哪一份内容、被拒绝的设计是否已经进游戏，以及退出后能否找回未完成方案。

R13把这些对象分开：

| 对象 | 保存什么 | 生效条件 |
|---|---|---|
| 会话 | 完整消息、输入、滚动位置、提案引用、请求状态 | 自动落盘，不改变Mod |
| 请求 | 发出时的会话、Mod、配置ID、模型名、来源SHA和状态 | 只为这一轮任务提供身份与恢复依据 |
| 待审提案 | 真正编译出的candidate、预览、来源SHA及审批状态 | 玩家明确同意整份提案 |
| Mod版本 | 通过来源检查后导入的新版本 | 保存版本，不自动启用或替换当前对局 |
| 当前游戏资源 | 已部署资源与启动收据 | 下一次完整启动采用所选Mod |

API密钥与完整配置只属于独立配置模块。会话记录配置ID和模型名，不保存密钥、Authorization或自定义认证头。不要把可切换的模型配置对象整个塞进历史、上下文或诊断文件。

## 2. 页面结构服务于编辑流程

手机界面采用固定顶栏、中间独立滚动的气泡消息、底部输入区。历史抽屉按Mod查看会话，可以搜索、新建、改名、归档和恢复。会话始终绑定一个Mod，切换模型配置不等于切换编辑对象。

同一会话包含多份提案时，历史消息继续显示各自的处理状态。首版只支持整份同意或拒绝，避免卡牌、中文Key和关卡引用被拆开提交。打开卡片、关闭详情、返回会话都不代表同意。

视觉只参考DIY项目的深色底、棕紫面板、金色重点和圆角。保留Java原生View及现有资源引擎，不为配色改造引入Compose或另一个游戏Hook。输入框不随消息轮询重建，避免中文组合输入和正在输入的新内容被异步结果打断；键盘弹出后仍须能看到输入与发送操作。

会话切换前先把旧控件写回旧会话，再解除绑定并加载新会话。输入和滚动位置分别记录是否实际变更。新页面的空输入框或程序化scroll=0不能反写旧会话；旧页面的延迟滚动回调也不能作用于新会话。

## 3. 模型可以讨论，只有计划才能进入编译器

R13聊天输出增加一个外层：

```json
{"message":"先确认你希望保留哪项原技能。","plan":null}
```

`message`用于讨论、解释、澄清和不支持说明；`plan`为null时不替换当前待审方案。有修改时，plan仍须符合该Android版本实际开放的三资源合同，由本地确定性编译器处理。外层只允许约定字段，不从散文中猜测原生代码或执行任意脚本。

首次格式、聊天外壳或编译校验失败时，RC2在同一用户消息的**最多两次模型调用预算**内尝试一次修复。两次均失败就停止，保留旧提案和输入。HTTP认证/网络失败、取消以及凭据回传拦截不自动重试。原始FAIL继续留档，不能用修复后的成功记录替换它。

本地保存完整历史，联网上下文使用当前实际项目事实、待审候选、批准状态和有界历史。首版为最近12条消息、之前最多24条的短摘要，以及最近12个提案的状态。摘要不替代实际卡表；不将被拒绝的设计写成已经保存的游戏内容，也不无界上传全部本地历史。

## 4. 连续修改要沿候选分支编译

例如第一轮提出“鳄梨攻击改为6”，尚未同意，第二轮说“再加1攻并改小故事”。第二轮应从第一份candidate编译，最终卡片显示已保存版本→7攻的累计变化，而不是丢掉上一轮属性，或仅显示6→7使玩家看不清整份待审内容。

因此有两份基线需要同时保存：

- 工作基线：上一份未采纳candidate，供下一轮增量修改。
- 提交基线：原已保存Mod的ZIP SHA，供累计预览与最终来源检查。

新提案完成编译并成功写入会话后，才将旧待审提案标为`superseded`。讨论、澄清、unsupported、格式失败或编译失败均不清空旧待审提案。新卡也沿用上一轮**实际分配的GUID**，并继续使用安装级预约器；不能每轮按模型输出重新猜号或在取消后回收号码。

原草稿仍保留在旧目录。用户可以把真实草稿接入会话作为待审提案，但须校验Mod归属、来源SHA及candidate指纹；导入只产生“载入已有草稿”的记录，不伪造此前的聊天历史。

## 5. 对话内卡片来自真实编译结果

卡片使用提案报告中的`card_previews`，显示卡名、费用、攻击/生命、修改前后技能与中文。新增卡的before为空；原卡修改有真实before快照。展示的数据不能只依赖AI回复中声称“已经改为6攻”的文字。

点击卡片打开详情，继续查看属性、技能、小故事和目标提示。允许手改既有中文白名单字段：name、short_description、long_description、flavor_text、target_hint。手改生成新的子candidate及累计预览，仍需同意整份提案；不能借“改技能描述”绕过编译器改变技能逻辑。

卡片、消息和审批状态之间使用引用：消息存proposal_id，提案对象保存唯一的state及report。这样旧消息不会出现与真实提案不一致的“待同意”按钮。

## 6. 取消、过期与进程退出

请求发出时冻结会话ID、Mod ID、配置/模型、来源SHA和待审草稿。回包只归发起请求的会话。每次发布前核对本进程任务身份、请求ID和取消标记；切到另一会话或模型不能改变旧任务归属。

生成与编译期间可以停止；取消后晚到的HTTP回复或刚完成的编译不得发布提案或写Mod。为了不出现“界面已取消但Mod已经保存”，采纳进入写版本阶段后不提供中途取消。全局首版一次只运行一个工作任务，仍允许浏览其他会话和继续输入。

应用退出后没有本进程worker认领的generating/compiling请求标为interrupted，保留消息、输入和待审内容。accepting先核对采纳证据：存在匹配收据则恢复accepted；导入成功但收据前退出时，检查当前输出或历史版本及ZIP blob，再补收据。即使当前Mod后来已换到新版本，也只恢复旧采纳的真实结果，不重新导入或回退新版本。

来源Mod变化后，旧待审提案标为stale，仍可阅读，不能覆盖当前版本。来源SHA检查与实际导入必须处于同一个项目锁内；只给commit加锁，而让历史恢复和ZIP导入从其他线程无锁写入，仍有检查后被覆盖的窗口。R13使用按应用资源目录共享的LauncherStore工厂，项目索引读改写与commit共用同一实例锁，并只保留applicationContext。

## 7. 会话文件是真源，损坏不能静默清空

内部`native-workbench/conversations/sessions/<id>.json`保存完整会话；`navigation.json`只保存各Mod的选择，不作为消息索引。摘要从会话重建，导航丢失不等于历史丢失，失效选择也不能猜一个其他Mod的会话替代。

读写均使用独立JSON快照。多实例update在静态锁内重新读取，再修改和原子写回；异步追加消息时只改所需字段，不用请求开始时的旧快照覆盖最新输入/scroll。schema、会话ID、Mod ID和创建时间不可变；revision和更新时间由存储层维护。

schema 1只为缺失的可变字段补默认值；错误类型、身份缺失、未来schema、坏JSON均保留现场并显示错误，不自动变成空会话。落盘采用同目录暂存、文件同步、rename。归档只隐藏，拒绝只记状态。单份64MiB上限触发拒绝写入，不截断旧历史；这不等于模型请求长度或卡表能力上限。

Android与桌面JSON实现还存在差异：Android对JSONObject.NULL调用optString可能得到字面`"null"`。可空pending_proposal_id应先isNull再取值，不能只依赖桌面JSON jar的默认值行为。R13对此使用本机官方Android JSON源码另跑服务回归。
