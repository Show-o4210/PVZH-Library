# 01. 语义接口与测试流程

语义测试接口把“对谁、用什么卡、作用于哪个实体”作为参数，调用原版出牌、抽牌、召唤及阶段推进流程。它无需根据屏幕坐标猜测卡牌位置，也不需要用截图推断每次生命变化。

本页依据R19的 `scripts/test.py`、`scripts/session.py`、`scripts/cli.py` 和 `src/runtime.js` 整理；这些源文件保留在原工程，身份见[引用索引](06.R19实现与验收记录/工程资料索引.md)。下列命令是对应工程的接口说明，不是本库自带的可执行测试工具。

## 一、入口和运行边界

R19由APK内置Gadget启动本地服务。案例端口为设备及主机的 `127.0.0.1:43132`，ADB通过端口转发访问；它不是远程游戏服务，也不需要外部frida-server。ADB设备号、包名及端口应从当前工程确认，不照抄案例设备号。

请求为一行JSON，末尾换行；响应也为一行JSON：

```json
{"op":"state"}
```

```json
{"ok":true,"result":{}}
```

失败响应含 `ok:false` 与 `error`；不要仅凭socket连接成功判断操作已经完成。正常CLI会把接口拒绝作为失败返回。

命令在Unity主线程执行。该版使用 `UnitySynchronizationContext.ExecuteTasks` 的replacement包装，并保持原函数调用、ABI和重入保护；旧的onEnter调度曾使嵌套技能hook被Gum回调保护抑制。这个修正不能推广为所有Frida版本必须使用同一写法，移植时须同时验证线程与嵌套hook是否实际触发。

## 二、选择模式与建局

1. 先确认候选APK、脚本指纹、实际设备、卡表版本和资源模式。
2. 冷启动先经过必选门卫，再等 `installed` 与 `app_ready`。R19调试命令有约120秒启动暖机，普通界面不受此调试等待限制。
3. `session.launch(reset=True, profile='mod2')` 强停并通过显式测试Intent请求真正的资源按钮；`original`同理。
4. `reset=False`连接已运行的进程，不会把当前mod2热切成original；连接后必须核对实际 `status.resource_profile`。
5. `start_fixture`使用独立 `agent_test` 节点并支持固定seed、生命和资源。默认无画面对局由命令控制双方；它不是AI自动决策测试。

R19的 `app_ready` 不证明旧Context已移除或所有依赖实例完成初始化。连续温重开与一次含新卡的初始牌组冷建局都发生过访问异常；不要无限重试或把固定等待当作清理屏障。出现native access violation后立即停止向该模型发送命令，再强停恢复，并独立保存失败。

## 三、常用操作

在匹配的 `mod2-runtime` 工程目录执行，使用项目现有兼容Python：

```powershell
python -B scripts/test.py start --sun 50 --health 100 --seed 1337
python -B scripts/test.py give 601
python -B scripts/test.py state
python -B scripts/test.py plays
```

| CLI／原始op | 含义与要点 |
|---|---|
| `status`、`app_ready` | 查版本、模式、安装状态、暖机和就绪；不是技能验收 |
| `cards`、`card`／`card_info` | 查实际加载的卡牌定义；GUID不是在场实体ID |
| `give <GUID>` | 指定卡经原版抽牌流程入手，已有牌库数量与顺序保持 |
| `draw` | 自然抽牌，消耗原牌库顶牌 |
| `draw --guid <GUID> --count N` | 指定抽入测试卡；数量限制以当前源码为准，R19为1–10 |
| `plays`／`legal_plays` | 读取当前玩家的合法动作、实体ID、目标与order |
| `play <card_id> --targets ... --order ...` | 使用实际合法候选，保留原版费用、目标与触发 |
| `select`／`select_target` | 完成原生后续选目标，不能忽略choice状态 |
| `summon <GUID> --lane <0..4>` | 直接原生创建单位，不花出牌费用；不能代替合法墓碑打出或PlayTrigger测试 |
| `end`／`end_phase` | 为当前活动玩家推进阶段 |
| `fixture_effect` | 原生白名单效果，用来建立受伤、增益等前置条件 |

`--player`或原始 `player_id` 显式指定玩家。每局从state读取local/opponent和实体ID，不依赖历史中的0、5、24等号码。`summon`使用路线序号0–4，`play`的targets使用合法动作中真实目标实体ID，两者不可混淆。

完整对局循环应先读state，处理尚未完成的目标选择，等当前阶段可操作，再提交合法出牌；没有出牌则推进阶段。观察到 `game_over` 后停止修改，不继续打牌。R19已用该方式完成原版36次操作的胜利，以及普通牌组加指定测试卡后的改版23次操作终局。

## 四、设置前置条件和观察结果

`fixture_effect`只允许当前源码列出的效果与字段。R19包含Damage、Heal、Buff、SetStat、ExtraAttack、Grant、变墓碑、回手、Destroy和Slow，不提供任意字段写入、任意原生方法执行或直接Reveal／StateCheck。

R19的fixture Grant仅允许原版0–18与动作1012–1014；持续规则1001–1011来自卡体配置，不能把它们直接当成可授予的原版能力。伤害案例必须指定正确的source、player和target，以便核对阵营归属、倍率与受伤反应。

- `mod2_status`：技能计数、错误、待处理记录和资源模式。
- `events`：调试事件；有容量上限，短窗口比较时需防止ring淘汰。
- `mod2_history`：显式只读History快照，始终 `complete_history:false`。
- `animation_status`：真实动画结构的只读诊断；缺节点或截断应明确报告。
- `mod2_trace`：默认关闭的窄触发诊断，不能把观察日志当作技能执行器。

比较同generation中的前后状态、来源、目标和生命差，并做反例。Destroy可能仅先标记死亡，要等原版阶段与StateCheck观察实际离场；墓碑需要真实手牌出牌及正常揭示，不能把summon当成自动FaceDown。

无画面fixture的 `animations_empty` 不证明真实动画完成。带渲染验证使用新的冷进程，观察真实busy→empty和完整回合；模型结算、History生成、消费者完成、逐帧美术是不同证据层级。
