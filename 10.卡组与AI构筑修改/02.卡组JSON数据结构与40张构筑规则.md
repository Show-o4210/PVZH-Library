# 02. 卡组 JSON 数据结构与 40 张构筑规则

理解 PVZH 中不同场景下的卡组 JSON 数据结构，是修改人机出牌、制作每日挑战（BOTD）与关卡特化卡组的核心基础。

本篇详细对比解构客户端与资源包中存在的三种典型卡组 JSON 格式，并基于底层真实数据说明卡组构筑规则与底膜破解的真实机制。

---

## 一、 PVZH 三大典型卡组 JSON 格式解构

在 Unity 引擎数据层中，PVZH 存在三种不同结构的卡组 JSON 格式：

### 格式 1：`decks/` 全局通用卡组结构 (`Cards` 数组结构)
这是玩家自定义卡组与常规 AI 通用卡组（`deck_data_*`）的标准数据格式，对应检索索引库 [decks.json](../资源/decks.json)：

```json
{
  "DeckId": "Deck_SolarFlare_Custom",
  "HeroId": 900000001,
  "ignoreDeckLimit": false,
  "Cards": [
    { "CardGuid": 900000101, "Count": 4 },
    { "CardGuid": 900000102, "Count": 4 },
    { "CardGuid": 900000103, "Count": 4 }
  ]
}
```

| 属性 Key | 数据类型 | 核心含义与作用 |
| :--- | :---: | :--- |
| **`DeckId`** | `string` | 卡组唯一识别名称（如 `Deck_SolarFlare_Strategy1`）。 |
| **`HeroId`** | `long` | 绑定英雄的唯一 GUID（如 900000001 代表耀斑花）。 |
| **`ignoreDeckLimit`** | `bool` | 是否忽略标准 40 张与单卡 4 张上限标志位。 |
| **`Cards`** | `array` | 卡牌组合列表，每一项包含 `CardGuid` (卡牌数字/字符串 GUID) 与 `Count` (携带张数)。 |

---

### 格式 2：`data_assets/` 独立卡组结构 (`MainDeckCardIds` 平铺数组)
这是关卡底包 `data_assets_*` 中储存的独立卡组格式（如战役关卡、BOTD 每日挑战与 PVE 卡组）：

```json
{
  "DeckName": "",
  "MainDeckCardIds": [
    175, 175, 175, 177, 177, 177, 182, 182, 182, 182,
    23, 23, 23, 23, 250, 250, 250, 321, 321, 321,
    249, 249, 249, 238, 238, 238, 238, 71, 71, 167
  ],
  "SuperpowerOverrideCardIds": []
}
```

| 属性 Key | 数据类型 | 核心含义与作用 |
| :--- | :---: | :--- |
| **`DeckName`** | `string` | 显示名称（一般留空，由关联的关卡节点或内部 Key 控制）。 |
| **`MainDeckCardIds`** | `array[int]` | **平铺卡牌 ID 数组**。每包含一张该卡牌，数组中就包含一个对应数字 ID。 |
| **`SuperpowerOverrideCardIds`** | `array[int]` | 手动指定/替换该卡组出战时的超能技能卡 ID（若为空则使用英雄默认超能）。 |

---

### 格式 3：关卡 JSON 内嵌入卡组约束配置 (`OpponentConfig.Parameters`)
在关卡 TextAsset 中（详见 [09. 关卡修改](../09.关卡修改/README.md)），除关联 `DeckId` 外，还可在 `Parameters` 节点中动态调控摸牌与抽卡行为：

```json
"Parameters": {
  "Faction": 1,
  "MinimumDeckSize": 0,
  "InitialCardsToDrawFromDeck": 4,
  "InitialCardsToDrawFromSuperpowerPool": 1,
  "NumCardsToDrawPerTurn": 1,
  "InitialSunCount": 1,
  "ShuffleDeckAtStartOfGame": true,
  "CreateAllCardsInDeck": false
}
```

## 二、 40 张构筑规则与底层数据实证分析

根据 Python `UnityPy` 对官方 `data_assets` 中 **768 套预设卡组** 的真实解包统计，官方卡组张数分布如下：

```
张数分布统计表：
- 40 张标准套牌 : 672 套 (如 Deck_GrassKnuckles_R3 等天梯/常规对局卡组)
-  2 张极端微型 :   2 套 (如 Surprise_2_Middle Managers)
-  4 ~ 12 张残局 :  17 套 (如 botd_w16d6_plant 等 BOTD 每日挑战解密)
- 16 ~ 39 张非标 :  62 套 (如 botd_w15d6_zombie 为 32 张卡)
- 41 ~ 49 张扩充 :  11 套 (如 Soft_PVE_Deck_Plant_SolarFlare_012 为 41 张卡)
- 60 ~ 66 张大型 :   2 套 (如 Set3_All_Plants 60 张, Set3_All_Zombies 66 张)
- 212 张卡包资产 :   1 套 (New User Initial Cards 初始玩家全卡库)
- 440 张全卡沙盒 :   1 套 (SANDBOX_PURCHASE_UNLOCKS_ALL_THE_CARDS 沙盒解锁全卡牌)
```

## 三、 关于 Mod 破限的真实可行路径（避坑澄清）

> [!WARNING]
> **澄清：单纯改 JSON 中的 `ignoreDeckLimit` 走不通！**
> 很多初学者以为只要在 JSON 中将 `ignoreDeckLimit` 改为 `true` 就能在客户端卡册里随意组组 40 张同名卡或突破上限。**这种做法在常规客户端组牌界面是行不通的**！
> 
> **底层约束机制**：
> 1. **引擎 C# / Native 逻辑校验**：PVZH 客户端代码（`libil2cpp.so`）在卡册组牌与提交出战时，会在底层 C# 运行期硬性校验单卡 4 张上限与双职业规则，单纯修改 TextAsset 中的标志位会被客户端逻辑直接覆盖或忽略。
> 2. **真破限路径（底膜修改）**：要真正实现常规对局/卡册中的组牌破限（例如突破单卡 4 张限制或跨职业限制），**必须走更底层的 Native 汇编修改**（即修改 `libil2cpp.so` 动态库中负责 `DeckLimit` 校验的 C# 方法汇编指令）。具体技术原理与汇编 Patch 请参考 [11. 静态高级实战](../11.静态高级实战/README.md)。
> 3. **关卡 PVE 原生支持**：无需修改 `so` 即可突破 40 张限制的**唯一合法场景**，是在自定义关卡 JSON 的 `MainDeckCardIds` 数组中直接配置非 40 张卡牌（如前文统计的 BOTD 每日解密关卡）。
