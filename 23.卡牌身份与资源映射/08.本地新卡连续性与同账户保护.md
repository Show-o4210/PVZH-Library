# 08 · 本地新卡连续性与同账户保护

本节接续[R26可配置获取](06.可配置新卡获取与手机Mod列表.md)及[R28资源绑定故障](07.原版资源名校验与自动获取启动故障.md)，记录2026-10-25 Android R29的新保护。**自动获取负责补到玩家选择的目标；连续性保护只保留已证明属于同一账户、同一卡身份的本地已有数量。** 关闭自动获取仍可执行后者，不能通过重新发4张掩盖库存丢失。

已有RC2主用户连续性恢复观察，并补充RC4真实AI普通模板新卡的获取与正式加载结果；两者属于不同候选，不拼成全技能稳定验收。没有官方云端支持自定义GUID的结论。Mod内许可、恢复入口和RC4跳过对局的边界见[第21章11](../21.语义调试与技能扩展实战/11.Mod内能力与启动健康恢复/README.md)。

## 制作时先选对模板

R29真实AI曾为普通新卡选择345 Magic Beanstalk。其原版metadata为`set=Token`，顶层tags和根Tags组件均含`cheats`；新增GUID和技能编译不改变这些收藏限制，因此不自动获得。用户明确决定保留游戏限制：供玩家获取／组牌的新卡应选原版可收藏非Token模板，精确外观只有Token时应说明冲突并建议其他模板。

本轮没有`collection`计划字段或Token转普通卡功能。AI资料、候选事实与UI只增加只读分类／警告；实际set、双层cheats、Unusable、超能及原生资格仍要核对，不能凭名称、技能树或模型自述声称可获取。只读分类和原合同拒绝687项主机检查，不等于新一轮实机收藏通过。此类模板选择错误和下面“有效已有卡后来被替换”的问题分开排查，不能靠连续性保护、调试give或强制发Token绕过。

同一RC2候选的原生资格检查另证：10 Peashooter为allowed=true、Silver、usable=true、ignoreDeckLimit=true；345为Token且allowed=false；653为Set4、allowed=true、ignoreDeckLimit=false。因此`ignoreDeckLimit=true`本身不是不可收藏标记，不能用它否定原版豌豆射手；只读摘要保留真实字段，不改原版牌组规则。这只覆盖这三个原生检查，不代表650定义全部实机资格已验。来源为[三模板实际报告](../../pvzh-launcher/native-r29/evidence/rc2-native-template-eligibility.json)和[只读模板指导](../../pvzh-launcher/native-r29/docs/TEMPLATE-COLLECTION-GUIDANCE.md)。

## 1. 为什么要在Unity前留下证明

R28已证明本地持久化及离线读取，但保留了首次cold再次从0补齐的失败。R29观察到：自动获取关闭、受控首个托管Unity帧尚未执行时，已有新卡就可能从本地文件消失。只在player-cards模块开始后读当前内存，可能拿到已经替换的空值。

因此在资源／PlayerCardSafety事务成功之后、每条Unity释放路径之前调用`NativeInventoryContinuity.prepare`。它只读当前Android用户下的本地`PlayerInventory`：核对实际卡表SHA、字典GUID与Card.Guid、冻结新卡身份；排除Token、超能力、Unusable、Blank和Cheats。运行时仍须再次检查原生收藏资格。

新GUID不是充分条件。另一Mod同号但不同namespace／身份的卡，不得继承旧数量；已经移除、不在获胜卡表或不可收藏的卡也不能靠快照重新启用。原版／没有合格候选时不遍历账户库存。

私有证明包含本次事务、PID、卡表和身份摘要，以及每个已有本地账户库存的来源路径、源SHA和正数量。有效期15分钟，超过5秒的未来时间拒绝；跨事务／PID不自动重放。外层保存原JSON文本与SHA并在Java／JS双层验证。它不读取Delta作为拥有权来源，不复制货币、英雄、卡包或整份旧存档，也不随Mod导出。

## 2. 账号和缓存路径必须同时可信

`PlayerInventory`自身没有账户字段，holder指针也不足以证明归属。运行时同时要求exact本地holder、当前IoC holder相同、exact LocalPlayerInventoryPersister、当前AuthedIdentity以及原生locator和persister缓存路径一致。缓存的完整路径还必须落在当前应用／当前Android用户的同账户库存文件。

原生身份persister会缓存内部GenericProtobufPersister，因此只读当前GetIdentity不足以排除“新账户身份＋旧账户保存器”。身份变化推进epoch，清理在途同步归属并放弃不能安全保存的工作。无需读取或记录AuthenticationToken。

路径不明、账号变化、旧事务、未知身份是正常保护性skip；不能为追求恢复率，放宽为任意`PlayerData`目录、跨Android用户或只按GUID匹配。

## 3. 启动只消费一次，缺键和0严格区分

`Cards`是`Dictionary<int,int>`。必须使用ContainsKey区分“根本缺键”和“明确记录为0”：

| 首个可判定本地库存 | 行为 |
| --- | --- |
| 已有4张 | 不写入，消费本次seed |
| 明确0张／现有2张 | 保留0或2，消费seed |
| 缺键，证明同账户同身份曾有4张 | 恢复原4张，与目标数量2或8无关，消费seed |
| 原生定义未载入 | 暂缓判定；不可收藏时不恢复 |

“无需恢复也消费”很关键：玩家之后合法消耗到缺键，不能被启动前4张反复复活。恢复后走原生SaveLocalPlayerInventoryCommand及本地persister，再LoadOrCreate读回；计入`bootstrap_saves`，不调用AddCardToInventory、不计为自动获取。

字典异常撤销本次插入；保存失败重试按此刻真实数量，不能max到历史seed。真实写入／读回异常进入健康partial，正常skip只留诊断。

## 4. 后续Sync只保护紧邻旧库存

实现额外观察IdentityProvider.SetIdentity、SyncPlayerInventoryCommand.OnExecute和LogSuccessAndAcceptServerData。既有SetLocalInventory入口只在确切接受位置、同线程、同holder、同旧对象、同请求账户／epoch下才执行缺键复制；不能把所有Set都当服务器同步。

复制源是Set前再次读取的旧本地真实数量：旧2张且新对象缺键时保留2；旧0或缺键不复活；新对象显式0或更少数量不覆盖。请求归属不明、调用点／线程／身份变化都跳过。不得修改服务器DTO、Delta／Sync persister、原卡或货币。

该分支的主机负例通过不代表设备已执行官方成功同步。下面的RC2观察中`sync_accepts=0`，因此只能确认启动接管恢复，不能宣称此Sync分支已成功、EA服务已接受新卡或云端会保存namespace。

## 5. RC2实际观察及没有证明的事

Pixel6主用户RC2、auto关闭，APK SHA256为`b5350bfaa325ba66ef5ad096f20dea54d2940b08ebfa66d409c9de1225c8dc5d`。本次证明当前账户启动前已有900054四张。

| 观察项 | 结果 |
| --- | --- |
| 磁盘时间线 | 100ms为4；44,211ms为0；46,381ms恢复4，观察缺失后约2.17秒恢复 |
| 最终原生／磁盘 | 4／4 |
| 原自动获取 | `grants=[] / native_saves=0` |
| 连续性接管 | consumed1、restored_records1、bootstrap_saves1、pending_save=false |
| 错误 | player-cards与连续性errors均为空 |
| 后续Sync分支 | accepts0、restored0、保存验证0；skip为`sync-definitions-not-ready` |
| 网络与报告状态 | 默认网络137，`validated_internet=false`；`OBSERVED_PENDING_DIRECT_HTTPS_PROOF` |

本次证明真实字典插入、原生本地保存和读回走通，且没有借自动获取补到目标。它没有证明库存最初被谁替换，更没有证明官方Sync成功。默认路由存在不等于系统或应用层外网已验证；后续网络证明要另列，不能回写本报告。重复冷启、数量变化、已有新卡牌组、正式玩家流程与最终稳定结论仍需最终候选的分组证据。

## 6. 失败恢复的保留边界

若早期文件已被替换，而card-assets又在消费seed之前失败，下个PID不会自动重放旧证明。新prepare覆盖active前，按原快照文件SHA归档到私有history，保留来源供明确恢复；本轮未实现自动跨PID续期或面向用户的历史库存恢复操作。不能以健康ready、保留了备份或存在恢复按钮，推断任何失败后都能自动救回。

私有库存证明含账户持卡信息，不进Library、Git、Mod导出或公开源码包。本库只收字段筛选摘要，不能当作共享卡库或官方云存档。

## 8. RC4按普通模板自然获得新卡

RC4 SHA256为`42c084fce94bdbf8dae5b9ecc623502e02f23a7d63d016363d2175b80115ec62`。真实AI重新选择653 Typical Beanstalk，生成900002“试炼豆芽”，保持Set4、usable=true且没有cheats；独立身份及资源复用不变，后续仅把血量3改4。未开放Token转换，也没有用调试give或强制发Token。

实际UI勾选Mod并正常启动，900002的原生资格allowed=true、库存4张、errors为空；再次观察补差quantity=0、before=after=4。正式40张牌组及原进度节点入口实际采用新卡资源，sprite可加载。该结果证明所选普通模板可以按既有获取流程使用，不能替345 Token未获得的旧结果改成PASS，也不能单凭这份quantity=0报告宣称全套冷启／官方Sync已经通过。

card、refine、reject和确认NodeID后的关卡真实API流程与独立保存产物检查通过；拒绝未改已存Mod。正式关卡实际采用40僵尸英雄血、10初始阳光和359／356场景实体。用户随后明确要求跳过当前对局，实际打出新卡造成3伤／抽1及下一回合精确场景增量记录为**USER_SKIPPED**，不称技能实机通过。
