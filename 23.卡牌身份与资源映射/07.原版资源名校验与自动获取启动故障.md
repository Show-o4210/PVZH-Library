# 07 · 原版资源名校验与自动获取启动故障

本节整理2026-10-25 Android R28的资源绑定修复。前面的[03](03.新增GUID与资源复用流程.md)讲新身份与资源复用，[06](06.可配置新卡获取与手机Mod列表.md)讲补卡与持久化；本节补充两者之间容易遗漏的**运行时初始化是否成功**。原版公开Python v1合同不变。

当前证据状态：原版数据分类、主机回归及RC2实际APK独立检查通过；Pixel6首次补足21项、关闭补卡且离线的独立冷重启22项、恢复原配置后的最终启动22项通过，最终交付收据为 **PASS**，已证明这张卡真实本地落盘。最初cold的“零补差／零额外保存”检查失败仍保留，其有效网络状态未取证，不能称为已验证联网启动。后续恢复网络开关的对照没有实际默认网络，因果判断仍为 **INCONCLUSIVE**。本地持久化通过，不代表初次库存重发原因已解决或官方云同步兼容。

## 1. 已加载卡表不等于补卡模块已经安装

现场新卡为“守望豆芽”900054，3费2/4，使用原版模板653的资源 `Typical Beanstalk`。活动Mod、实际卡表和中文收据一致，自动获取保存配置与本次冻结配置均为开启、每卡4张，新增候选也包含900054；库存仍没有该卡。

这不是Token继承导致的拒绝。模板和新卡元数据均为 `usable=true / set=Set4 / isPower=false / isPrimaryPower=false`。真正错误来自此前资源绑定校验只接受英数字、下划线、短横线，误拒了资源名中的空格。

当时初始化按 `card-assets → player-cards → 后续模块` 执行。前者抛出 `Invalid original-resource binding` 后，启动状态变为 `installed=false / boot_failed_phase=card-assets`，后面的自动获取Hook没有安装。本进程只尝试初始化一次，重新读取库存或提高获取数量无法修复这种失败。游戏主体仍可能运行，因此表面症状只是“没有发新卡”。

`player_cards_status` 或原生可组牌检查若也被启动失败拦截，应记录“检查未执行”，不能把它写成“该卡不允许组牌”或“库存保存失败”。此前分层验收未覆盖这个模板名字，旧结果不回写为已覆盖全部原版模板。

## 2. 身份别名与原版资源名使用不同规则

新增卡别名如 `pvzhmod_<项目摘要>_<GUID>` 是程序生成的标识符，可以使用严格格式；`resource_prefab` 是原版资源数据，不应该套同一份标识符正则。

原版资源名字可能带空格或单引号，例如 `Typical Beanstalk`、`Jack O' Lantern`。必须保留原样；删除空格、换下划线或任意改名会改变实际寻址目标，不能作为修复。

R28使用冻结可信原版表建立 `template_guid → prefabName` 精确白名单，每条绑定同时检查：

- 独立别名符合生成格式，且与新增GUID一致；GUID为有效整数。
- `template_guid` 是原版名单中具有真实资源名字的模板。
- `resource_prefab` 与该模板的原版名字逐字符一致。
- 不含路径分隔符、控制字符、冒号或危险路径段 `.`、`..`，也不接受未知资源名。

这不意味着允许导入包任意声明本机路径。白名单必须来自匹配版本的可信原版底稿，不能从正在加载的改版表反向生成“原版”。更换基础版本时重新读取来源并核对哈希，不能把R28的固定表当成所有版本通用数据。

Java生成绑定与Gadget运行时应使用一致的来源约束。Java编译或绑定检查通过，只证明该阶段通过；运行时仍需报告真实安装状态。

## 3. 全量原版检查先分类，不能要求每条都有美术

R28读取的冻结原版卡表共有650个定义：

| 分组 | 数量 | 处理 |
| --- | --- | --- |
| 有真实资源名字 | 646 | 逐项验证原名与模板绑定，全部进入资源白名单 |
| 其中 `usable=true` | 600 | 属于上述646的子集；不是“600张都可收藏”的证明 |
| 无资源占位定义 | 4 | 562、564、615、668；均 `prefabName=null / usable=false`，不作为可绑定模板 |

旧正则误拒224个有名模板，它们都带空格，其中2个还带单引号。这个统计是资源名字覆盖，不是全部卡牌技能或收藏资格验证。

初版R28曾把4个null占位也送入要求有效名字的白名单构造器，使空绑定／原版入口同样可能初始化失败。主机及独立APK检查发现后，RC1在安装前被拒绝并保留失败记录。修正为646有名资源与4个不可用占位分组，再验证空绑定启动。不能把RC1构建成功当成交付成功，也不能为方便把null强转成字符串 `"null"`。

## 4. “新卡没获取”的排查顺序

1. 保留现场，先核对待审提案、已采纳Mod、勾选顺序与实际加载收据。实际卡表／中文哈希必须与本次采用来源一致；不能只看Mod开关或文件名。
2. 核对新GUID是否真的存在于最终卡表，并出现在相对可信原版表的候选差集中。多Mod仍是整文件优先，不自动取所有勾选卡表的新卡并集。
3. 分别核对已保存配置与本次冻结采用配置的自动获取开关、目标数量。进程已启动后改设置，不代表本次已生效。
4. 检查模板、原版资源名、独立别名与CN Key关系。已有合法空格／单引号不能误判成未知资源；不可用或Token模板也不能仅因新GUID就强制变可收藏。
5. 查看运行时 `installed`、`boot_phase`、`boot_failed_phase` 和首个错误。若资源模块先失败，先修初始化；不要把后面没有执行的补卡和资格检查写成各自失败。
6. 初始化成功后，才检查原生可组牌资格、mapper/本地holder就绪、当前拥有数、实际补差及原版持久化命令。保留Token排除、身份变化与失效引用保护。
7. 冷重启验证要检查 `before / after / quantity`。再次看到4张可能是每次从0重发，不能单凭显示数量证明落盘；应确认重启前库存已保存，重启后原生读到4且补差为0。收藏画面、组牌与技能结算仍分别留证。

如果冷启动仍出现补发，应保留这条失败，再用“关闭自动获取、离线、完整新进程”隔离验证本地保存。若要判断网络影响，另做有效联网且关闭获取的对照，必须记录Android实际默认链路／连接状态，不能只依据Wi-Fi和移动数据开关。两种检查回答不同问题：前者确认原生本地文件能否被独立读回，后者才可能支持网络相关判断。不能因为本地保存通过，就删除重发失败；也不能在未跟踪实际来源调用时，把库存重发确定归因于服务器、云同步或已经安装成功的资源校验。

文档中的排查顺序不是自动连接设备、修改玩家存档或调用发卡接口的授权。实际操作遵循用户当次范围；不通过删库存、改set或手工发卡掩盖初始化错误。
