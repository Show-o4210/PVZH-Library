# 06 · 可配置新卡获取与手机 Mod 列表

本节整理Android启动器R26在R25 RC5之后的增量：把既有“新卡补四张”改为可配置开关/目标数量，并提供手机Mod列表封面与常驻开关。本文不修改公开Python v1制卡合同，也不把UI或离线测试当作游戏实际拥有权证明。此前资源身份关系先读[01](01.身份、文本与技能的关系.md)、[03](03.新增GUID与资源复用流程.md)，玩家生命周期与服务器限制读[05](05.本地新卡身份与服务器裸GUID边界.md)和[Agent15](../agents/15-multimod-player-lifecycle.md)。

## 1. 新卡定义、可收藏和实际拥有是三回事

在 `card_data` 增加GUID，只能证明多了一份定义。资源别名解决卡面/动画寻址，CN Key解决独立文字；这些都不自动等于普通收藏拥有。

启动时先确定最终实际采用的卡表，再取它相对可信原版表的GUID差集。之后继续使用本版原版可组牌资格，排除不可用、超能力、主超能力、Token和原版过滤不允许的定义。候选清单中出现Token不等于Token会被发放，候选与资格过滤是两个阶段。

多Mod仍按同名逻辑资源整文件覆盖。A、B同时勾选且都提供卡表时，列表靠前者的整表生效；“所有勾选Mod的新卡并集”不是本版语义。中文和关卡各自也可能由不同包提供，组合冲突继续提示，不能借补卡机制暗中按GUID/CN Key合并。

## 2. 自动补足必须与安全修复分开

R26保存设置默认开启、目标4张，数量为1～999，下一次完整启动采用。只补足，不反复增加，也不因调小数量或关闭开关扣除已经持有的有效同身份卡：

```text
补足数量 = max(0, 目标数量 - 已持有数量)
```

这只控制本地新卡获取。GUID同号身份核对、旧引用备份、已移除新卡与坏档牌组处理仍要执行；不能因为“用户关闭自动获取”而关闭这些保护。若Mod移除后定义不再存在，相关旧引用仍按既有保护策略处理，这与降低目标数量不扣库存并不矛盾。

保存配置与本次运行配置要使用不同语义字段：

| 层级 | 字段 | 含义 |
| --- | --- | --- |
| 保存设置 | `enabled`、`quantity`、`revision` | 下次启动希望的自动补足配置 |
| 冻结运行配置 | `enabled` | 原有Mod卡库模式许可，不能改作补卡开关 |
| 冻结运行配置 | `auto_grant_enabled`、`grant_quantity`、`settings_revision` | 本次实际采用的补足开关、数量和修订 |
| 冻结运行配置 | `valid_guids`、`candidate_guids` | 最终有效GUID与相对原版新增候选 |

缺省配置兼容旧版本补四张；损坏配置报告技术失败，不静默覆盖。设置同值保存不递增修订。Unity已载入后不把改磁盘文件描述为即时生效，仍需完整重启。

目标数量超过4只影响本地拥有数，不改变原版牌组职业、40张或同卡张数等约束。保留准确holder、mapper就绪、本地inventory与Delta隔离，不扩展服务器裸GUID协议，也不宣称联机、云端或跨设备兼容。

## 2.1 补入内存不等于库存已经保存

RC1真实测试首次普通新卡4张、Token0、原Validator保存40张和fixture合法出牌都通过，但repeat冷启动显示`before=0, after=4, quantity=4`。旧固定目标实现每次重新补4张，掩盖了没有落盘；“重启后还是4张”不能单独证明持久化。旧版本的当时检查保留，本节补充它们的判定边界。

匹配1.67.8 ARM64原生实现中，`AddCardToInventory`只更新Dictionary，`SetLocalPlayerInventory`也只替换引用。`SaveLocalPlayerInventoryCommand.Execute`先检查HasLocal与IsDirty，再取本地库存，调用`LocalPlayerInventoryPersister.Write`，最后清Dirty。应复用原版身份/serializer，不手写玩家protobuf，不误用Delta或SyncPersister。

RC2仅实际补差或旧pending时，验证exact本地holder与库存身份，`MarkDirty(true)`后调用原命令，经原LocalPersister.LoadOrCreate读回本轮改动数。保存失败保留pending，零差值时也应重试；新补差先失效旧lastMerge，缓存判断不得跳过pending。成功读回后才能报告合并完成。读回短期GC根成对释放，不为每次保存永久占根。

原生读回仍不替代独立冷启动。应检查repeat的补差为0，再把目标升到8、改成2并冷启动仍持有8；同时核Token为0、原版卡数量和InventoryDelta文件不变。下面的最终证据表逐层登记，不能从命令反汇编或host mock直接推断Android持久化通过。

## 2.2 set=Silver还会影响启动库存修复

RC2首次4张与重复冷启通过后，八张测试仍失败：原保存命令曾读回8，稍后原始库存与磁盘变成4，原InventoryDelta多出该新GUID的-4。直接反汇编核对发现`FixupLocalPlayerInventoryCommand.OnExecute`对数量≥5的卡调用私有`IsSilverCard`，以CardData.Set和字符串`Silver`比较，为真则派发`4-count`修正。因此这不是GetCount/收藏界面统一截断，更不是新保存代码直接写Delta。

夹具克隆原版豌豆10，继承set=Silver、rarity=4/R0。资源复用与新增GUID成立，并不保证摆脱原版按set执行的账户规则。仅重新检查字典版本可发现数量被改，却无法让“目标降至2时原8张保留”自动成立；也不能改成上限4或偷偷改卡set来掩盖这个失败。

RC3选择精确保护当前Mod有效可收藏新GUID：仅私有Fixup.IsSilverCard原返回true时豁免该新卡，原版650张、未知、Token、超能、不可用及原版入口保持原逻辑。auto关闭仍保留这一保护，因为关闭获取不应使旧库存被扣。这是匹配1.67.8 ARM64/RVA签名的一处新增Hook，不是全局跳过Fixup，也不是开放新技能配方；26项技能登记不变。运行结果按最终表单独验收，不能把静态链条当作已经观察到该现场指令trace。

## 3. 列表封面只是展示资源

手机默认行使用56dp封面、单行名称、小字revision、右侧常驻Switch；点封面/标题/版本/整行进入原有详情。资源、冲突、路径等说明放在二级，排序模式才显示长按拖动把手。开关保存失败回退原值，避免界面显示与保存方案不同。

`mod.json` 可选字段示意：

```json
{"thumbnail":"art/cover.png"}
```

它只用于启动器封面，不等于替换游戏卡面，不参与Manifest的卡牌资产寻址。选最浅、字典序优先清单，字符串路径优先按清单所在目录解析，再尝试包根；没有指定图时可回退cover/thumbnail/preview/icon常规文件名。

ZIP仅作为只读容器，不解压到任意路径、不执行其中代码、不请求URL。路径拒绝绝对形式、反斜杠、URL/冒号、控制字符、空段、`.`和`..`。本例边界为清单64KiB、每图4MiB、目录20000项、最多8张候选，PNG/JPEG/WebP尺寸≤8192、像素≤32Mi，解码前按显示大小采样。

小型LRU按ZIP SHA及显示尺寸区分，换包不复用旧图；无图/坏图/超限图用暖色首字封面。后台队列有界，异步结果要核对请求标识、Activity生命周期及视图附着，避免列表重建、改名或换包后串图。可选封面失败不能阻止Mod启动。

## 4. 数量编辑与测试工具也要守住边界

原生AlertDialog默认正按钮会自动关闭。数量输入应在show后覆盖正按钮监听，仅在整数合法且持久化成功后关闭；0、1000、空输入等原位显示错误。不能让用户看到“保存成功”，实际却写入旧值。

窄开发动作 `new_cards_set` 仅接收 `enabled` Boolean与`quantity`整数两个字段。旧transport若自动添加 `_request_id` 应修正传输层，不能为测试方便放宽业务schema。correlation可用现有Intent额外字段记录。没有增加任意脚本、路径读取或native执行入口。

图标控件的content-description含机器标识及可读标题后缀时，测试工具应按既有约定识别。测试Intent可能重新渲染Activity，打开的Dialog却仍覆盖其上；这种测试编排失误必须留证并修正runner，不能误判为生产UI故障。
